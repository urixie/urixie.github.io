FreeRTOS 队列、信号量与互斥锁

多任务系统中，最容易出问题的地方不是任务创建，而是任务之间如何传递数据、如何等待事件、如何保护共享资源。FreeRTOS 提供队列、信号量、互斥锁和任务通知来解决这些问题。

经验法则：传数据优先用队列；通知事件优先用任务通知或二值信号量；保护共享资源用互斥锁；中断里只通知任务，不做复杂业务处理。

1. 队列：任务间传递数据

队列适合在任务之间传递结构体、消息、命令、采样值或事件。发送方把数据复制进队列，接收方从队列中取出数据。 

typedef struct {
    uint8_t cmd;
    uint16_t value;
} app_msg_t;

static QueueHandle_t s_msg_queue;

s_msg_queue = xQueueCreate(8, sizeof(app_msg_t));

队列是 FreeRTOS 中最常用、最安全的数据通道之一。它能减少全局变量共享带来的并发问题。

2. 队列发送与接收

app_msg_t msg = {
    .cmd = 1,
    .value = 100,
};

xQueueSend(s_msg_queue, &msg, pdMS_TO_TICKS(10));

app_msg_t rx_msg;
if (xQueueReceive(s_msg_queue, &rx_msg, portMAX_DELAY) == pdPASS) {
    handle_msg(&rx_msg);
}

队列发送和接收都有超时时间。使用 portMAX_DELAY 表示一直等待，但要确认配置允许无限等待，并且任务确实应该长期阻塞。

3. 中断到任务：FromISR 接口

中断中不能随便调用普通 FreeRTOS API，需要使用带 FromISR 后缀的接口。中断里通常只做最小处理，然后把数据或事件交给任务。 

void uart_rx_isr(void)
{
    BaseType_t high_task_woken = pdFALSE;
    uint8_t data = uart_read_byte();

    xQueueSendFromISR(s_msg_queue, &data, &high_task_woken);
    portYIELD_FROM_ISR(high_task_woken);
}

portYIELD_FROM_ISR() 用于在中断退出时请求任务切换。如果中断唤醒了更高优先级任务，系统可以尽快切过去处理数据。

4. 信号量：事件同步

二值信号量适合表达“某个事件发生了”。例如 DMA 完成、中断接收完成、按键触发等。任务等待信号量，中断或其它任务释放信号量。 

static SemaphoreHandle_t s_dma_done_sem;

s_dma_done_sem = xSemaphoreCreateBinary();

// 任务中等待
xSemaphoreTake(s_dma_done_sem, portMAX_DELAY);

// 中断中释放
xSemaphoreGiveFromISR(s_dma_done_sem, &high_task_woken);

5. 计数信号量

计数信号量适合表示多个同类资源或累计事件。例如缓冲区数量、连接数、多个数据块可用等。 

SemaphoreHandle_t sem = xSemaphoreCreateCounting(10, 0);

// 生产一个资源
xSemaphoreGive(sem);

// 消费一个资源
xSemaphoreTake(sem, pdMS_TO_TICKS(100));

6. 互斥锁：保护共享资源

互斥锁用于保护共享资源，例如 SPI 总线、I2C 总线、文件系统、全局配置结构体、日志输出等。互斥锁和二值信号量很像，但互斥锁带有优先级继承机制，更适合保护资源。 

static SemaphoreHandle_t s_i2c_mutex;

s_i2c_mutex = xSemaphoreCreateMutex();

if (xSemaphoreTake(s_i2c_mutex, pdMS_TO_TICKS(100)) == pdPASS) {
    i2c_transfer();
    xSemaphoreGive(s_i2c_mutex);
}

拿到互斥锁后要尽快释放，不要在持锁期间长时间阻塞，也不要在中断中使用互斥锁。

7. 优先级反转与优先级继承

优先级反转是指高优先级任务等待低优先级任务释放资源，而中优先级任务又抢占低优先级任务，导致高优先级任务迟迟无法运行。互斥锁的优先级继承可以缓解这个问题。

8. 任务通知：轻量事件机制

任务通知是 FreeRTOS 中非常轻量的同步机制。它不需要额外创建队列或信号量，适合一对一事件通知、计数通知、bit 事件标志等场景。 

// 任务中等待通知
ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

// 其它任务中通知
xTaskNotifyGive(s_task_handle);

// 中断中通知
vTaskNotifyGiveFromISR(s_task_handle, &high_task_woken);

如果只是“通知某个任务有事件来了”，任务通知通常比二值信号量更轻量。但如果需要传递结构体数据，还是应该使用队列。

9. 事件组：等待多个条件

事件组（Event Group）用一组位表示多个事件，任务可以等待“任意一个”或“全部”事件发生，适合系统初始化同步和多条件等待：

#define EV_WIFI_UP    (1u << 0)
#define EV_TIME_SYNC  (1u << 1)
#define EV_CFG_LOADED (1u << 2)

static EventGroupHandle_t sys_events;

void app_init(void) { sys_events = xEventGroupCreate(); }

/* 各模块完成后设置自己的位 */
void wifi_on_connected(void) { xEventGroupSetBits(sys_events, EV_WIFI_UP); }

/* 上报任务：等待网络、时间和配置全部就绪 */
static void report_task(void *arg)
{
    EventBits_t bits = xEventGroupWaitBits(sys_events,
                                           EV_WIFI_UP | EV_TIME_SYNC | EV_CFG_LOADED,
                                           pdFALSE,          /* 退出时不清除这些位 */
                                           pdTRUE,           /* 等待全部位 */
                                           pdMS_TO_TICKS(30000));
    if ((bits & (EV_WIFI_UP | EV_TIME_SYNC | EV_CFG_LOADED)) != (EV_WIFI_UP | EV_TIME_SYNC | EV_CFG_LOADED)) {
        log_warn("init timeout, bits=0x%lx", (unsigned long)bits);
    }
    /* ... */
}

注意：

  • 事件组的位不计数，同一事件发生多次只记录一次，不适合传递“发生了几次”。
  • xEventGroupSetBitsFromISR() 实际上把置位操作交给定时器服务任务执行，需要启用软件定时器，并且置位会有一定延迟。
  • 可用的位数取决于 TickType_t 宽度，TickType_t 为 32 位时可用 24 位，为 64 位时可用 56 位。

10. 流缓冲区与消息缓冲区

队列按“项”拷贝数据，对于串口接收这种不定长字节流，逐字节入队效率很低。FreeRTOS 10.0 起提供：

对象数据形式适用
流缓冲区（Stream Buffer）连续字节流，没有边界串口、USB CDC 的原始数据
消息缓冲区（Message Buffer）带长度的不定长消息，按条读取一帧一帧的协议报文
 
static StreamBufferHandle_t uart_rx_sb;

void uart_init_rtos(void)
{
    uart_rx_sb = xStreamBufferCreate(512, 1);       /* 容量 512 字节，有 1 字节就唤醒读取者 */
}

/* 串口 DMA 半满 / 全满 / 空闲中断中：把新收到的数据写入流缓冲区 */
void uart_rx_isr_chunk(const uint8_t *data, size_t len)
{
    BaseType_t woken = pdFALSE;
    size_t n = xStreamBufferSendFromISR(uart_rx_sb, data, len, &woken);
    if (n < len) g_uart_overflow++;                 /* 缓冲区满，记录溢出 */
    portYIELD_FROM_ISR(woken);
}

static void protocol_task(void *arg)
{
    uint8_t buf[64];
    for (;;) {
        size_t n = xStreamBufferReceive(uart_rx_sb, buf, sizeof(buf), pdMS_TO_TICKS(100));
        if (n > 0) parser_feed(buf, n);
        else       parser_timeout();                /* 100ms 没有数据：帧间超时 */
    }
}
流缓冲区和消息缓冲区假定只有一个写入者和一个读取者。多个任务或中断同时写入时，必须在外部加保护（例如写入放在临界区内），否则数据会交错损坏。

流缓冲区本质上是内核提供的环形缓冲区，自己实现无锁环形缓冲的方法见 环形缓冲区。

11. 队列集：同时等待多个队列

一个任务需要同时等待多个队列或信号量时，可以使用队列集（需 configUSE_QUEUE_SETS 1）：

QueueSetHandle_t set = xQueueCreateSet(CMD_Q_LEN + 1);
xQueueAddToSet(cmd_queue, set);
xQueueAddToSet(data_ready_sem, set);

for (;;) {
    QueueSetMemberHandle_t who = xQueueSelectFromSet(set, portMAX_DELAY);
    if (who == cmd_queue) {
        xQueueReceive(cmd_queue, &cmd, 0);          /* 已确认有数据，超时用 0 */
        handle_cmd(&cmd);
    } else if (who == data_ready_sem) {
        xSemaphoreTake(data_ready_sem, 0);
        handle_data();
    }
}

队列集的容量必须等于所有成员容量之和。很多情况下更简单的做法是合并成一个队列，在消息里用类型字段区分来源；只有在无法修改消息源（例如来自第三方库的信号量）时才需要队列集。

12. 递归互斥锁与死锁

普通互斥锁被同一个任务重复获取会造成自己等待自己（死锁）。如果一个加锁的函数会调用另一个也加同一把锁的函数，可以使用递归互斥锁：

SemaphoreHandle_t lock = xSemaphoreCreateRecursiveMutex();

void flash_write_page(...)
{
    xSemaphoreTakeRecursive(lock, portMAX_DELAY);
    /* ... */
    xSemaphoreGiveRecursive(lock);
}

void flash_write_file(...)
{
    xSemaphoreTakeRecursive(lock, portMAX_DELAY);
    flash_write_page(...);                           /* 嵌套获取同一把锁 */
    xSemaphoreGiveRecursive(lock);                   /* 获取几次就要释放几次 */
}

递归锁能解决嵌套调用问题，但也容易掩盖设计上的混乱。更常见的死锁来源是两个任务以相反顺序获取两把锁。预防方法：

  • 所有任务按固定顺序获取多把锁。
  • 获取锁时使用有限超时，超时后记录并释放已持有的锁。
  • 尽量让一个资源只由一个任务访问（资源所有者任务），其他任务通过消息请求服务，从根本上消除锁。

13. 中断延迟处理的标准写法

中断中只做最少的工作，处理交给任务，是 RTOS 系统的基本模式。任务通知是最轻量的实现：

static TaskHandle_t adc_task_handle;

void DMA1_Channel1_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;
    if (dma_transfer_complete()) {
        dma_clear_flag();
        vTaskNotifyGiveFromISR(adc_task_handle, &woken);   /* 通知计数加 1 */
    }
    portYIELD_FROM_ISR(woken);                             /* 必要时中断返回后立即切换 */
}

static void adc_task(void *arg)
{
    for (;;) {
        uint32_t n = ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(50));  /* 取走全部计数 */
        if (n == 0) { log_warn("adc timeout"); continue; }
        if (n > 1)  g_adc_overrun += n - 1;                       /* 处理不及时，丢了数据块 */
        process_adc_block();
    }
}

n > 1 说明任务处理速度跟不上中断，这是很有价值的诊断信息。中断与共享数据的并发问题见 中断与并发。

14. 工作场景：串口协议接收重构

原实现：串口每收到一个字节触发中断，用 xQueueSendFromISR 逐字节入队，协议任务逐字节出队解析。115200 波特率下 CPU 占用明显，高负载时出现丢字节。

  1. DMA + 空闲中断：串口改用 DMA 循环接收，在 DMA 半满、全满和串口空闲中断中把新数据块写入流缓冲区，中断次数从每字节一次降为每帧一到两次。
  2. 流缓冲区：协议任务从流缓冲区批量读取，送入解析器；读超时作为帧间隔判断。
  3. 溢出可见：流缓冲区写入不完整时累计溢出计数，通过调试命令查看。
  4. 发送路径：多个任务都需要发送数据时，不直接调用串口发送，而是把报文放入发送队列，由协议任务统一发送，串口外设只有一个所有者。
  5. 结果：CPU 占用显著下降，长时间压力测试无丢帧。

15. 选择建议

  • 传递数据：队列。
  • 中断唤醒任务：任务通知或二值信号量。
  • 保护共享资源：互斥锁。
  • 多个同类资源计数：计数信号量。
  • 一对多事件位：事件组。
