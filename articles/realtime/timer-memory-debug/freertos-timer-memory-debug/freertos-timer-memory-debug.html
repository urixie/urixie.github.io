FreeRTOS 软件定时器、内存与调试

FreeRTOS 项目真正上线时，最常见的问题往往不是 API 不会用，而是定时器回调阻塞、任务栈不够、堆碎片、优先级配置不合理、FromISR 用错以及系统长时间运行后偶发异常。本文整理软件定时器、内存管理和调试检查方法。

1. 软件定时器是什么

FreeRTOS 软件定时器由内核定时器服务任务统一管理。它不是硬件定时器中断，回调函数运行在定时器服务任务上下文中。 

static void led_timer_cb(TimerHandle_t timer)
{
    (void)timer;
    led_toggle();
}

TimerHandle_t timer = xTimerCreate("led",
                                   pdMS_TO_TICKS(500),
                                   pdTRUE,
                                   NULL,
                                   led_timer_cb);

xTimerStart(timer, 0);

定时器回调必须短小，不能长时间阻塞。否则会影响其它软件定时器回调执行。

2. 一次性定时器与周期定时器

  • 一次性定时器：到期后只执行一次回调。
  • 周期定时器：到期后自动重新计时，周期执行回调。
// pdFALSE：一次性定时器
xTimerCreate("once", pdMS_TO_TICKS(1000), pdFALSE, NULL, cb);

// pdTRUE：周期定时器
xTimerCreate("period", pdMS_TO_TICKS(1000), pdTRUE, NULL, cb);

3. 定时器回调注意事项

  • 不要在定时器回调中做长时间循环。
  • 不要在回调中等待很久的队列、信号量或互斥锁。
  • 复杂工作应通知任务去处理。
  • 多个软件定时器共用定时器服务任务，某个回调卡住会影响其它回调。
static void timer_cb(TimerHandle_t timer)
{
    (void)timer;
    xTaskNotifyGive(s_work_task_handle); // 只通知任务
}

4. FreeRTOS 内存管理

FreeRTOS 可以使用动态内存，也可以使用静态内存。动态创建任务、队列、信号量、定时器时，会从 FreeRTOS 堆中分配内存。静态创建则由用户提供控制块和栈空间。

  • heap_1：只能分配，不能释放。
  • heap_2：可释放，但不合并相邻空闲块。
  • heap_3：封装标准库 malloc/free。
  • heap_4：支持释放和合并空闲块，常用。
  • heap_5：支持多个非连续内存区域。

很多 MCU 项目会选择 heap_4.c，因为它支持空闲块合并，碎片控制相对更好。

5. 静态创建对象

对稳定性要求较高的项目，可以优先使用静态创建，避免运行过程中动态分配失败。 

static StaticTask_t s_task_tcb;
static StackType_t s_task_stack[1024];

xTaskCreateStatic(task_entry,
                  "worker",
                  1024,
                  NULL,
                  2,
                  s_task_stack,
                  &s_task_tcb);

静态创建的好处是内存占用更可控，坏处是灵活性较差。对嵌入式产品来说，确定性通常比灵活性更重要。

6. 栈溢出检测

FreeRTOS 可以配置栈溢出检测。常见配置项包括 configCHECK_FOR_STACK_OVERFLOW 和钩子函数 vApplicationStackOverflowHook()。 

void vApplicationStackOverflowHook(TaskHandle_t task, char *task_name)
{
    (void)task;
    printf("stack overflow: %s\n", task_name);
    taskDISABLE_INTERRUPTS();
    while (1) {
    }
}

栈溢出检测不能替代栈水位分析。建议调试阶段周期性打印关键任务的栈水位，并保留足够余量。

7. 运行统计与调试

FreeRTOS 可通过任务列表、运行时间统计、栈水位、断言和 trace 工具分析系统状态。常见排查方向包括任务是否阻塞、优先级是否合理、CPU 是否被高优先级任务占满、队列是否长期满或空。 

char buf[512];
vTaskList(buf);
printf("%s\n", buf);

vTaskGetRunTimeStats(buf);
printf("%s\n", buf);

这些接口需要在 FreeRTOSConfig.h 中打开对应配置。不同芯片 SDK 对统计接口支持程度不同，需要结合工程配置确认。

8. 常见问题排查表

现象优先排查方向
某个任务不运行优先级被压制、任务一直阻塞、栈溢出
系统偶发死机栈溢出、中断优先级、FromISR API 用错
队列发送失败队列满、接收任务优先级低或未运行
定时器不准Tick 配置、回调耗时、定时器服务任务优先级

9. 定时器服务任务的配置

所有软件定时器回调都在定时器服务任务（Timer Service / Daemon Task）中执行，定时器 API 调用通过命令队列发给它：

#define configUSE_TIMERS              1
#define configTIMER_TASK_PRIORITY     ( configMAX_PRIORITIES - 2 )  /* 通常设为较高优先级 */
#define configTIMER_QUEUE_LENGTH      10
#define configTIMER_TASK_STACK_DEPTH  ( configMINIMAL_STACK_SIZE * 2 )
  • 定时器任务优先级决定回调的及时性：优先级低于忙碌的业务任务时，回调会被推迟。
  • 命令队列满时，xTimerStart() 等调用会失败（或在指定超时内阻塞），中断中大量操作定时器时要加大队列长度。
  • 回调运行在定时器任务的栈上，回调中调用的函数也要计入该任务的栈需求。

10. 把工作推迟到定时器任务：xTimerPendFunctionCall

中断中需要执行一段不适合在中断里完成、又不值得单独建任务的处理时，可以把函数推给定时器任务执行：

static void handle_fault_deferred(void *p1, uint32_t p2)
{
    log_error("fault source=%lu", (unsigned long)p2);    /* 打日志等耗时操作 */
    power_stage_shutdown_sequence();
}

void FAULT_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;
    pwm_force_off();                                      /* 紧急动作仍在中断中立即完成 */
    xTimerPendFunctionCallFromISR(handle_fault_deferred, NULL, read_fault_source(), &woken);
    portYIELD_FROM_ISR(woken);
}

前面提到的 xEventGroupSetBitsFromISR() 内部就是用这一机制实现的。

11. 堆管理方案的选择

方案特点适用
heap_1只分配不释放，最简单、确定启动时创建所有对象，之后不再分配
heap_2可释放，不合并相邻空闲块（已不推荐）老项目兼容
heap_3包装标准库 malloc / free，加调度器保护需要与 C 库共用堆
heap_4可释放，合并相邻空闲块，减少碎片大多数项目的默认选择
heap_5在 heap_4 基础上支持多块不连续内存内部 SRAM + 外部 SDRAM、多个 SRAM 区域
 
/* heap_5：使用前必须先定义内存区域（按地址从低到高排列） */
static uint8_t sram1_heap[32 * 1024];
static uint8_t sram2_heap[16 * 1024] __attribute__((section(".sram2")));

const HeapRegion_t regions[] = {
    { sram1_heap, sizeof(sram1_heap) },
    { sram2_heap, sizeof(sram2_heap) },
    { NULL, 0 }
};

int main(void)
{
    vPortDefineHeapRegions(regions);   /* 在创建任何内核对象之前调用 */
    /* ... */
}

运行时监控堆的健康状况：

size_t free_now = xPortGetFreeHeapSize();
size_t free_min = xPortGetMinimumEverFreeHeapSize();  /* 历史最低值，判断余量最有用 */

历史最低剩余值才是衡量余量的指标。如果程序运行期间反复申请和释放不同大小的内存，即使总剩余量足够，也可能因为碎片而申请失败；关键路径尽量使用静态创建或固定大小的内存池。

12. 断言与钩子函数

开发阶段把所有“出错时会被调用”的钩子都实现出来，让问题在第一现场暴露：

void vApplicationMallocFailedHook(void)            /* configUSE_MALLOC_FAILED_HOOK */
{
    taskDISABLE_INTERRUPTS();
    fault_record("malloc failed", xPortGetFreeHeapSize());
    for (;;);
}

void vApplicationStackOverflowHook(TaskHandle_t task, char *name)   /* configCHECK_FOR_STACK_OVERFLOW */
{
    taskDISABLE_INTERRUPTS();
    fault_record("stack overflow", (uint32_t)name);
    for (;;);
}

void vAssertCalled(const char *file, int line)     /* configASSERT 调用 */
{
    taskDISABLE_INTERRUPTS();
    fault_record(file, line);
    for (;;);
}

fault_record 可以把信息写到复位后不清零的 RAM 区域，配合看门狗复位，下次启动时读出并上报。量产版本中是否保留断言要权衡：保留断言能在现场暴露问题，但需要确保断言触发后系统能通过复位恢复。

13. RTOS 下的 HardFault 分析

RTOS 系统发生 HardFault 时，除了常规的寄存器分析，还要确定是哪个任务出的问题：

  1. 在 HardFault 处理中判断 LR（EXC_RETURN）的第 2 位，确定异常发生时使用的是 PSP（任务）还是 MSP（中断 / 启动阶段）。
  2. 从对应栈中取出压栈的 PC、LR，用 addr2line 定位出错代码。
  3. 读取 pxCurrentTCB 指向的任务控制块中的任务名（或调用 pcTaskGetName(NULL)），记录当前任务。
  4. 检查该任务的栈水位：栈溢出覆盖了相邻内存是 RTOS 中 HardFault 的常见原因。

调试器（如 Ozone、STM32CubeIDE、VS Code + Cortex-Debug）通常支持 RTOS 感知（RTOS-aware）调试，可以直接查看每个任务的调用栈，比只看当前栈有用得多。

14. 可视化跟踪工具

当问题与时序有关（偶发延迟、任务饿死、优先级反转）时，日志往往不够用。可视化跟踪工具会记录任务切换、中断、队列操作等事件，并在时间轴上显示：

工具特点
SEGGER SystemView通过 J-Link RTT 实时采集，开销小，免费用于非商业评估
Percepio Tracealyzer功能全面，支持多种分析视图，商业软件
内核 trace 宏 + GPIO在 traceTASK_SWITCHED_IN() 等宏中翻转 GPIO，用逻辑分析仪观察

即使没有专用工具，用 trace 宏 + GPIO 的方式也能直接看到任务的实际执行时间和切换顺序。

15. 工作场景：运行一段时间后创建对象失败

现象：设备运行若干小时后，某次网络重连时 xTaskCreate 返回失败，重连任务无法启动。

  1. 查看堆状态：xPortGetFreeHeapSize() 显示剩余 6KB，而新任务只需要 2KB 栈，说明问题不是总量不足。
  2. 怀疑碎片：网络模块每次重连都动态创建并删除任务，同时协议层频繁申请大小不一的报文缓冲区，空闲内存被切成许多小块。
  3. 改进：
  4. 网络重连任务改为常驻任务，平时阻塞等待重连请求。
  5. 报文缓冲区改为固定大小的内存池（例如 8 个 256 字节的块）。
  6. 关键对象（主要任务、队列、互斥锁）改为静态创建。
  7. 监控：周期性记录 xPortGetMinimumEverFreeHeapSize()，长时间运行确认稳定。

16. 工程检查清单

  • 任务栈是否做过水位检测。
  • 软件定时器回调是否足够短。
  • 中断中是否只调用 FromISR API。
  • 互斥锁是否只在任务上下文使用。
  • 动态对象是否可能创建失败。
  • 是否开启断言和栈溢出钩子。
  • 队列长度是否根据峰值流量设计。
  • 任务优先级是否按实时性设计。
  • 定时器服务任务的优先级、命令队列长度和栈大小是否按需配置。
  • 堆方案是否选择合适（通常为 heap_4 / heap_5），是否监控历史最低剩余堆空间。
  • 是否实现了内存申请失败、栈溢出和断言钩子，并能在复位后读出故障记录。
  • HardFault 处理是否能区分 PSP / MSP 并记录出错任务。
  • 时序相关问题是否使用 SystemView、Tracealyzer 或 trace 宏 + GPIO 分析。
