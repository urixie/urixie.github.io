RTOS 任务设计方法

从时间特性出发划分任务、分配优先级，用事件驱动和活动对象模式组织任务，并通过 CPU 利用率与响应时间分析验证设计。

1. 从需求到任务划分

刚开始用 RTOS 时最常见的问题是“任务拆得太多”或“一个任务做所有事”。任务划分的依据不是功能模块，而是时间特性：

划分依据说明例子
时延要求不同响应时间要求差别大的工作放在不同任务电机控制（1ms）与界面刷新（50ms）
会阻塞等待需要等待外部事件的工作单独成任务等待网络数据、等待串口帧
周期不同周期差别大的工作分开10ms 采样与 1s 上报
执行时间长长时间计算不能阻塞短时延工作文件系统写入、加密、压缩
独占资源一个外设由一个任务独占访问只有“通信任务”操作 4G 模块

几条经验：

  • 任务数量控制在必要范围：小型 MCU 项目通常 4~10 个任务足够。每个任务都有栈开销和上下文切换开销，也增加了同步的复杂度。
  • 同一时间特性的工作合并：多个 100ms 周期的轻量工作可以放在同一个任务里顺序执行。
  • 中断只做最少的事：读取数据、清除标志、通知任务，处理放在任务中（延迟处理）。中断与任务之间的协作方式见 队列与同步。

2. 优先级怎么分配

FreeRTOS 是基于优先级的抢占式调度，优先级分配直接决定系统能否按时响应。常用原则：

  1. 时延要求越严格，优先级越高：周期越短的任务优先级越高（单调速率调度，Rate Monotonic 的思路）。
  2. 按时延而不是“重要性”分配：日志任务不重要但可以等，故障保护任务时延要求最高；“重要”不等于“优先级高”。
  3. 执行时间长的任务放低优先级：例如文件写入、OTA 下载、界面渲染。
  4. 高优先级任务必须会阻塞：如果高优先级任务一直不阻塞（轮询），低优先级任务永远得不到执行。

一个典型的优先级表：

任务周期 / 触发最坏执行时间优先级
保护任务故障中断通知50us6（最高）
控制任务1ms 周期200us5
采集任务10ms 周期1ms4
通信任务串口帧到达2ms3
业务 / 状态机任务事件驱动不定2
日志 / 存储任务队列非空10ms（写 Flash）1
Idle——0

3. 任务内部结构：事件驱动优于轮询

任务的主循环应当“等待事件 → 处理 → 再等待”，而不是不停轮询标志位：

/* 不推荐：轮询 + 固定延时，响应慢且浪费 CPU */
for (;;) {
    if (g_rx_flag) { g_rx_flag = 0; handle_rx(); }
    if (g_key_flag) { g_key_flag = 0; handle_key(); }
    vTaskDelay(pdMS_TO_TICKS(10));
}

/* 推荐：阻塞等待消息，有事件立即处理，没有事件时不占 CPU */
typedef enum { EV_RX_FRAME, EV_KEY, EV_TIMEOUT, EV_CMD } event_type_t;
typedef struct {
    event_type_t type;
    uint16_t     len;
    uint8_t      data[32];
} app_event_t;

static void app_task(void *arg)
{
    app_event_t ev;
    for (;;) {
        if (xQueueReceive(app_queue, &ev, portMAX_DELAY) == pdTRUE) {
            app_fsm_dispatch(&ev);          /* 交给状态机处理 */
        }
    }
}

这就是“活动对象”（Active Object）模式：每个任务拥有一个消息队列和一个状态机，其他任务和中断只能通过发消息与它交互，不直接访问它的内部数据。好处是共享数据大幅减少，几乎不需要互斥锁；状态机的写法见 状态机设计。

4. 消息设计

  • 消息结构定长且尽量小：队列按值拷贝，消息太大会占用大量 RAM 和拷贝时间。大数据（如一帧 512 字节的报文）放在内存池或环形缓冲中，消息里只传指针和长度，同时明确由谁负责释放。
  • 队列深度按突发量计算：考虑最坏情况下消费者被高优先级任务阻塞的时间内，生产者最多会产生多少条消息。
  • 发送失败要处理：中断中发送队列满时不能阻塞，应计数丢弃次数并在调试接口中可见。
  • 请求-响应：需要返回结果时，在消息中携带回复用的任务句柄（配合任务通知）或回调，避免调用方忙等。

5. 时间分析：系统是否来得及

上线前至少做一次粗略的 CPU 负载与最坏响应时间分析：

CPU 利用率 = Σ (任务最坏执行时间 / 任务周期)

控制任务  200us / 1ms   = 20%
采集任务    1ms / 10ms  = 10%
通信任务    2ms / 20ms  = 10%   （按最短帧间隔估算）
日志任务   10ms / 100ms = 10%
合计                     = 50%   → 留有余量

利用率只是必要条件，还要检查：

  • 高优先级任务对低优先级任务的阻塞：低优先级任务的最坏响应时间 = 自身执行时间 + 所有高优先级任务在此期间的执行时间。
  • 临界区与关中断时间：最长关中断时间直接叠加到中断响应延迟上。
  • 共享资源的阻塞：低优先级任务持有互斥锁时，高优先级任务需要等待，要限制持锁时间。

实测比估算更可靠：用 GPIO 在任务开始和结束时翻转电平，用逻辑分析仪测量真实执行时间和抖动；或使用 FreeRTOS 的运行时间统计功能，方法见 定时器、内存与调试。

6. 工作场景：一个数据采集终端的任务架构

需求：4 路 ADC 每 10ms 采样一次，RS485 Modbus 从机响应主站查询，每分钟把统计数据写入 Flash，按键与 LED 指示，看门狗保护。

任务触发方式优先级说明
采集任务vTaskDelayUntil 10ms4启动 ADC + DMA，等待 DMA 完成通知后滤波
Modbus 任务串口空闲中断通知3解析帧、读写寄存器表、回复
业务任务消息队列2状态机：正常 / 报警 / 配置模式
存储任务消息队列1写 Flash 耗时长，放在最低优先级
监控任务1s 周期2检查各任务心跳后喂硬件看门狗

设计要点：

  • 采集结果通过“最新值 + 互斥锁”或双缓冲共享给 Modbus 任务，Modbus 任务只读不写。
  • 寄存器表的写操作（主站修改配置）通过消息交给业务任务处理，保证配置只在一个地方被修改。
  • 存储任务写 Flash 期间如果会暂停取指（同一 Bank 擦写），要评估对采集任务的影响，必要时把关键代码放在 RAM 中执行。
  • 每个任务在主循环中更新自己的心跳计数，监控任务确认所有心跳都在增长才喂狗，任何一个任务卡死都会触发复位。

7. 任务设计检查清单

  • 任务是否按时间特性（时延、周期、阻塞、执行时长）划分，数量是否控制在必要范围。
  • 优先级是否按时延要求分配，高优先级任务是否都会阻塞。
  • 任务主循环是否事件驱动，而不是轮询 + 固定延时。
  • 任务之间是否通过消息交互，共享数据是否最小化并有明确的所有者。
  • 消息结构是否小而定长，大数据是否通过指针传递并明确释放责任。
  • 队列深度是否按最坏突发量计算，发送失败是否计数。
  • 是否估算过 CPU 利用率，是否实测过关键任务的执行时间与响应时间。
  • 是否有多任务心跳监控，任何任务卡死都能被发现。
