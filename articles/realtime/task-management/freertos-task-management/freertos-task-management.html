FreeRTOS 任务管理与栈空间

FreeRTOS 的任务可以理解为嵌入式系统中的轻量线程。每个任务都有自己的任务函数、栈空间、优先级和任务控制块。任务设计是否合理，会直接影响系统实时性、稳定性和可维护性。

1. 任务创建

常用 xTaskCreate() 创建动态任务，也可以用 xTaskCreateStatic() 创建静态任务。动态任务由 FreeRTOS 堆分配任务控制块和栈，静态任务由用户提供内存，更适合对内存确定性要求高的项目。 

static void led_task(void *arg)
{
    (void)arg;

    while (1) {
        led_toggle();
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

xTaskCreate(led_task, "led", 1024, NULL, 1, NULL);

任务函数通常是一个不会返回的无限循环。如果任务确实要结束，应调用 vTaskDelete(NULL) 删除自己。

2. 任务句柄

任务句柄用于操作指定任务，例如删除、挂起、恢复、通知等。创建任务时可以保存句柄。 

static TaskHandle_t s_uart_task_handle;

xTaskCreate(uart_task,
            "uart",
            2048,
            NULL,
            3,
            &s_uart_task_handle);

如果后续不需要主动控制任务，可以把最后一个参数传 NULL。如果需要从中断或其它任务通知该任务，建议保存句柄。

3. 任务优先级设计

优先级应该按实时性和阻塞行为设计，而不是按“功能重要性”随意设置。高优先级任务应该尽快完成处理并进入阻塞态。

  • 硬实时响应任务：优先级较高，但必须短小。
  • 通信接收任务：通常高于普通业务任务。
  • 显示刷新任务：优先级不宜过高，避免影响采样和通信。
  • 日志、存储、统计任务：一般优先级较低。
高优先级任务如果写成无阻塞死循环，会饿死低优先级任务。这类问题表现为系统某些功能不运行，但并不一定死机。

4. 任务延时：vTaskDelay 与 vTaskDelayUntil

vTaskDelay() 是相对延时，从当前调用时刻开始等待指定 Tick。vTaskDelayUntil() 是周期性延时，适合固定周期任务。 

void sample_task(void *arg)
{
    TickType_t last_wake = xTaskGetTickCount();

    while (1) {
        adc_sample_once();
        vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(10));
    }
}

周期采样、周期控制、定时通信更适合用 vTaskDelayUntil()，它比简单 vTaskDelay() 更容易维持稳定周期。

5. 任务栈空间

每个 FreeRTOS 任务都有独立栈。任务栈用于保存局部变量、函数调用上下文、中断嵌套时的部分上下文等。栈太小会导致栈溢出，栈太大又会浪费 RAM。

6. 栈水位检测

FreeRTOS 提供栈水位检测接口，可以查看任务历史运行过程中剩余栈空间的最小值。调试阶段建议重点关注通信、显示、文件系统、协议解析等任务。 

UBaseType_t watermark = uxTaskGetStackHighWaterMark(NULL);
printf("stack watermark = %u\n", (unsigned)watermark);

如果水位值很小，说明任务栈接近耗尽，需要增大栈或减少局部变量占用。尤其不要在任务函数里定义几 KB 的局部数组。

7. 任务的删除与生命周期

嵌入式系统中大多数任务创建后永远不退出。确实需要结束任务时，注意：

static void ota_task(void *arg)
{
    do_ota_download();
    /* 任务函数不能直接 return，必须删除自己 */
    vTaskDelete(NULL);
}
  • 任务函数不能直接返回，否则会进入移植层的错误处理（prvTaskExitError），结束时必须调用 vTaskDelete(NULL)。
  • 动态创建的任务删除自己时，其 TCB 和栈由空闲任务负责释放。如果空闲任务长期得不到 CPU（高优先级任务一直忙），内存不会被回收。
  • 删除任务不会自动释放它申请的其他资源：持有的互斥锁、动态分配的缓冲区、打开的外设都需要在删除前自行清理。
  • 频繁创建 / 删除任务会造成堆碎片，更推荐让任务常驻，在没有工作时阻塞等待。

8. 挂起与恢复的陷阱

vTaskSuspend() / vTaskResume() 看起来方便，但容易引入问题：

  • 挂起持有资源的任务：被挂起的任务如果正持有互斥锁，等待该锁的任务会永久阻塞。
  • 不能用于同步：xTaskResumeFromISR() 如果在任务调用 vTaskSuspend(NULL) 之前执行，这次恢复就丢失了，任务会一直挂起。中断唤醒任务应该使用任务通知或信号量，它们会“记住”事件。
  • 挂起不计数，多次挂起只需一次恢复。

适合使用挂起的场景很少，例如调试时临时停止某个任务，或在进入低功耗前暂停非关键任务。

9. 栈大小如何估算

栈太小会溢出导致随机崩溃，太大浪费 RAM。推荐“估算 → 实测 → 留余量”的方法：

  1. 初始估算：函数调用深度 × 每层局部变量 + 中断嵌套不使用任务栈（Cortex-M 中断使用 MSP）+ 上下文保存约 16~32 个字（使用 FPU 时更多）。
  2. 注意大户：printf / snprintf 一类格式化函数可能使用数百字节栈；局部大数组（如 char buf[512]）直接占用栈；递归调用要避免。
  3. 实测水位：在所有功能（包括异常路径、最长的协议帧、错误处理）都运行过之后，读取 uxTaskGetStackHighWaterMark()。
  4. 留余量：最终大小 = 实测最大使用量 × 1.2 ~ 1.5。
/* 调试命令：打印所有任务的状态与栈水位（需 configUSE_TRACE_FACILITY 与 configUSE_STATS_FORMATTING_FUNCTIONS） */
static char buf[512];
vTaskList(buf);
printf("Name          State  Prio  Stack  Num\r\n%s", buf);

vTaskList 输出的 Stack 列就是剩余栈的最小值（单位为字）。它会短时间挂起调度器，只在调试时使用。

10. 多任务健康监控

单纯在某个任务中喂硬件看门狗，只能发现“这个任务卡死”，其他任务卡死时看门狗仍然被正常喂。更可靠的做法是让监控任务汇总所有任务的心跳：

#define TASK_COUNT 4
static volatile uint32_t g_heartbeat[TASK_COUNT];

void task_heartbeat(int id) { g_heartbeat[id]++; }   /* 各任务在主循环中调用 */

static void monitor_task(void *arg)
{
    uint32_t last[TASK_COUNT] = {0};
    for (;;) {
        vTaskDelay(pdMS_TO_TICKS(1000));
        bool all_alive = true;
        for (int i = 0; i < TASK_COUNT; i++) {
            if (g_heartbeat[i] == last[i]) {
                all_alive = false;
                log_error("task %d stalled", i);
            }
            last[i] = g_heartbeat[i];
        }
        if (all_alive) {
            iwdg_refresh();              /* 只有全部任务都活着才喂狗 */
        }
    }
}

对于长时间阻塞等待事件的任务（如等待外部命令），在阻塞等待上设置超时（例如 500ms），超时也更新心跳，避免被误判为卡死。

11. 工作场景：一个任务偶尔卡死

现象：设备运行数天后偶发看门狗复位，复位前日志显示通信任务不再更新心跳。

  1. 保留现场：在看门狗复位前（或使用窗口看门狗的早期唤醒中断）记录各任务状态、当前任务名和栈水位到保留 RAM，复位后读出。
  2. 分析状态：记录显示通信任务处于 Blocked 状态，正在等待一个互斥锁。
  3. 查找持锁者：通过 xSemaphoreGetMutexHolder() 得知持有者是存储任务，而存储任务卡在等待 Flash 操作完成的循环中（Flash 异常时没有超时）。
  4. 修复：Flash 等待循环加入超时与错误处理；互斥锁获取使用有限超时，超时后记录错误；缩小锁的保护范围，不在持锁期间执行耗时的 Flash 操作。
  5. 预防：所有阻塞等待都设置合理超时，不在业务代码中使用 portMAX_DELAY 等待可能永远不会到来的资源。

12. 任务设计检查清单

  • 任务职责是否单一。
  • 任务是否有明确阻塞点。
  • 优先级是否按实时性设计。
  • 任务栈是否经过水位检测。
  • 是否避免局部大数组。
  • 任务删除前是否释放相关资源。
  • 周期任务是否使用 vTaskDelayUntil()。
  • 需要结束的任务是否调用 vTaskDelete(NULL)，删除前是否释放了它持有的资源。
  • 是否避免用 vTaskSuspend / vTaskResume 做任务同步。
  • 栈大小是否经过估算、全功能运行后实测水位，并保留 20%~50% 余量。
  • 是否有汇总所有任务心跳的监控机制，只有全部任务正常才喂看门狗。
  • 等待资源时是否设置了超时，而不是无限等待。
