Linux 基础命令与文件系统

本文整理 Linux 入门和嵌入式 Linux 调试中最常用的基础命令与文件系统知识。重点不是背命令，而是理解 Linux 中“一切皆文件”的思想：普通文件.目录.设备节点.进程信息.内核参数，都可以通过统一的文件接口进行查看和操作。

嵌入式 Linux 调试时，很多问题不是代码本身，而是路径.权限.设备节点.挂载点.脚本执行环境和文件系统状态出错。先熟悉基础命令和目录结构，后面看驱动.进程和系统服务会轻松很多。

0.开始之前：先学会安全地输入命令

命令行的基本形式可以理解为 命令 [选项] [参数]。命令决定“做什么”，选项决定“怎样做”，参数则是要处理的文件.目录或关键字。例如 ls -lah /etc 中，ls 是查看目录，-lah 是详细.包含隐藏文件.以易读单位显示，/etc 是目标目录。

教程里的 $ 通常表示普通用户提示符，# 通常表示 root 提示符；它们不是命令内容。先在自己的家目录或 /tmp 做实验，不要一开始就在 /./etc 或设备目录中尝试删除.移动.改权限等操作。 

# 先确认自己在哪个目录.以哪个用户身份工作
pwd
whoami

# 不确定命令参数时，优先查看本机帮助
ls --help
man ls
command -v ls

pwd 会打印当前工作目录；whoami 显示当前用户；command -v ls 用来确认实际执行的是哪个 ls。许多嵌入式设备的命令来自 BusyBox，可能没有 man，也不支持桌面发行版里的全部选项；这时先执行 命令 --help，不要凭记忆直接套用网络命令。

不理解命令含义时，不要为了“试一下”在命令前加 sudo，也不要复制带有通配符.重定向或递归删除的命令。尤其是 rm -rf.chmod -R.chown -R.rsync --delete，目标路径写错会造成大范围且难以恢复的损失。

1.Linux 目录结构

Linux 没有 Windows 那种 C 盘.D 盘概念，所有内容都挂在根目录 / 下面。不同目录有不同职责。

  • /bin./sbin：基础命令。
  • /etc：配置文件。
  • /dev：设备节点，例如串口.磁盘.GPIO 相关设备。
  • /proc：进程和内核运行时信息。
  • /sys：设备模型.驱动.总线.类等信息。
  • /mnt./media：挂载外部存储或临时文件系统。

目录结构不是所有发行版都完全相同，例如现代发行版可能把 /bin 链接到 /usr/bin，嵌入式系统也可能没有 /home。因此排查时不要只靠“通常应该在这里”，而是先从根目录实际查看，再由服务配置.启动脚本或命令输出确认真实路径。

先读懂路径，再读懂 ls

pwd                    # 当前工作目录，例如 /home/xyj/work
ls /                   # 列出根目录内容
ls -ld /etc /dev /tmp  # -d 查看目录对象本身，而非列出目录内部
ls -lah /etc           # -l 详细格式；-a 包含隐藏项；-h 易读大小

cd /etc                # 绝对路径：从根目录开始
cd ../var              # 相对路径：相对于当前目录
cd -                   # 回到上一次工作目录
cd ~                   # 回到当前用户家目录
ls -ld "name with spaces"  # 路径含空格时用引号包住

ls -l 的一行通常包含权限.硬链接数.所有者.所属组.大小.修改时间和名称。例如 -rwxr-xr-x 1 root root 12345 app 中，最前面的 - 表示普通文件，后面的三组 rwx 是权限；权限部分会在后文详细解释。每次切换目录后先执行 pwd，可以避免“命令正确但操作错目录”的常见失误。

2.常用查看命令

日常定位问题时，先看文件.路径.权限和内容是否正确。 

cat /etc/hostname          # 输出短文件的全部内容
less /var/log/messages     # 分页查看；按 / 搜索，q 退出
head -n 20 app.log         # 只看前 20 行，常用于确认文件格式
tail -n 50 app.log         # 看最后 50 行，常用于看最近错误
tail -F app.log             # 跟踪日志；文件被轮转重建后会重新打开
wc -l app.log               # 统计行数，判断日志量级
file firmware.bin           # 判断文件类型，不要只相信扩展名
stat app.log                # 查看大小.时间戳.inode 等详细元数据
du -sh *                    # 当前目录每个项目实际占用的总大小
df -hT                      # 各挂载分区的可用空间和文件系统类型

cat 适合短小文本；日志.配置备份或伪文件系统内容很大时，直接 cat 会刷屏，反而看不到关键信息。less 适合交互式阅读，head 和 tail 分别用于查看开头和末尾，file 则能防止把二进制.压缩包误当作普通文本阅读。

tail -f 会持续跟踪同一个已打开的文件；日志轮转时，旧文件可能被改名并新建一个同名文件，tail -F 更适合长期观察这类日志。若系统没有 less 或 tail -F，先看 --help 确认 BusyBox 支持的替代选项。

看日志时，先问三个问题

  • 日志是否真的在增长？先用 stat app.log 或 ls -l app.log 对比大小和修改时间。
  • 错误发生在什么时候？用 tail -n 100 app.log 查看错误前后的上下文，而不是只搜到一行 error 就结束。
  • 程序写的是不是这个文件？配置中的路径可能是相对路径，先用 pwd 和启动脚本确认实际工作目录。

3.创建.复制.移动与删除：先确认目标，再执行修改

文件操作本身并不复杂，真正容易出错的是目标路径和 shell 的展开规则。先写出目标目录.再用 ls 确认，最后再执行修改命令，比事后恢复简单得多。下面的练习全部放在自己的家目录中，不会碰系统文件。 

cd ~
mkdir -p linux-lab/logs
cd linux-lab

printf '%s\n' 'first line' > notes.txt
# > 会新建或清空后写入

printf '%s\n' 'second line' >> notes.txt
# >> 在文件末尾追加

cp notes.txt logs/notes.bak       # 复制；目标是新文件名
mv notes.txt notes-renamed.txt    # 移动或改名，取决于目标位置
cp -a logs logs-copy              # -a 尽量保留属性并递归复制目录
rm -i notes-renamed.txt           # -i 删除前询问，适合手工操作

> 和 >> 是 shell 重定向，不是 printf 的参数。前者会覆盖目标文件，后者会追加；因此写配置前应先备份。错误输出也能单独保存：./app >app.out 2>app.err 表示标准输出写入 app.out，错误输出写入 app.err；2>&1 表示把错误输出合并到标准输出当前指向的位置。

* 是通配符，会在命令执行前被 shell 展开为当前目录中的多个文件。例如 cp *.log logs/ 会复制所有以 .log 结尾的文件。执行带通配符的删除或移动前，可先用 printf '%s\n' *.log 查看它实际会匹配哪些名称。不要把未验证的 * 与递归删除一起使用。

rm 删除的是目录项，不会进入回收站。特别是 rm -r 会递归删除目录，-f 会取消多数确认提示。新手排查空间问题时，应先用 du 找到大文件，而不是直接在系统目录中执行删除命令。

4.搜索与过滤：从“找到文件”到“找到那一行”

Linux 调试经常需要在大量日志和源码中查找关键字。常用组合是 grep.find.xargs。

grep：在文本.日志和源码中找关键字

grep -n "error" app.log
# -n 显示行号，便于回到原文确认上下文

grep -in "timeout" app.log
# -i 忽略大小写；适合匹配 ERROR.Error.error

grep -r --include="*.c" -n "spi_init" src/
# -r 递归目录；--include 只搜索 .c 文件，避免扫描无关二进制文件

grep -E "error|failed|timeout" app.log
# -E 使用扩展正则，竖线表示“或”

grep -v '^#' config.ini | grep -v '^$'
# -v 反选：去掉注释行和空行后再观察有效配置

搜索词里有空格.星号.方括号等特殊字符时优先用单引号，例如 grep -n 'device not found' app.log。grep 找到的是匹配行，不一定就是根因；应使用 grep -n -C 3 'error' app.log 查看命中行前后各 3 行，结合时间和调用顺序判断。

find：按名称.类型.时间和大小找文件

find . -type f -name "*.c"
# . 是起点；-type f 只要普通文件；-name 按文件名匹配

find /var/log -type f -mtime -1
# 最近 24 小时内修改过的普通文件

find . -type f -size +100M
# 大于 100 MiB 的文件，排查磁盘占用时很有用

find . -type f -name "*.log" -print0 | xargs -0 grep -n "error"
# -print0 与 xargs -0 用 NUL 分隔，能正确处理文件名中的空格或换行

不要在根目录上不加条件地执行 find /，它可能很慢.产生大量权限错误，并给存储较慢的嵌入式设备增加负担。优先从明确目录开始，例如 /var/log.应用部署目录或工程目录；必要时把权限错误单独重定向为 2>/dev/null，但不要用它掩盖本该处理的访问问题。

进程搜索也有更可靠的写法

ps aux | grep '[a]pp'
# 方括号避免 grep 自己也出现在结果里

pgrep -af app
# -a 显示完整命令行；比 ps | grep 更直接（若系统提供）

在嵌入式板子上，如果没有完整 GNU 工具，BusyBox 版本命令可能参数较少，需要根据实际系统裁剪情况调整写法。

5.权限与用户：先读懂 ls -l，再修改权限

Linux 文件权限分为所有者.所属组和其它用户三类，每类有读.写.执行权限。很多“命令不能执行”“设备打不开”的问题，本质是权限不对。 

$ ls -l run.sh
-rw-r--r-- 1 xyj developers 120 Jul 10 09:30 run.sh

# 第 1 个字符：- 普通文件，d 目录，l 软链接
# 接下来的 9 个字符：rw- | r-- | r--
# 分别对应：所有者 | 所属组 | 其他用户

chmod u+x run.sh       # 只给文件所有者增加执行权限
chmod 755 app          # 所有者 rwx；组 r-x；其他用户 r-x
chmod 644 config.ini   # 所有者可读写；其他用户只读
ls -l /dev/ttyS0       # 查看串口设备节点的属主.组和权限

数字权限是 r=4.w=2.x=1 的相加：7 等于 rwx，6 等于 rw-，5 等于 r-x。但目录的 x 不是“执行目录”，而是允许进入和访问目录项；目录没有 x 时，即使能读到文件名，也可能无法打开其中的文件。

chown 用户:组 文件 用于改变属主和所属组，通常需要管理员权限。例如部署程序时，应该按服务实际运行用户设置最小权限，而不是图省事使用 chmod 777。后者会让所有用户都可写，既不安全，也会掩盖真正的用户组配置问题。

shell 脚本的“不能执行”还有一个常见原因：文件是 Windows 换行符 CRLF，内核会把解释器路径读成 /bin/sh\r。可先运行 file run.sh 检查；确认问题后再使用项目规定的换行转换工具。不要仅凭报错就反复 chmod。

对脚本来说，只有读权限不够，还需要执行权限；对设备节点来说，应用程序还需要具备访问该设备节点的权限。

6.软链接与硬链接：程序版本和库文件为什么常有箭头

软链接类似快捷方式，保存的是目标路径；硬链接是多个文件名指向同一个 inode。嵌入式系统里常用软链接管理版本.库文件和启动脚本。 

ln -s app_v1.2.0 app_current
ls -l app_current
# 可能显示：app_current -> app_v1.2.0

readlink app_current       # 查看软链接保存的原始目标
readlink -f app_current    # 解析为最终绝对路径；可发现断链
ls -li app_v1.2.0          # 查看 inode；比较硬链接时有用

软链接可以跨文件系统，也可以指向目录；代价是目标文件移动或删除后会变成“断链”。排查动态库.启动脚本或版本切换问题时，先用 ls -l 看箭头指向哪里，再用 readlink -f 验证最终路径是否存在。不要把软链接当成文件副本：删除链接通常不会删除目标，但删除目标会让链接失效。

7.磁盘.挂载与空间：文件在不在，不等于分区没问题

df 看的是“文件系统或分区”还剩多少空间，du 看的是“目录或文件”占了多少空间。两个命令回答的问题不同：某个分区满了时先用 df 定位分区，再用 du 在该挂载点内找大目录。 

df -hT
# -h 以易读单位显示；-T 显示文件系统类型

du -xhd 1 /var
# -x 不跨越到其他挂载点；-h 易读单位；-d 1 只展开一层

lsblk -f
# 查看块设备.分区.文件系统和挂载点（若系统提供）

findmnt
# 以树状方式显示当前挂载关系（若系统提供）

cat /proc/mounts
# BusyBox 环境中也常可用；显示内核看到的挂载信息

常见场景是：df -h 显示 /var 所在分区已满，而应用报“写日志失败”。此时不要只看当前目录；应从 df -hT 找到挂载点，再执行 du -xhd 1 挂载点，逐层缩小范围。du 与 df 数字差异很大时，可能存在“文件已删除但仍被进程打开”的情况，需要再结合 lsof（若可用）或重启相关服务排查。

发现文件系统为只读 ro 挂载时，不要立即反复执行 remount 为读写。只读可能是文件系统错误后的保护结果；应先保存日志.检查内核信息和存储介质状态，再按产品维护流程处理。

8.压缩.传输与同步：把“文件发过去”做成可验证的动作

tar 负责把多个文件打成一个归档，也可以同时 gzip 压缩；scp 适合一次性复制；rsync 适合反复同步构建产物。无论使用哪种方式，传输后都要在目标端验证文件名.权限和版本，而不是只看到命令没有报错就认为部署成功。

tar：把选项拆开理解

tar -czf project.tar.gz project/
# c=create 创建归档；z=gzip 压缩；f=后面紧跟归档文件名

tar -tzf project.tar.gz
# t=list 只列出归档内容；解压前先检查里面有什么

tar -xzf project.tar.gz -C /tmp/restore-test
# x=extract 解压；-C 指定目标目录，避免解到当前未知位置

记忆 tar 时，关键不是死背字母顺序，而是知道 f 后面必须跟归档文件名。解压来自他人的压缩包前，先用 tar -tzf 列表检查内容；生产系统中应选择明确的空目录作为解压目标。

scp 与 rsync：部署前后都要确认

scp ./build/app root@192.168.1.10:/opt/demo/
# 本地文件在前，远端写成 用户@主机:路径

ssh root@192.168.1.10 'ls -l /opt/demo/app'
# 在远端确认文件是否到达.权限是否正确

rsync -avz ./build/ root@192.168.1.10:/opt/demo/
# -a 保留常用属性并递归；-v 显示过程；-z 传输时压缩

rsync -avzn ./build/ root@192.168.1.10:/opt/demo/
# -n 是 dry-run，只显示将要发生的变化，首次同步建议先使用

rsync ./build/ 远端:/opt/demo/ 末尾的 / 表示同步 build 目录内部内容；去掉它则可能把整个 build 目录放到目标目录下。--delete 会删除目标端多出来的文件，只应在确认目标目录专属于本次部署.且 dry-run 结果正确后使用。

9./dev./proc 与 /sys：从用户态观察设备和内核

/proc 和 /sys 是理解 Linux 运行状态的窗口。它们看起来像文件系统，但很多内容并不是真实磁盘文件，而是内核导出的运行时信息。 

# /dev：设备节点是否出现.谁可以访问
ls -l /dev/ttyS0
ls -l /dev/video0

# /proc：系统运行状态
cat /proc/cmdline        # 内核启动参数
cat /proc/meminfo        # 内存统计
cat /proc/interrupts     # 中断计数；可多次对比某设备计数是否增长
cat /proc/mounts         # 当前挂载信息

# /sys：设备模型.总线和驱动导出的属性
ls /sys/class
ls /sys/bus/platform/devices
find /sys/class -maxdepth 2 -type l | head -n 20

dmesg -T | tail -n 80    # 最近内核日志；部分系统不支持 -T

例如串口程序打不开 /dev/ttyS0 时，先执行 ls -l /dev/ttyS0：如果节点不存在，应回到内核日志.设备树或驱动注册流程；如果节点存在但权限不足，应检查应用实际用户和所属组；如果能打开但没有数据，再检查波特率.线路和驱动日志。不要通过手工 mknod 伪造节点来绕过前两类问题。

有些驱动会在 /sys 暴露可写属性。正确流程是先 cat 读取当前值，确认该属性的内核文档和单位，再在测试环境中写入。注意 sudo echo 1 > 文件 的重定向仍由当前 shell 执行，可能没有写权限；若确实需要管理员写入，应使用经过确认的 printf '1\n' | sudo tee 文件，并避免把它用于未知属性。

10.把命令串成排查流程：三个新手常见场景

场景 1：程序“不能执行”

pwd
ls -l ./app
file ./app
./app
echo $?
# 0 通常表示成功；非 0 表示失败，需结合上一步输出判断

ldd ./app
# 检查动态库依赖；静态链接程序.精简系统或目标架构不匹配时结果不同

按顺序确认：路径是否正确.文件是否存在.是否具有执行权限.可执行文件架构是否与设备匹配.动态库是否齐全。若报 Permission denied，还要检查所在文件系统是否以 noexec 方式挂载；若报 not found 但文件明明存在，可能是动态加载器或依赖库缺失，不能只盯着文件名。

场景 2：日志没有写入或磁盘突然满了

df -hT
stat /var/log/myapp/app.log
tail -n 100 /var/log/myapp/app.log
du -xhd 1 /var/log
find /var/log -type f -size +50M -ls

先用 df 判断是不是空间或只读挂载问题，再用 stat 确认目标日志是否真的更新，最后用 du 和 find 找占用来源。不要把“日志没变化”直接等同于“程序没运行”：它也可能写到了另一个工作目录.被日志级别过滤，或没有权限创建目录。

场景 3：设备节点没有出现

dmesg | tail -n 100
ls -l /dev | grep -i tty
cat /proc/interrupts
ls /sys/class
ls /sys/bus/platform/devices

先看内核是否识别或报错，再看对应设备节点.sysfs 条目和中断计数。把“硬件是否枚举”“驱动是否绑定”“设备节点是否创建”“应用是否有权限”分成四步检查，比直接修改应用代码更有效。

十1.工程检查清单与练习顺序

  • 开始命令前：确认当前用户.当前目录和目标路径；含空格的路径加引号。
  • 看文件前：先判断它是普通文本.二进制.软链接还是设备节点，再选择 cat.less.file 或 ls -l。
  • 修改前：用 ls.printf 或 rsync -n 预览通配符和同步结果；对配置先备份。
  • 权限问题：同时核对文件权限.属主.所属组.运行用户和挂载选项，不要用 777 掩盖问题。
  • 设备问题：按“内核日志 → /sys → /dev → 权限 → 应用参数”顺序排查。
  • 空间问题：先 df 找分区，再 du 找目录，最后才决定如何清理。
  • 嵌入式目标：把命令当作“可能被裁剪的工具”，每次先确认 BusyBox 或发行版实际支持的参数。

建议按本文顺序在 ~/linux-lab 中完成目录.文件.重定向.grep.find.权限和 tar 的小练习。命令真正变成能力，不是记住几十条缩写，而是每次都能回答：我正在操作哪个路径？这条命令会修改什么？执行后应如何验证结果？
