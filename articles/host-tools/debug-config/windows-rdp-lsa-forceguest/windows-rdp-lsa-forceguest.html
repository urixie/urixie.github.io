Windows 远程桌面 LSA 认证失败：ForceGuest 排查与修复案例

真实 Windows RDP 故障复盘：3389 可达、密码有效但出现 LSA 身份验证错误，结合事件日志、SMB 1272 和 ForceGuest 策略逐层定位并验证修复。

案例结果：目标电脑原本可以建立 TCP 3389 连接，Windows 凭据在目标机器上也有效，但 RDP 始终报“无法连接到本地安全机构”。进一步发现 forceguest=1 和 SMB 网络认证错误 1272；将 forceguest 改为 0 后，实际进入远程桌面，并获得服务器端 1149 认证成功事件。

本文根据一次实际调试记录整理。为适合公开网站，主机名统一写作 TARGET-PC，IP 使用文档专用示例地址 192.0.2.219、192.0.2.157（不是原始现场地址）。所有命令中的示例名称或地址都需替换为实际值；不公开密码。

1. 故障现象与结论

在 Windows 自带的远程桌面连接 mstsc.exe 中连接目标主机，输入本地管理员账号后，客户端提示：

出现身份验证错误。
无法连接到本地安全机构

这可能是由于密码已过期。
如果密码已过期，请更新密码。

其中“可能密码已过期”只是 Windows 给出的候选解释，本案例没有证据支持密码实际过期，也没有重置密码。初始验证已经显示 RDP 服务和监听端口正常，因此应继续区分网络、凭据、协商、策略和会话各阶段。

结论边界：ForceGuest 管理的是本地账户进行网络登录时的身份映射，不能简单宣称它直接控制所有 RDP 交互式登录。此例证实了修改配置与网络管理认证及 RDP 恢复之间的时间顺序，但没有通过 CredSSP/NTLM 完整抓包证明内部每一步的因果机制。它不是所有 LSA 错误的通用修复。

4. 分层排查方法

4.1 先复现，再限定时间查询客户端日志

在客户端重试一次连接，记下精确时间。查看 Microsoft-Windows-TerminalServices-RDPClient/Operational：

$end = Get-Date
Get-WinEvent -FilterHashtable @{
    LogName   = 'Microsoft-Windows-TerminalServices-RDPClient/Operational'
    StartTime = $end.AddMinutes(-30)
    EndTime   = $end
} -MaxEvents 30 -ErrorAction Stop |
    Select-Object TimeCreated, Id, Message | Format-List

现场出现事件 1024（尝试连接）、1028（服务器支持 SSL）、226（TsSslEventHandshakeContinueFailed，0x80004005）和 1026（断开原因 519）。这些是连接失败的客户端迹象，不能单凭代码判定“密码错误”或“证书已过期”。

4.2 正确阅读目标的 4625 失败事件

$end = Get-Date
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4625
    StartTime = $end.AddMinutes(-30)
    EndTime   = $end
} -MaxEvents 10 -ErrorAction Stop |
    Select-Object TimeCreated, Id, Message | Format-List

需要联合核对 发生时间、账号域、登录类型、调用进程、状态码及来源地址。其中 0xC000006D 是登录失败的概括状态，0xC000006A 是密码不匹配子状态。登录类型 2 是交互式登录，3 是网络登录，10 是远程交互式登录。

本例两条失败事件发生于先前的向日葵操作，调用方为 AweSun.exe、类型为 2；不能把它们当成随后 RDP 尝试的密码错误证明。

4.3 在目标电脑核对相同的 Windows 密码

runas /user:TARGET-PC\Administrator "notepad.exe"

在目标电脑执行，按提示手动输入与 RDP 相同的 Windows 账号密码。现场记事本成功打开，因此密码可通过本机身份验证。runas 不验证 RDP 登录权限，也不等于 NLA 或网络认证一定正常；PIN、向日葵密码和 Windows 账户密码也不可混用。

4.4 核对 NLA、TLS 和 NTLM 参数

Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa\MSV1_0' |
    Format-List RestrictReceivingNTLMTraffic, NtlmMinServerSec, NtlmMinClientSec

Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp' |
    Format-List UserAuthentication, SecurityLayer, MinEncryptionLevel

现场读到 UserAuthentication=1（启用 NLA）、SecurityLayer=2（要求 TLS）、MinEncryptionLevel=2；NTLM 最低会话安全的客户端及服务端值均为 536870912（0x20000000）。该数值表示要求 128 位会话安全，不等于“禁用 NTLM”。

独立 TLS 检测成功协商 Tls12，加密套件为 TLS_RSA_WITH_AES_256_GCM_SHA384；证书主题与目标计算机名一致且在有效期内。诊断期间未导入证书或改变信任存储。独立探测使用当次证书指纹校验，它不能证明系统已建立正常的 CA 信任，更不能证明 RDP 登录成功。

4.5 从远程管理与 SMB 获取 Guest 线索

管理端口探测得到 135、445 可连接，5985、5986 超时。尝试读取远程日志时提示“出现了特定的安全程序包错误”；针对 IPC$ 的一次临时网络认证测试又返回：

SMB_AUTH_RESULT=1272
你不能访问此共享文件夹，因为你组织的安全策略阻止未经身份验证的来宾访问。

1272 与来宾访问提示是下一步检查网络账户映射模式的关键线索。上述管理协议测试只是现场取证，不要求所有读者为了排查而开放更多网络管理端口。

4.6 读取 ForceGuest 与认证组件配置

Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa' |
    Format-List forceguest, LmCompatibilityLevel, 'Security Packages', 'Authentication Packages'

Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders' |
    Format-List SecurityProviders

目标电脑明确返回 forceguest : 1，与此同时其他组件字段有的为空。字段不显示不能直接说明 DLL 损坏；本次没有擅自改写 Security Packages、Authentication Packages 或 SecurityProviders。

5. 实际修复：ForceGuest 从 1 改为 0

配置项实际操作
位置目标电脑的管理员 PowerShell
注册表项HKLM:\SYSTEM\CurrentControlSet\Control\Lsa
键与类型forceguest，REG_DWORD
原值1 = Guest only（本地网络账号按 Guest 映射）
新值0 = Classic（本地账号按自身身份进行网络认证）
重启情况没有因本项修改重启电脑，也没有重启 RDP 服务

只在确认现场存在与 Guest 映射一致的异常、了解共享策略影响后执行。先读取并记录原值：

$lsa = 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa'
$original = Get-ItemPropertyValue -LiteralPath $lsa -Name forceguest -ErrorAction Stop
Write-Host "原始 ForceGuest 值: $original"

# 经评估确认适用后才执行：
Set-ItemProperty -LiteralPath $lsa -Name forceguest -Value 0
Get-ItemPropertyValue -LiteralPath $lsa -Name forceguest

现场修改后读回结果为 0。随后重新建立 RDP 连接；该设置变更没有要求重新配置证书、降低 TLS 安全层或禁用 NLA。

影响范围：从 Guest only 改为 Classic，会改变本地账号用于网络共享/管理访问时的身份与权限判断。如果这是组织策略管理的机器，必须先确认策略来源与合规要求；修改可能随后被组策略重新覆盖。

6. 修复完成后的多重验证

不能只靠注册表读回 0 就宣布成功。本次按“网络管理认证 → RDP 客户端 → 真实桌面 → 服务器日志”顺序交叉验证。

  1. 远程日志可读：修改前的安全程序包错误没有再次出现；使用相同凭据成功读取远程 Security 和 RDP 事件日志。
  2. RDP 进入证书确认阶段：出现与目标计算机名对应的自签名证书警告；用户核对目标后手动确认。不能对任意未知证书警告直接点“是”。
  3. 真正进入远程桌面：用户实际确认“已点击‘是’，进入了远程桌面”。
  4. 服务器侧成功事件：取得事件 1149，时间为 2026-10-19 10:28:17，账号为 Administrator。

复用时可在满足远程事件日志访问权限的条件下，使用交互式凭据查询 1149：

$target = '192.0.2.219' # 替换为目标实际 IP
$cred = Get-Credential -UserName 'TARGET-PC\Administrator'
$end = Get-Date
Get-WinEvent -ComputerName $target -Credential $cred -FilterHashtable @{
    LogName   = 'Microsoft-Windows-TerminalServices-RemoteConnectionManager/Operational'
    Id        = 1149
    StartTime = $end.AddMinutes(-15)
    EndTime   = $end
} -MaxEvents 5 -ErrorAction Stop |
    Select-Object TimeCreated, Id, Message | Format-List
项目修改前修改后
ForceGuest10
本地账号验证成功没有改密码
SMB 临时认证1272未单独复测，不宣称已验证成功
远程日志读取安全程序包错误成功
RDP 登录LSA 错误证书确认后成功进入桌面
服务器事件未取得本次认证成功记录取得 1149 成功事件
重启后的持久性未检查未进行持久性验证

单独的 1149 不能替代桌面实际可用的确认；反之，仅仅出现证书确认窗口也不能宣称已进入远程桌面。本例二者都有对应证据。

7. 推荐复用的排查顺序

  1. 确认地址与账号范围：区分本地账号、域账号、PIN 和其他远控软件密码。
  2. 检查网络及 TCP 3389：端口不通优先查服务、防火墙、路由；端口通才进入认证排查。
  3. 复现并记时：记录精确时间和完整错误；客户端与目标事件日志限定同一个时间窗口。
  4. 确认日志归属：检查调用进程、登录类型、账号域和来源，避免将其他软件的 4625 混入 RDP。
  5. 验证相同的 Windows 密码：有条件时在目标机器通过 runas 验证，不要看到“可能过期”就先重置。
  6. 核对 NLA、TLS、NTLM：区分客户端错误文本和实际 TLS 协商能力，不要直接降低加密要求。
  7. 发现 Guest 线索再读取 ForceGuest：结合 1272 或同类网络认证异常，而不是所有 RDP 故障一律修改。
  8. 记录原值、只改必要项目：在设备策略允许的情况下切到 Classic，重新连接。
  9. 以桌面可用为验收：核验证书、真实登录结果与服务器端身份验证事件。

8. 避免的误判与技术边界

  • 密码过期：Windows 提示是可能原因，不能取代密码验证；本次没有密码重置。
  • 4625 事件归因：向日葵发起的旧交互式失败，不等于这次 RDP 的失败。
  • SSL/TLS 错误：客户端的概括性协商错误与独立 TLS 1.2 握手成功可以同时存在。
  • 日志空输出：可能来自没有事件、权限、筛选条件或错误抑制，不能直接判断组件损坏。
  • 时间异常：曾遇到本机日志中的未来时间记录，因此查询须设置 StartTime、EndTime 并校对时钟。
  • ForceGuest 的适用边界：本案例没有 CredSSP/NTLM 内部流程抓包，也没有回滚复现；保留“实际恢复成功”和“底层因果链不完全证明”的区分。

9. 回滚与复发处理

本案例的原值是 1。只有经确认需要恢复该机器先前的 Guest 网络共享模型时，才执行以下回滚；这不是修复后必须完成的收尾步骤：

$lsa = 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa'
Set-ItemProperty -LiteralPath $lsa -Name forceguest -Value 1
Get-ItemPropertyValue -LiteralPath $lsa -Name forceguest

如果故障重现，首先确认该值是否被管理工具或组策略恢复；若依然为 0，应重新获取新的报错和日志证据，不要重复“改成 0”来代替诊断。此次未确认原值由谁配置、未进行回滚重现，也未进行重启后的持久性验证。
