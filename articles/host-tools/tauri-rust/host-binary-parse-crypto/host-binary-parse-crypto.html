上位机二进制解析、校验与加密

以固件头为例说明二进制格式定义与 Rust 解析，CRC 参数一致性，签名、HMAC 与 AES-GCM 的适用场景和密钥管理。

1. 上位机为什么要处理二进制数据

嵌入式上位机经常需要处理设备产生或使用的二进制数据：

  • 固件文件：解析固件头（版本、长度、CRC），生成升级包，校验完整性。
  • 设备日志 / 采集记录：设备把定长记录写入 Flash 或 SD 卡，上位机读取后解析成表格。
  • 配置文件：上位机生成二进制配置下发给设备，或从设备读回解析显示。
  • 通信报文：协议帧的组包和解析。

这些数据的格式由设备端的 C 结构体定义，上位机必须按字节精确解析，不能依赖语言自身的内存布局。

2. 格式定义：先写清楚再写代码

以固件头为例，格式文档应当明确每个字段的偏移、长度、字节序和含义：

偏移长度字段说明
04magic固定值 0x46574844（小端存储）
42header_ver头格式版本，用于兼容
62hw_id硬件型号
84fw_version主.次.修订编码为 0x00MMmmpp
124image_size镜像长度（不含头）
164image_crc32镜像 CRC32（IEEE）
2012reserved保留，填 0

设备端对应的 C 结构体需要显式控制对齐和字节序，方法见 结构体与数据布局。头格式中一定要有版本字段，以后增加字段时上位机和设备都能识别新旧格式。

3. Rust 解析：显式偏移与字节序

#[derive(Debug, Clone)]
pub struct FwHeader {
    pub header_ver: u16,
    pub hw_id: u16,
    pub fw_version: u32,
    pub image_size: u32,
    pub image_crc32: u32,
}

#[derive(Debug)]
pub enum ParseError {
    TooShort(usize),
    BadMagic(u32),
    UnsupportedVersion(u16),
}

const MAGIC: u32 = 0x4657_4844;
const HEADER_LEN: usize = 32;

fn u16_le(b: &[u8], off: usize) -> u16 { u16::from_le_bytes([b[off], b[off + 1]]) }
fn u32_le(b: &[u8], off: usize) -> u32 { u32::from_le_bytes(b[off..off + 4].try_into().unwrap()) }

pub fn parse_header(b: &[u8]) -> Result<FwHeader, ParseError> {
    if b.len() < HEADER_LEN {
        return Err(ParseError::TooShort(b.len()));
    }
    let magic = u32_le(b, 0);
    if magic != MAGIC {
        return Err(ParseError::BadMagic(magic));
    }
    let header_ver = u16_le(b, 4);
    if header_ver != 1 {
        return Err(ParseError::UnsupportedVersion(header_ver));
    }
    Ok(FwHeader {
        header_ver,
        hw_id: u16_le(b, 6),
        fw_version: u32_le(b, 8),
        image_size: u32_le(b, 12),
        image_crc32: u32_le(b, 16),
    })
}

要点：

  • 先检查长度再访问，所有来自文件或设备的数据都视为不可信输入。
  • 用 from_le_bytes / from_be_bytes 明确字节序，不要直接把字节转换成结构体。
  • 错误类型要具体（太短、魔数错误、版本不支持），方便在界面上给出有用的提示。
  • 字段多、格式复杂时，可以使用 nom、binrw 等解析库，但简单格式手写反而更清晰。

4. 校验：CRC 与哈希

CRC 用于检测传输和存储中的意外错误，上位机与设备必须使用完全相同的 CRC 参数（多项式、初始值、输入输出反转、结果异或值）：

// Cargo.toml: crc = "3"
use crc::{Crc, CRC_32_ISO_HDLC, CRC_16_MODBUS};

const CRC32: Crc<u32> = Crc::<u32>::new(&CRC_32_ISO_HDLC);   // 与 zlib / 以太网相同的 CRC32
const CRC16_MODBUS: Crc<u16> = Crc::<u16>::new(&CRC_16_MODBUS);

pub fn verify_image(header: &FwHeader, image: &[u8]) -> bool {
    image.len() == header.image_size as usize && CRC32.checksum(image) == header.image_crc32
}

设备端常用的“STM32 硬件 CRC 单元”默认参数与标准 CRC32 不同（不反转、不异或），两端结果对不上时首先核对参数。可以用一个固定字符串（例如 "123456789"）的校验值作为两端的测试向量。

CRC 和 SHA-256 只能发现意外损坏，不能防止恶意篡改：攻击者修改固件后重新计算 CRC 即可。需要确认固件来源时必须使用数字签名。

5. 加密与签名：各自解决什么问题

需求技术说明
检测意外损坏CRC32、SHA-256不需要密钥
确认来源、防篡改数字签名（Ed25519、ECDSA P-256）私钥签名，设备内置公钥验证
共享密钥下的防篡改HMAC-SHA256双方持有同一密钥，密钥泄露则失效
防止内容被读取AES-GCM、AES-CTR 等加密加密不等于防篡改，推荐使用带认证的 AES-GCM

固件升级的典型组合是：签名保证来源可信（必须），加密保护知识产权（可选）。设备端的验证流程见 Bootloader 与 OTA。

// 使用 AES-256-GCM 加密配置数据（Cargo.toml: aes-gcm = "0.10"）
use aes_gcm::{aead::{Aead, AeadCore, KeyInit, OsRng}, Aes256Gcm, Key};

pub fn encrypt_config(key_bytes: &[u8; 32], plain: &[u8]) -> Result<Vec<u8>, aes_gcm::Error> {
    let key = Key::<Aes256Gcm>::from_slice(key_bytes);
    let cipher = Aes256Gcm::new(key);
    let nonce = Aes256Gcm::generate_nonce(&mut OsRng);       // 每次加密使用新的随机 nonce（12 字节）
    let mut out = nonce.to_vec();                            // 输出格式：nonce || 密文 || 认证标签
    out.extend(cipher.encrypt(&nonce, plain)?);
    Ok(out)
}

使用加密时的工程要点：

  • 同一密钥下 nonce 绝不能重复，否则 GCM 的安全性完全失效。
  • 不要自己设计加密算法或“异或混淆”，使用经过验证的库。
  • 解密失败（认证标签不匹配）时直接拒绝，不要尝试使用解密出来的数据。

6. 密钥管理

加密方案中最薄弱的环节通常是密钥管理，而不是算法：

  • 签名私钥只保存在受控的签名环境中（专用机器、HSM 或 CI 的密钥管理服务），绝不能放进上位机程序、代码仓库或发给客户的文件中。
  • 上位机内嵌的密钥可以被提取：任何发布给用户的程序都可以被逆向，内嵌对称密钥只能提高门槛，不能作为安全边界。
  • 设备端密钥尽量每台设备不同（由设备唯一 ID 派生或产线写入），单台设备被破解不影响整批设备。
  • 密钥需要有轮换方案：签名公钥可以在设备中预置多个，或者通过受签名保护的升级包更新。

7. 工作场景：固件打包与升级工具

需求：上位机工具把编译产物打包成升级文件，通过串口发送给设备的 Bootloader。

  1. 打包（在发布流水线中执行）：读取 .bin，填写固件头（版本来自 Git 标签、硬件型号、长度、CRC32），用 Ed25519 私钥对“头 + 镜像”签名，签名附加在文件末尾。
  2. 上位机加载：解析头部，检查魔数、头版本、硬件型号是否与连接的设备匹配，校验 CRC；签名由设备验证，上位机只携带公钥做预检查，提前发现错误文件。
  3. 传输：按块发送，每块带序号和 CRC16，设备应答后发送下一块，超时重发。
  4. 设备验证：Bootloader 收完后验证签名，通过后才写入标志切换到新固件。
  5. 测试：准备错误魔数、错误型号、篡改一个字节、截断文件等测试用例，确认每种情况都被拒绝并给出明确提示。

8. 二进制处理检查清单

  • 二进制格式是否有文档，明确偏移、长度、字节序，并包含格式版本字段。
  • 解析前是否检查长度，所有外部输入是否按不可信数据处理。
  • 两端 CRC 参数是否一致，是否有固定测试向量。
  • 是否区分了完整性校验、来源认证和保密需求，防篡改是否使用了签名或 HMAC。
  • 加密是否使用 AES-GCM 等带认证的模式，nonce 是否保证不重复。
  • 签名私钥是否只存在于受控环境，没有出现在上位机程序和代码仓库中。
  • 是否用损坏、篡改、截断等异常文件测试过解析与校验流程。
