用 Tauri 开发串口上位机

基于 Tauri 2 与 serialport 库，说明工程结构、Rust 命令、后台接收线程与事件推送、前端调用和打包发布要点。

1. 为什么用 Tauri 做上位机

嵌入式工程师常用的上位机技术路线：

方案优点缺点
C# WinForms / WPF开发快，串口库成熟主要面向 Windows
Qt（C++ / PySide）跨平台，控件丰富体积较大，授权需要注意
Python + Tkinter / PyQt上手快，适合内部工具打包体积大，发布给客户不够专业
ElectronWeb 技术做界面，生态丰富安装包和内存占用大
Tauri（Rust + Web 前端）安装包小（几 MB）、性能好、跨平台需要学习 Rust，前后端通信要设计

Tauri 的结构是：界面用 Web 技术（HTML / CSS / JS，可选 Vue、React 等）编写，运行在系统自带的 WebView 中；设备通信、文件处理等逻辑用 Rust 编写。前端通过 invoke 调用 Rust 命令，Rust 通过事件把数据推送给前端。本文基于 Tauri 2。

2. 工程结构

3. Rust 端：串口命令

// src-tauri/src/lib.rs
use std::io::{Read, Write};
use std::sync::Mutex;
use std::time::Duration;
use serialport::SerialPort;
use tauri::State;

#[derive(Default)]
struct AppState {
    port: Mutex<Option<Box<dyn SerialPort>>>,
}

#[tauri::command]
fn list_ports() -> Result<Vec<String>, String> {
    let ports = serialport::available_ports().map_err(|e| e.to_string())?;
    Ok(ports.into_iter().map(|p| p.port_name).collect())
}

#[tauri::command]
fn write_bytes(state: State<'_, AppState>, data: Vec<u8>) -> Result<(), String> {
    let mut guard = state.port.lock().map_err(|e| e.to_string())?;
    let port = guard.as_mut().ok_or("串口未打开")?;
    port.write_all(&data).map_err(|e| e.to_string())
}

pub fn run() {
    tauri::Builder::default()
        .manage(AppState::default())
        .invoke_handler(tauri::generate_handler![list_ports, open_port, write_bytes, close_port])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}

要点：

  • 命令返回 Result<T, String>，错误信息会作为 Promise 的 reject 传给前端，前端可以直接显示给用户。
  • 串口对象放在 Mutex 中，由 Tauri 的状态管理（manage）共享给所有命令。
  • 前端传来的参数会自动反序列化，Vec<u8> 对应 JS 中的数字数组。

4. 后台接收线程与事件推送

串口接收不能在命令里阻塞等待，应该在打开串口时启动后台线程，收到数据后通过事件推送给前端：

use tauri::{AppHandle, Emitter};

#[tauri::command]
fn open_port(app: AppHandle, state: State<'_, AppState>, name: String, baud: u32) -> Result<(), String> {
    let port = serialport::new(&name, baud)
        .timeout(Duration::from_millis(50))
        .open()
        .map_err(|e| format!("打开 {name} 失败：{e}"))?;

    let mut reader = port.try_clone().map_err(|e| e.to_string())?;
    *state.port.lock().unwrap() = Some(port);

    std::thread::spawn(move || {
        let mut buf = [0u8; 1024];
        loop {
            match reader.read(&mut buf) {
                Ok(n) if n > 0 => {
                    let _ = app.emit("serial-data", buf[..n].to_vec());
                }
                Ok(_) => {}
                Err(e) if e.kind() == std::io::ErrorKind::TimedOut => {}   // 超时：继续等待
                Err(e) => {
                    let _ = app.emit("serial-error", e.to_string());       // 设备拔出等错误
                    break;
                }
            }
        }
    });
    Ok(())
}

实际工程中还需要：关闭串口时通知接收线程退出（例如用 AtomicBool 标志或通道）；高速数据时不要每收到几个字节就发一次事件，而是在 Rust 端组帧或按时间（如 20ms）合并后再推送，避免前端被大量事件拖慢。

5. 前端：调用命令与监听事件

import { invoke } from '@tauri-apps/api/core';
import { listen } from '@tauri-apps/api/event';

const ports = await invoke<string[]>('list_ports');

try {
  await invoke('open_port', { name: ports[0], baud: 115200 });
} catch (err) {
  showError(String(err));                       // Rust 返回的 Err 字符串
}

const unlisten = await listen<number[]>('serial-data', (event) => {
  appendHex(new Uint8Array(event.payload));     // 显示为十六进制
});

await invoke('write_bytes', { data: [0x01, 0x03, 0x00, 0x00, 0x00, 0x02, 0xC4, 0x0B] });

注意：invoke 的参数名在 JS 侧使用 camelCase，Rust 函数参数使用 snake_case，Tauri 会自动转换。界面关闭或切换页面时调用 unlisten() 取消监听。

6. 协议处理放在哪一端

放在 Rust 端放在前端
组帧、校验（CRC）、超时重发显示格式、图表
高速数据的解析和统计用户输入校验
文件读写、固件升级流程交互流程控制
加解密—

原则是：与设备通信的时序、可靠性相关的逻辑放在 Rust 端，前端只处理“已经解析好的数据”和用户交互。这样协议代码可以写单元测试，也可以被命令行工具复用。二进制解析和加密的写法见 二进制解析与加密，设备端的串口协议设计见 UART、SPI 与 I2C。

7. 打包与发布

  • Windows：生成 msi 或 NSIS 安装包；系统需要 WebView2（Windows 10/11 通常已内置，安装包可配置自动安装）。
  • 串口驱动：USB 转串口芯片（CH340、CP2102 等）的驱动不包含在应用中，需要告知用户或单独提供。
  • 代码签名：给客户发布时建议对安装包进行代码签名，否则可能被系统或杀毒软件拦截。
  • 自动更新：Tauri 提供 updater 插件，更新包需要签名，签名私钥不要提交到仓库。
  • 权限：使用文件对话框、文件系统等插件时，需要在 capabilities 中声明前端可调用的权限，只授予需要的范围。

8. 工作场景：一个 Modbus 调试上位机

需求：选择串口和波特率，周期性读取设备的 20 个寄存器并显示曲线，可以修改参数并写入，支持导出 CSV。

  1. Rust 端：串口管理、Modbus RTU 组帧和 CRC 校验、请求超时与重试、周期轮询任务；每轮读取结果作为一个事件推送。
  2. 前端：串口选择、寄存器表格、实时曲线（只保留最近 N 个点）、参数写入表单。
  3. 错误处理：设备无应答、CRC 错误、串口拔出都在界面上显示状态，并统计通信成功率。
  4. 导出：前端调用 Rust 命令，Rust 端把缓存的数据写成 CSV，路径通过文件对话框插件选择。
  5. 测试：协议模块编写单元测试（固定报文 → 解析结果），用 USB 转串口回环和真实设备分别测试。

9. 上位机开发检查清单

  • 串口接收是否在后台线程中进行，关闭串口时线程能否正确退出。
  • 设备拔出、无应答、校验错误等异常是否有明确提示，而不是程序卡住或崩溃。
  • 高速数据是否在 Rust 端合并或组帧后再推送，前端是否限制了显示的数据量。
  • 协议、校验、超时重试等逻辑是否放在 Rust 端并有单元测试。
  • 前端可用的插件权限是否按最小范围配置。
  • 安装包是否考虑了 WebView2、串口驱动、代码签名与更新签名密钥的管理。
