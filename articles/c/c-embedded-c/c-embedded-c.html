嵌入式 C 关键语法与 GNU C 扩展实践

本文整理嵌入式 C 中经常出现、但普通 C 语言教程讲得不够深入的关键点，包括 volatile、static、const、宏定义、条件编译、中断共享变量、寄存器位操作、函数指针和 GNU C 扩展语法等内容。

嵌入式 C 的重点是理解编译器优化、硬件寄存器副作用、中断并发和资源受限环境。GNU C 扩展语法很常见，但它不是标准 C，使用时要清楚可移植性边界。

一、嵌入式 C 与普通 C 的差异

普通 C 程序主要处理内存中的数据，而嵌入式 C 经常直接面对硬件寄存器、中断、DMA、外设状态和实时约束。变量的值可能被中断、硬件或 DMA 改变，而不是只由当前代码路径改变。

  • 寄存器读写可能有副作用。
  • 中断可能在任意时刻修改共享变量。
  • 编译器优化可能删除看似“无意义”的重复读取。
  • 栈和堆空间有限，不能无限制创建大对象。
  • 编译器扩展语法可能提升表达能力，但也可能降低可移植性。

二、volatile 的作用

volatile 告诉编译器：这个变量的值可能在当前代码无法感知的情况下发生变化，每次访问都必须真实读写，不能随意优化掉。 

static volatile uint8_t s_uart_rx_done;

void uart_rx_isr(void)
{
    s_uart_rx_done = 1U;
}

void wait_uart_rx(void)
{
    while (s_uart_rx_done == 0U) {
        // 等待中断修改标志
    }
}

常见需要 volatile 的场景包括中断共享变量、硬件寄存器、DMA 状态标志和多任务共享标志。但 volatile 不是锁，不能解决原子性和互斥问题。

三、static 的几种用法

static 在 C 语言中有两类常见含义：改变生命周期，或者限制符号可见性。文件内全局变量和内部函数建议使用 static，避免污染全局命名空间。 

static uint32_t s_sample_count;

static void filter_reset(void)
{
    s_sample_count = 0U;
}

函数内部的静态局部变量生命周期贯穿整个程序，但作用域仍在函数内部，适合保存简单状态。不过如果函数需要重入，静态局部变量会带来风险。

四、const 的工程意义

const 表示对象不应被修改。嵌入式中，常量表、字符串、配置描述表、命令表都适合使用 const，这样可以帮助编译器把数据放到只读区域，也能减少误修改。 

typedef struct {
    uint8_t cmd;
    const char *name;
} cmd_info_t;

static const cmd_info_t g_cmd_table[] = {
    {0x01, "read"},
    {0x02, "write"},
};

指针和指针指向的数据都可能是 const。const uint8_t *data 表示不能通过该指针修改数据，适合作为只读输入缓冲区。

五、宏定义与条件编译

宏常用于常量、位操作、条件编译和简单内联表达式。宏没有类型检查，复杂宏必须加括号，避免运算优先级问题。 

#define BIT(n)              (1U << (n))
#define ARRAY_SIZE(arr)     (sizeof(arr) / sizeof((arr)[0]))
#define APP_DEBUG_ENABLE    1

#if APP_DEBUG_ENABLE
#define APP_LOG(msg)        debug_print(msg)
#else
#define APP_LOG(msg)        do { } while (0)
#endif

条件编译适合区分不同芯片、不同板卡、调试版本和发布版本，但不要让条件分支过度分散，否则代码可读性会明显下降。

六、中断函数中的 C 语言注意事项

中断函数应尽量短，只做必要的数据搬运和标志设置。耗时处理、日志输出、复杂协议解析、动态内存申请都不适合放在中断里。 

static volatile uint8_t s_tick_flag;

void timer_isr(void)
{
    s_tick_flag = 1U;
}

void app_loop(void)
{
    if (s_tick_flag != 0U) {
        s_tick_flag = 0U;
        // 在主循环中处理周期任务
    }
}

如果中断和主循环共享多字节变量，需要考虑读写是否原子。必要时短暂关闭中断，或者使用 RTOS 提供的同步机制。

七、寄存器读写与位操作

寄存器操作通常通过地址、结构体或厂商提供的宏完成。寄存器读改写时要注意只修改目标 bit，避免误伤其它配置位。 

#define GPIO_ENABLE_REG     (*(volatile uint32_t *)0x40000000U)
#define GPIO0_ENABLE_BIT    BIT(0)

GPIO_ENABLE_REG |= GPIO0_ENABLE_BIT;
GPIO_ENABLE_REG &= ~GPIO0_ENABLE_BIT;

有些寄存器写 1 清零，有些寄存器读取会清标志，有些寄存器需要按固定顺序访问。写驱动时必须结合芯片手册理解寄存器副作用。

八、回调函数与函数指针

函数指针常用于事件回调、驱动适配层、命令表和状态机处理。它可以减少大量 switch 分支，但也会降低初学者阅读直观性。 

typedef void (*event_cb_t)(uint8_t event);

static event_cb_t s_event_cb;

void app_register_callback(event_cb_t cb)
{
    s_event_cb = cb;
}

void app_emit_event(uint8_t event)
{
    if (s_event_cb != NULL) {
        s_event_cb(event);
    }
}

使用回调前必须判空，并且要明确回调执行上下文：是在中断里调用，还是在主循环/任务里调用。

九、GNU C 扩展语法概览

嵌入式项目中经常使用 GCC、Clang、ESP-IDF、Linux 内核风格代码，因此会遇到 GNU C 扩展语法。它们能增强表达能力，但不是 ISO C 标准的一部分，迁移到其它编译器时要谨慎。

  • __attribute__：给变量、函数、结构体增加编译器属性。
  • typeof：在宏中获取表达式类型。
  • 语句表达式：让宏内部可以写多条语句并返回一个值。
  • __builtin_*：使用编译器内建函数。
  • 弱符号、段放置、packed、aligned 等属性：常用于启动代码、驱动和链接脚本配合。

十、__attribute__ 常见用法

__attribute__ 是 GNU C 中非常常见的扩展，用于声明对齐、紧凑布局、弱符号、指定段、废弃接口等属性。 

typedef struct __attribute__((packed)) {
    uint8_t header;
    uint16_t length;
    uint8_t cmd;
} packed_frame_t;

uint8_t dma_buffer[1024] __attribute__((aligned(4)));

void user_hook(void) __attribute__((weak));

void user_hook(void)
{
    // 默认弱实现，用户可以在其它文件中重写
}

packed 可以减少结构体填充字节，但可能导致非对齐访问，部分 MCU 上会降低效率甚至触发异常。对外部协议建议优先手动序列化，不要盲目依赖 packed 结构体。

十一、section、used 与链接脚本配合

section 可以把函数或变量放到指定段，常用于启动代码、中断向量表、Bootloader、Flash 固定区域、保留参数区等场景。used 可以避免符号被优化删除。 

const uint32_t app_magic __attribute__((section(".app_info"), used)) = 0xA55A1234U;

void boot_entry(void) __attribute__((section(".boot_text")));

void boot_entry(void)
{
    // Bootloader 入口代码
}

使用 section 时必须检查链接脚本是否定义了对应段，否则符号可能没有放到预期位置。

十二、typeof 与语句表达式

GNU C 支持 typeof 和语句表达式，常用于写类型安全一些的宏。例如 Linux 内核风格的 min、max、container_of 等宏会用到类似能力。 

#define MIN(a, b) ({          \
    typeof(a) _a = (a);       \
    typeof(b) _b = (b);       \
    _a < _b ? _a : _b;        \
})

uint16_t x = MIN(100U, 200U);

语句表达式可以让宏像函数一样返回值，但它是 GNU C 扩展。若项目要求严格标准 C 或需要支持非 GCC 兼容编译器，应避免使用。

十三、container_of 思想

container_of 的思想是：已知结构体中某个成员的地址，反推出整个结构体对象的地址。它常用于链表、事件节点、驱动对象封装等场景。 

#define OFFSET_OF(type, member) ((size_t)&(((type *)0)->member))

#define CONTAINER_OF(ptr, type, member) \
    ((type *)((char *)(ptr) - OFFSET_OF(type, member)))

typedef struct {
    uint8_t id;
    uint16_t value;
} item_t;

这类宏很强大，但也很容易写出难读代码。普通业务模块不建议过度使用，底层框架、链表和驱动抽象层中使用更合适。

十四、GNU C 扩展使用建议

  • 能用标准 C 清晰表达时，优先使用标准 C。
  • 必须使用扩展时，建议集中封装在公共头文件或底层模块中。
  • 使用 packed 前确认平台是否允许非对齐访问。
  • 使用 section 后检查 map 文件和链接脚本。
  • 使用弱符号时，要确认重名强符号确实参与链接。
  • 使用复杂宏时，注意参数是否会被重复求值。
  • 如果代码需要跨编译器，提前评估 GNU C 扩展的替代方案。

十五、嵌入式 C 编码检查清单

  • 中断共享变量是否需要 volatile。
  • 文件内部变量和函数是否使用 static 限制可见性。
  • 只读表、字符串和输入缓冲区是否使用 const。
  • 宏参数和宏整体是否加了括号。
  • 中断函数中是否存在耗时操作。
  • 寄存器读改写是否可能影响其它 bit。
  • 回调函数是否判空，执行上下文是否清楚。
  • GNU C 扩展语法是否有明确使用理由。
  • 使用 section、aligned、packed 后是否通过 map 文件或反汇编确认结果。
