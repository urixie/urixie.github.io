AI 编程助手在嵌入式开发中的使用

说明 Claude Code、Codex 等 AI 编程助手适合与不适合的嵌入式工作、项目上下文文件、推荐工作流程和提问方式。

1. AI 编程助手在嵌入式开发中的定位

Claude Code、Codex 这类命令行 AI 编程助手可以读取整个代码仓库、执行命令、修改文件和运行测试。它们在嵌入式开发中能明显提高效率，但嵌入式有自己的特殊性：代码最终运行在真实硬件上，时序、寄存器、电气特性无法通过“编译通过”来验证。

比较合理的定位是：把 AI 助手当作一个读代码快、写样板代码快、但不了解你的硬件的同事。它擅长的事情交给它，涉及硬件事实的部分由工程师确认。

2. 适合交给 AI 的工作

工作说明注意
阅读陌生代码梳理厂商 SDK、开源驱动、老项目的调用关系和初始化流程关键结论回到源码确认
样板代码寄存器位定义、外设初始化框架、命令解析表、状态机骨架寄存器地址和位定义对照数据手册核对
上位机与脚本串口工具、数据解析脚本、日志分析、构建脚本、CI 配置风险低，收益最高
单元测试为协议解析、算法、环形缓冲等纯逻辑代码编写测试让它先运行测试，确认测试本身能失败
代码审查检查并发访问、整数溢出、边界条件、资源泄漏作为补充，不替代人工审查
文档整理根据代码生成接口说明、寄存器表、变更说明核对准确性
问题分析分析编译错误、链接错误、HardFault 寄存器转储、内核 Oops 日志提供完整日志和 map / elf 信息

3. 需要特别谨慎的地方

  • 寄存器与硬件细节：AI 可能给出看似合理但不存在的寄存器名、错误的位偏移，或把另一个系列芯片的外设用法套过来。任何寄存器操作都要对照该芯片的参考手册。
  • 时序与实时性：中断优先级、临界区、DMA 与 Cache 一致性、外设时序要求，这些问题编译器和单元测试都发现不了。
  • 安全相关代码：加密、签名验证、Bootloader 跳转、看门狗策略，需要逐行审查。
  • “修好了”的错觉：让测试通过的最快方式之一是修改测试本身，审查改动时要留意这一点。
  • 数据安全：不要把密钥、密码、客户数据交给 AI；涉及保密协议的代码是否可以使用在线 AI 服务，要先确认公司规定。

4. 给 AI 提供项目上下文

AI 助手每次开始工作时并不了解项目约定。在仓库根目录放一份说明文件（Claude Code 读取 CLAUDE.md，Codex 读取 AGENTS.md），写清楚它需要知道的事情：

# 项目说明

## 硬件
- MCU：STM32G431CBU6（Cortex-M4F，128KB Flash，32KB SRAM）
- 外设分配见 docs/pinout.md，不要修改引脚分配

## 构建与测试
- 构建：cmake --preset release && cmake --build --preset release
- 主机单元测试：cmake --preset test && ctest --preset test
- 修改代码后必须保证上述两条命令通过

## 代码约定
- C11，不使用动态内存分配（禁止 malloc）
- 中断服务函数只做标志设置和数据搬运，处理放在任务中
- 寄存器访问使用 LL 库，不使用 HAL
- 第三方代码在 third_party/，不要修改

## 注意
- 寄存器相关修改需在提交说明中注明参考手册章节

这份文件也是给新同事看的项目说明，写好它本身就有价值。

5. 推荐的工作流程

  1. 任务拆小：“给 Modbus 从机增加 0x10 写多个寄存器功能，并补充单元测试”比“完善 Modbus 功能”更容易得到正确结果。
  2. 先计划后修改：让 AI 先说明打算修改哪些文件、如何实现，确认方向后再动手。
  3. 让它自己验证：要求 AI 修改后执行编译和测试，把错误信息反馈给它继续修正，而不是由人来回复制粘贴。
  4. 审查差异：用 git diff 逐个文件审查改动，重点看是否有超出任务范围的修改。
  5. 硬件验证：编译和测试通过后，上板验证由工程师完成，结果（日志、波形）可以再交给 AI 分析。
  6. 小步提交：每完成一个可验证的步骤就提交，出问题时可以回退。Git 工作习惯见 嵌入式项目的 Git 工作流。

6. 提问的方式

AI 的回答质量很大程度取决于提供的信息：

不好的问法更好的问法
“串口收不到数据”“STM32G4 的 USART2 使用 DMA 循环接收 + 空闲中断，波特率 115200，示波器看 RX 引脚有波形，但空闲中断从不触发。相关代码在 drivers/uart.c，请检查初始化和中断使能”
“程序死机了”“运行约 2 小时后 HardFault，下面是 HardFault 处理中打印的寄存器和 map 文件中相关地址段，请分析可能原因”
“写一个 SPI 驱动”“参考 drivers/i2c_sensor.c 的分层方式，为 W25Q64 写一个 SPI Flash 驱动，提供读、页编程、扇区擦除和读 ID，SPI 底层接口已在 bsp/spi.h 中”

要点：说明芯片型号和软件环境、已经确认的事实、相关文件位置，以及期望的产出形式。

7. 工作场景：用 AI 助手开发一个产测工具

需求：产线需要一个工具，通过串口向设备发送测试命令，依次测试 LED、按键、ADC、Flash、RS485，生成测试报告。

  1. 设备端：工程师定义测试命令协议（命令码、参数、应答格式），写入文档。让 AI 根据文档在固件中实现命令解析框架和各测试项的骨架，工程师补充和核对硬件相关部分。
  2. 上位机端：让 AI 根据同一份协议文档编写 Python 或 Tauri 上位机：串口选择、逐项测试、超时处理、结果判定、CSV 报告。这部分几乎可以完全交给 AI，工程师负责审查和试用。
  3. 测试：让 AI 为协议解析编写单元测试，并写一个模拟设备的脚本（虚拟串口应答），在没有硬件时也能测试上位机流程。
  4. 上线：工程师在真实设备上验证，把产线反馈的问题和日志交给 AI 修改。

整个过程中，AI 承担了大量协议实现、界面和测试代码的编写，工程师把精力放在协议设计、硬件相关代码和最终验证上。

8. AI 辅助开发检查清单

  • 仓库中是否有 CLAUDE.md / AGENTS.md 等说明文件，写明硬件、构建测试命令和代码约定。
  • 任务是否拆分得足够小，是否先确认实现方案再修改代码。
  • AI 修改后是否自行执行了编译和测试，测试是否被不当修改。
  • 寄存器、时序、中断与安全相关代码是否经过工程师对照手册审查。
  • 是否用 git diff 审查了全部改动，并小步提交。
  • 是否避免向 AI 提供密钥、密码和受保密协议约束的数据。
  • 最终功能是否在真实硬件上验证。
