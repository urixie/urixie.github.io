Verilog Testbench仿真与调试

FPGA 设计不能只靠上板测试。Testbench 可以在仿真环境中给 DUT 提供时钟、复位和输入激励，观察输出是否符合预期。很多时序、状态机和协议问题，在上板前就应该通过仿真发现。

工程建议：每写一个有明确输入输出的模块，都至少写一个基础 Testbench。尤其是 ADC/SPI/IIC/UART/帧解析/FIFO/状态机这类模块，没有仿真就上板，后期排错成本会非常高。

1. Testbench 基本结构

Testbench 本身不综合成硬件，只用于仿真。它通常没有端口，内部例化待测模块 DUT，然后产生输入激励。

`timescale 1ns/1ps

module tb_counter;

reg clk;
reg rst_n;
wire [7:0] cnt;

counter dut (
    .clk   (clk),
    .rst_n (rst_n),
    .cnt   (cnt)
);

endmodule

2. 产生时钟和复位

仿真中最常见的激励是时钟和复位。时钟用 always 周期翻转，复位用 initial 控制释放时刻。

initial begin
    clk = 1'b0;
end

always #10 clk = ~clk; // 50MHz

initial begin
    rst_n = 1'b0;
    #100;
    rst_n = 1'b1;
end

3. 输入激励

输入激励可以直接在 initial 中按时间推进，也可以封装成 task，让测试过程更清晰。

task send_pulse;
begin
    trig = 1'b1;
    @(posedge clk);
    trig = 1'b0;
    @(posedge clk);
end
endtask

initial begin
    trig = 1'b0;
    wait(rst_n == 1'b1);
    repeat (5) send_pulse();
    #1000;
    $finish;
end

4. 波形输出

使用 Icarus Verilog、GTKWave 等工具时，可以输出 VCD 波形文件。其它 FPGA IDE 也有自己的波形查看器。

initial begin
    $dumpfile("tb_counter.vcd");
    $dumpvars(0, tb_counter);
end

5. $display 调试

$display 可以在仿真控制台打印变量值，适合快速判断状态跳转、计数值和错误路径。

always @(posedge clk) begin
    if (data_valid) begin
        $display("time=%0t data=%h", $time, data);
    end
end

6. 自检查 Testbench

更好的 Testbench 不只是看波形，而是自动判断输出是否正确。这样改代码后可以快速回归验证。

if (cnt !== 8'd10) begin
    $display("ERROR: cnt expected 10, got %0d", cnt);
    $finish;
end else begin
    $display("PASS");
end

7. 常见仿真问题

现象优先排查方向
波形全是 X复位没有释放、信号未初始化、分支未赋值
输出慢一拍时序逻辑寄存器更新延迟，确认是否符合设计
状态机不跳转跳转条件没有拉高、握手信号时序不对
仿真正确上板错误时序约束、跨时钟域、复位同步、外设真实时序
综合后行为不同不可综合语句、latch、阻塞/非阻塞误用

8. 上板调试思路

上板调试时，可以使用 FPGA 厂商提供的逻辑分析仪工具抓内部信号，例如 SignalTap、ILA、安路或其它工具链中的在线调试功能。抓信号时要优先抓状态机状态、计数器、valid/ready、错误标志和外设接口关键线。

9. 参考模型与自动比对

“看波形判断对不对”只适合最初的调试。随着测试用例增加，必须让 Testbench 自动判断结果。最实用的结构是参考模型 + 比对器（scoreboard）：

  • 参考模型用行为级代码（不考虑时序和可综合性）计算出“正确答案”。
  • DUT 输出结果后，与参考模型的结果逐个比对，记录错误数量。
  • 仿真结束时统一打印 PASS / FAIL，便于脚本判断。
// 期望值队列：输入时由参考模型计算期望输出，DUT 输出时取出比对
reg [15:0] expect_q [0:1023];
integer    wr_idx = 0, rd_idx = 0, errors = 0;

always @(posedge clk) begin
    if (din_valid) begin
        expect_q[wr_idx] <= ref_model(din);      // 参考模型：function 实现的行为级计算
        wr_idx <= wr_idx + 1;
    end
    if (dout_valid) begin
        if (dout !== expect_q[rd_idx]) begin
            errors = errors + 1;
            $display("ERROR @%0t: idx=%0d expect=%h got=%h", $time, rd_idx, expect_q[rd_idx], dout);
        end
        rd_idx <= rd_idx + 1;
    end
end

这种写法不关心 DUT 的流水线延迟是多少拍，只要输出顺序正确就能自动对齐，非常适合滤波器、协议处理、数据通路等模块。

10. 用 task 封装总线：总线功能模型

测试接口模块时，把“发送一个 UART 字节”“完成一次 SPI 传输”“写一个寄存器”封装成 task，测试用例读起来就像操作说明：

localparam real BIT_NS = 1_000_000_000.0 / 115200;    // UART 位时间

// 模拟外部设备向 DUT 发送一个字节
task uart_send_byte(input [7:0] data);
    integer i;
    begin
        rx = 1'b0; #(BIT_NS);                          // 起始位
        for (i = 0; i < 8; i = i + 1) begin
            rx = data[i]; #(BIT_NS);                   // 低位先发
        end
        rx = 1'b1; #(BIT_NS);                          // 停止位
    end
endtask

initial begin
    rx = 1'b1;
    wait (rst_n);
    uart_send_byte(8'hAA);
    uart_send_byte(8'h55);
    uart_send_byte(8'h03);
end

这种模拟外部器件行为的 task 集合称为总线功能模型（BFM）。BFM 中还可以故意制造异常：错误的停止位、波特率偏差 3%、字节之间插入长间隔，用来验证 DUT 的容错能力。

11. 随机激励与边界测试

手写的测试用例往往只覆盖“想到的情况”，bug 常常藏在没想到的组合里。加入随机激励可以大幅提高覆盖面：

integer seed = 12345;                           // 固定种子：出错时可以复现
initial begin
    repeat (10000) begin
        @(posedge clk);
        din_valid <= ($random(seed) % 4) != 0;  // 75% 的概率输入有效，模拟不连续的数据流
        din       <= $random(seed);
        m_ready   <= ($random(seed) % 8) != 0;  // 下游随机反压
    end
end

随机测试之外，边界值必须单独构造：计数器最大值与回绕、FIFO 刚好满和刚好空、最大和最小数据长度、复位发生在传输中途。固定随机种子并打印出来，出错时用同一个种子就能稳定复现。

12. 文件驱动测试：与 Python / MATLAB 联合验证

对于算法类模块（滤波、FFT、图像处理），用 Python 或 MATLAB 生成输入数据和期望结果，Testbench 读取文件进行仿真，再把 DUT 输出写回文件交给脚本比对：

reg [15:0] stim [0:4095];
integer    fout, k;
initial begin
    $readmemh("stim_input.hex", stim);          // Python 生成的十六进制输入
    fout = $fopen("dut_output.txt", "w");
    for (k = 0; k < 4096; k = k + 1) begin
        @(posedge clk);
        din <= stim[k];
        din_valid <= 1'b1;
    end
    din_valid <= 1'b0;
end

always @(posedge clk)
    if (dout_valid) $fwrite(fout, "%0d\n", $signed(dout));

脚本端可以计算误差、画频谱、与浮点参考结果比较。定点化带来的量化误差在这一步就能评估，而不是上板后才发现精度不够。

13. 仿真工具与回归测试

工具特点适用
Icarus Verilog + GTKWave开源、轻量、命令行友好学习、小型模块、CI 回归
Verilator把 Verilog 编译成 C++，速度极快大规模、长时间仿真，配合 C++ / Python 测试
ModelSim / Questa功能全面，支持 SystemVerilog 与覆盖率商业项目、复杂验证
Vivado Simulator（xsim）与 Vivado 集成，直接支持 Xilinx IP 仿真模型含 Xilinx IP 的设计

几个工程习惯：

  • 每个 Testbench 都要有超时保护，防止 DUT 卡死时仿真永远不结束：
initial begin
    #10_000_000;                                 // 10ms 仿真时间上限
    $display("FAIL: timeout");
    $finish;
end
  • 结果以统一格式输出（例如最后一行固定为 PASS 或 FAIL: n errors），用脚本批量运行所有 Testbench，形成回归测试。每次修改代码后跑一遍，及时发现改动带来的副作用。
  • 使用厂商 IP 的模块需要调用 IP 的仿真模型（Vivado 中生成 IP 时会同时生成），开源仿真器可能不支持加密模型，这时用厂商仿真器或把 IP 替换为行为模型。
  • 仿真通过不等于上板正确：仿真不检查时序、不模拟亚稳态。上板前还要确认 时序约束 和 跨时钟域处理。

14. 仿真检查清单

  • 是否产生了稳定时钟。
  • 复位时长是否足够。
  • 是否覆盖正常路径、异常路径和边界条件。
  • 是否检查输出结果，而不是只看波形。
  • Testbench 是否包含必要的超时退出。
  • 上板前是否确认时序约束和跨时钟域处理。
  • 是否使用参考模型和自动比对代替人工看波形，结束时是否统一输出 PASS / FAIL。
  • 接口模块是否用 task 封装总线功能模型，并构造了异常输入。
  • 是否加入随机激励和随机反压，随机种子是否固定并打印。
  • 算法模块是否用 Python / MATLAB 生成测试数据并比对输出。
  • 是否建立了可批量运行的回归测试，每次修改后执行。
