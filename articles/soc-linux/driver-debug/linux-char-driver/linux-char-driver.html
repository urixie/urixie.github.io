Linux 字符设备驱动入门

从 platform 驱动与设备树匹配、devm 资源管理、中断与 file_operations 讲起，配合一个完整驱动骨架，说明何时需要写驱动以及调试方法。

1. 什么时候需要自己写驱动

嵌入式 Linux 项目中，大部分常见外设已经有现成的内核驱动：I2C 传感器有 IIO 驱动，SPI Flash 有 MTD 驱动，以太网 PHY、USB、显示屏也都有。自己写驱动之前先确认三件事：

  1. 内核里是否已有驱动：搜索内核源码中芯片型号或兼容字符串（grep -r "ti,ads1015" drivers/），往往只需要在设备树中添加节点、在内核配置中打开。
  2. 能否在用户态完成：低速的 GPIO、I2C、SPI 设备，通过 libgpiod、/dev/i2c-*、spidev 在用户态访问就能满足需求，调试更方便，见 用户态访问 GPIO、I2C、SPI 与 UART。
  3. 确实需要内核驱动的情况：有严格实时性要求的中断处理、需要 DMA、需要接入内核子系统（输入、IIO、网络、显示），或者需要给多个进程提供统一的设备抽象。

2. platform 驱动与设备树匹配

嵌入式 SoC 上的外设大多没有自动枚举能力（不像 PCI、USB），内核通过设备树得知“板子上有什么设备、接在哪里”，再通过兼容字符串把设备和驱动匹配起来。

/* 设备树：描述一个挂在 SoC 上的自定义外设 */
mydev@ff100000 {
    compatible = "acme,mydev";
    reg = <0x0 0xff100000 0x0 0x1000>;            /* 寄存器地址和大小 */
    interrupts = <GIC_SPI 45 IRQ_TYPE_LEVEL_HIGH>;
    reset-gpios = <&gpio1 RK_PA5 GPIO_ACTIVE_LOW>;
    status = "okay";
};
static const struct of_device_id mydev_of_match[] = {
    { .compatible = "acme,mydev" },
    { }
};
MODULE_DEVICE_TABLE(of, mydev_of_match);

static struct platform_driver mydev_driver = {
    .probe  = mydev_probe,
    .remove = mydev_remove,
    .driver = {
        .name           = "mydev",
        .of_match_table = mydev_of_match,
    },
};
module_platform_driver(mydev_driver);
MODULE_LICENSE("GPL");

内核启动时（或模块加载时）遍历设备树节点，compatible 与驱动表中的字符串一致时，调用驱动的 probe 函数。probe 没有被调用是驱动调试中最常见的问题，原因通常是：兼容字符串拼写不一致、节点 status 不是 "okay"、驱动没有编译进内核或模块没有加载、父总线节点被禁用。

3. probe 中做什么：使用 devm 资源管理

probe 负责获取资源、初始化硬件、注册设备。推荐使用 devm_ 开头的接口：资源与设备绑定，probe 失败或驱动卸载时自动释放，避免出错路径上的资源泄漏。

struct mydev {
    void __iomem      *base;
    int                irq;
    struct gpio_desc  *reset;
    struct miscdevice  misc;
};

static int mydev_probe(struct platform_device *pdev)
{
    struct device *dev = &pdev->dev;
    struct mydev *md;
    int ret;

    md = devm_kzalloc(dev, sizeof(*md), GFP_KERNEL);
    if (!md)
        return -ENOMEM;

    md->base = devm_platform_ioremap_resource(pdev, 0);     /* 映射 reg 描述的寄存器 */
    if (IS_ERR(md->base))
        return PTR_ERR(md->base);

    md->reset = devm_gpiod_get_optional(dev, "reset", GPIOD_OUT_HIGH);
    if (IS_ERR(md->reset))
        return dev_err_probe(dev, PTR_ERR(md->reset), "failed to get reset gpio\n");

    md->irq = platform_get_irq(pdev, 0);
    if (md->irq < 0)
        return md->irq;
    ret = devm_request_threaded_irq(dev, md->irq, NULL, mydev_irq_thread,
                                    IRQF_ONESHOT, dev_name(dev), md);
    if (ret)
        return ret;

    platform_set_drvdata(pdev, md);
    return mydev_register_misc(md);
}

dev_err_probe() 会在资源暂时不可用（-EPROBE_DEFER，例如依赖的 GPIO 控制器驱动还没加载）时不打印错误，并让内核稍后重试 probe。这是设备之间存在依赖时的标准处理方式。

4. 给用户态提供接口

驱动初始化好硬件后，需要让用户程序能访问它。常见的几种方式：

方式适用特点
misc 字符设备 + file_operations需要 read/write/ioctl 的自定义设备自动创建 /dev/xxx，最通用
sysfs 属性简单的配置项和状态（开关、阈值、版本）用 cat / echo 即可访问，调试方便
接入内核子系统输入设备、传感器（IIO）、LED、PWM、网络用户态使用标准工具和接口，无需自定义协议
 
static ssize_t mydev_read(struct file *f, char __user *buf, size_t len, loff_t *off)
{
    struct mydev *md = container_of(f->private_data, struct mydev, misc);
    u32 val = readl(md->base + REG_DATA);

    if (len < sizeof(val))
        return -EINVAL;
    if (copy_to_user(buf, &val, sizeof(val)))    /* 内核与用户空间之间必须用专用函数拷贝 */
        return -EFAULT;
    return sizeof(val);
}

static const struct file_operations mydev_fops = {
    .owner = THIS_MODULE,
    .read  = mydev_read,
    .unlocked_ioctl = mydev_ioctl,
};

几个铁律：不能直接解引用用户空间指针，必须用 copy_to_user / copy_from_user；寄存器访问用 readl / writel；能接入现有子系统的设备优先接入子系统，而不是自己发明 ioctl 协议。

5. 中断处理：上半部与下半部

Linux 中断处理分为两部分：

  • 上半部（硬中断）：在中断上下文中运行，不能睡眠，要尽快完成，通常只读取状态、清除中断。
  • 下半部：耗时的处理放到可以睡眠的上下文中。最常用的是线程化中断（request_threaded_irq 的 thread_fn），在内核线程中运行，可以调用 I2C 读写等会睡眠的函数。

挂在 I2C、SPI 总线上的设备，其中断处理需要通过总线读写寄存器，而总线访问会睡眠，所以必须使用线程化中断（handler 传 NULL，并设置 IRQF_ONESHOT），如上面 probe 中的写法。

6. 并发与同步

驱动可能被多个进程同时打开、同时调用，还要和中断处理并发：

机制能否睡眠适用
mutex持有期间可以睡眠进程上下文之间的互斥，例如两个进程同时 ioctl
spinlock（spin_lock_irqsave）持有期间不能睡眠与中断处理共享的数据
原子变量 atomic_t—简单的计数和标志
等待队列 wait_queue—read 阻塞等待数据到来，由中断唤醒
completion—等待某个一次性事件完成（如一次传输结束）

7. 工作场景：从设备树到用户程序的调试链路

驱动“不工作”时，按启动链路逐层确认：

  1. 设备树是否生效：ls /proc/device-tree/ 下能否找到对应节点，cat /proc/device-tree/.../compatible 是否正确（确认烧录的是新编译的 DTB）。
  2. 驱动是否加载：lsmod、ls /sys/bus/platform/drivers/ 中能否找到驱动名。
  3. probe 是否成功：dmesg | grep mydev 查看日志；ls /sys/bus/platform/devices/ 中设备的 driver 链接是否存在；cat /sys/kernel/debug/devices_deferred 查看是否卡在延迟 probe。
  4. 资源是否正确：cat /proc/interrupts 中断计数是否增长，cat /proc/iomem 寄存器区域是否被申请。
  5. 用户接口：/dev/mydev 是否存在、权限是否正确，用一个最小的测试程序读写验证。

更多内核与驱动调试手段，见 嵌入式 Linux 驱动与系统调试。

8. 驱动开发检查清单

  • 是否确认过内核中没有可用的现成驱动，用户态方案是否无法满足。
  • 设备树节点的 compatible、reg、interrupts、status 是否正确，驱动匹配表是否一致。
  • probe 是否使用 devm_ 接口管理资源，依赖未就绪时是否用 dev_err_probe 处理延迟 probe。
  • 用户空间数据是否通过 copy_to_user / copy_from_user 访问，寄存器是否用 readl / writel。
  • 总线设备的中断是否使用线程化中断，上半部是否足够短。
  • 多进程访问和中断共享的数据是否有正确的锁，持有自旋锁时是否没有睡眠。
  • 能接入现有子系统（IIO、input、LED、PWM）的设备是否优先接入子系统。
