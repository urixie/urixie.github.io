嵌入式 Linux 驱动与系统调试

嵌入式 Linux 调试通常横跨内核、设备树、驱动、用户态程序、文件系统和启动脚本。本文按工程排错视角整理常见入口：串口日志、dmesg、设备树、设备节点、sysfs/procfs、内核模块、交叉编译和 gdbserver。

调嵌入式 Linux 不要一上来就改代码。先确认硬件连线、设备树是否生效、驱动是否匹配、设备节点是否创建、权限是否正确、用户程序打开路径是否正确。

1. 启动日志与串口控制台

串口日志是嵌入式 Linux 最重要的第一现场。U-Boot、内核启动、驱动 probe.rootfs 挂载、systemd 启动都可以从串口看到线索。 

dmesg
cat /proc/cmdline
cat /proc/version
uname -a

如果系统无法启动，优先保留完整串口日志；如果系统已经启动，优先用 dmesg 查看内核日志。

2. 设备树调试

设备树描述硬件资源，例如 GPIO、I2C、SPI、UART、中断、时钟、电源和 pinctrl。驱动能否 probe 成功，很多时候取决于设备树节点是否正确。 

ls /proc/device-tree
find /proc/device-tree -name "*spi*"
hexdump -C /proc/device-tree/model

常见问题包括 compatible 不匹配、pinctrl 未配置、GPIO 极性错误、中断号错误、status 没有设为 okay。

3. 驱动 probe 与 dmesg

驱动加载后会根据 compatible、总线类型或设备 ID 匹配设备。匹配成功后执行 probe。probe 失败时，通常会在 dmesg 中留下错误码。

dmesg | grep -i spi
dmesg | grep -i i2c
dmesg | grep -i error

如果用户态找不到设备，先确认驱动是否 probe，再确认设备节点是否创建，最后确认权限和应用路径。

4. 设备节点与 sysfs

Linux 中很多设备会在 /dev 下生成节点，例如串口、SPI、I2C、输入设备等。/sys 则可以查看设备、驱动、总线和类的关系。

ls -l /dev/ttyS*
ls -l /dev/spidev*
ls /sys/class
ls /sys/bus/platform/devices
ls /sys/bus/spi/devices

5. 内核模块

如果驱动编译成模块，可以使用 insmod、rmmod、lsmod 调试加载和卸载。

insmod my_driver.ko
lsmod
rmmod my_driver
dmesg | tail -n 80

模块加载失败时，要检查内核版本、符号依赖、设备树匹配和模块参数。

6. 交叉编译与部署

嵌入式 Linux 用户程序通常在 PC 上交叉编译，再拷贝到板子运行。常见问题是工具链架构不匹配、动态库缺失、运行权限不够。

file app
readelf -h app
ldd app
scp app root@192.168.1.10:/opt/app/

如果目标板没有 ldd，可以用 readelf -d 查看依赖库。

7. 用户态调试：strace 与 gdbserver

strace 用来跟踪系统调用，gdbserver 用来远程调试程序。文件打不开、设备打不开、权限问题，优先用 strace；崩溃和逻辑错误，可以用 gdbserver。

strace -o trace.log ./app

gdbserver :2345 ./app
# PC 端：
# target remote 192.168.1.10:2345

8. 常见排查路径

现象排查路径
设备节点不存在设备树 status / compatible / 驱动 probe / udev 或 mdev

9. 动态调试：打开驱动中的 pr_debug

驱动中的 pr_debug() / dev_dbg() 默认不输出。开启 CONFIG_DYNAMIC_DEBUG 后，可以在运行时按文件、函数、模块打开：

mount -t debugfs none /sys/kernel/debug 2>/dev/null

# 打开某个模块的所有调试输出（+p 打印，+f 带函数名，+l 带行号）
echo 'module xyj_sensor +pfl' > /sys/kernel/debug/dynamic_debug/control
# 打开某个源文件
echo 'file drivers/spi/spi-rockchip.c +p' > /sys/kernel/debug/dynamic_debug/control
# 查看当前状态
grep xyj_sensor /sys/kernel/debug/dynamic_debug/control

# 启动阶段的驱动：通过内核命令行打开
#   dyndbg="module xyj_sensor +p"  或  xyj_sensor.dyndbg=+p

同时把控制台日志级别调高（dmesg -n 8），或直接用 dmesg -w 实时查看。

10. ftrace：看清内核里发生了什么

ftrace 是内核自带的跟踪框架，不需要额外工具，适合分析“驱动函数有没有被调用”“中断处理耗时多少”：

cd /sys/kernel/debug/tracing        # 新内核也可以使用 /sys/kernel/tracing

# 跟踪某个函数调用关系
echo xyj_sensor_read > set_graph_function
echo function_graph > current_tracer
echo 1 > tracing_on; sleep 2; echo 0 > tracing_on
cat trace | head -50

# 使用内核预置的事件：观察 I2C 传输与中断
echo 1 > events/i2c/enable
echo 1 > events/irq/irq_handler_entry/enable
cat trace_pipe

function_graph 会显示每个函数的耗时，能直接定位驱动中的慢路径。主机上安装 trace-cmd / KernelShark 可以更方便地录制和图形化查看。

11. perf：用户态和内核态的性能分析

perf top -p $(pidof gateway)          # 实时查看热点函数
perf record -g -p $(pidof gateway) -- sleep 10
perf report                           # 按调用栈分析 CPU 占用
perf stat -e cycles,instructions,cache-misses ./algo_test

交叉编译环境下，perf 需要与目标内核版本匹配（Buildroot 中启用 BR2_PACKAGE_LINUX_TOOLS_PERF）。要得到完整调用栈，被分析程序需要保留帧指针（-fno-omit-frame-pointer）或调试信息。

12. 外设总线调试

驱动或应用访问外设失败时，先区分是软件问题还是总线 / 硬件问题：

总线软件侧工具硬件侧手段
I2Ci2cdetect -y N、i2cget、i2cdump、i2c ftrace 事件逻辑分析仪看 START / ACK / NACK，检查上拉电阻
SPIspidev 测试程序（spidev_test）、设备树中的模式与频率逻辑分析仪看 CS、时钟极性与相位
UARTstty -F /dev/ttyS3 -a、microcom、回环测试示波器量波特率、电平（TTL / RS232 / RS485）
GPIOgpioinfo、gpioget、/sys/kernel/debug/gpio万用表 / 示波器确认电平
pinctrl/sys/kernel/debug/pinctrl/*/pinmux-pins对照原理图确认引脚复用

用户态访问方法见 用户态访问外设，驱动的 probe 流程见 字符设备驱动。pinmux-pins 能直接看到每个引脚当前被哪个设备占用，是排查引脚冲突最快的方法。

13. 网络问题排查

ip -br addr; ip route; ip neigh               # 地址、路由、ARP
ss -tunap                                     # 连接与监听端口，以及对应进程
ethtool eth0                                  # 链路速率、双工、是否 link up
ethtool -S eth0 | grep -i -E 'err|drop'       # 网卡统计中的错误与丢包
tcpdump -i eth0 -nn port 1883 -w /tmp/mqtt.pcap   # 抓包后拷回电脑用 Wireshark 分析
ping -I eth0 -c 4 192.168.1.1

排查顺序：物理链路（ethtool）→ IP 与路由 → DNS → 连接建立（ss、tcpdump）→ 应用协议。多网口设备（以太网 + 4G + Wi-Fi）要特别注意默认路由和路由优先级（metric）。

14. 启动时间分析

dmesg | head -1 ; dmesg | tail -1             # 内核时间戳范围
systemd-analyze                               # kernel / userspace 各阶段耗时
systemd-analyze blame | head -20
systemd-analyze critical-chain
# 内核阶段：命令行加 initcall_debug，再按耗时排序
dmesg | grep 'initcall' | sort -t' ' -k8 -n | tail

常见优化：减少 U-Boot 等待时间（bootdelay），内核去掉不需要的驱动或改为模块，延迟加载非关键驱动，rootfs 使用 squashfs，用户态服务并行启动、非关键服务延后启动。

15. 工作场景：SPI 设备读回全是 0xFF

  1. 确认设备节点：ls /dev/spidev* 存在，dmesg 无 probe 错误。
  2. 确认引脚复用：查看 pinmux-pins，发现 SPI 的 MISO 引脚被 UART 占用，设备树中两个节点使用了同一组引脚。
  3. 修正设备树：禁用冲突的 UART 节点，重新编译 DTB。
  4. 复测：数据仍然偶尔出错。逻辑分析仪显示时钟极性与器件要求不一致，把 spi-cpol / spi-cpha（或应用中的 SPI_MODE_x）改为器件手册要求的模式。
  5. 验证余量：把时钟频率从 10MHz 降到 5MHz 对比误码率，确认最终频率有足够余量。
  6. 记录：把引脚分配、SPI 模式和频率写入板级文档，避免下一块板重复踩坑。

16. 工程检查清单

  • 设备树节点是否实际进入运行系统。
  • compatible 是否和驱动匹配。
  • dmesg 中是否有 probe 成功或失败信息。
  • 设备节点是否创建，权限是否正确。
  • 用户程序打开路径是否与设备节点一致。
  • 应用架构和动态库是否匹配目标板。
  • 问题是否能通过 strace.gdbserver 或串口日志复现。
  • 内核是否开启 CONFIG_DYNAMIC_DEBUG、ftrace 等调试能力（至少在调试版中）。
  • 外设访问失败时，是否先用 pinmux、总线工具和逻辑分析仪区分软件与硬件问题。
  • 性能问题是否用 perf / ftrace 定位热点，而不是凭感觉优化。
  • 网络问题是否按物理链路、IP 路由、DNS、连接、应用协议的顺序排查。
  • 启动时间是否用 systemd-analyze 和 initcall_debug 量化分析过。
