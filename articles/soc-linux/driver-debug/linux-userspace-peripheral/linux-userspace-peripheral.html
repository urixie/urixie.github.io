Linux 用户态访问外设：GPIO、I2C、SPI 与串口

整理 libgpiod、i2c-dev、spidev 与 termios 的用法和坑点，以及用 poll/epoll 组织多外设应用程序的方法。

1. 用户态访问外设的适用范围

很多嵌入式 Linux 项目中的外设操作并不需要写内核驱动：控制几个 GPIO、读一个 I2C 温度传感器、和一个 SPI ADC 通信、通过串口与 MCU 交换数据，在用户态都能完成。用户态方案的好处是开发调试快（程序崩溃不会导致内核崩溃）、升级方便、可以使用各种语言。

外设用户态接口内核需要
GPIO/dev/gpiochipN + libgpiodGPIO 控制器驱动（SoC 自带）
I2C/dev/i2c-NCONFIG_I2C_CHARDEV
SPI/dev/spidevB.CCONFIG_SPI_SPIDEV + 设备树 spidev 节点
UART/dev/ttyS*、/dev/ttyUSB*串口驱动
PWM/sys/class/pwm/PWM 控制器驱动 + 设备树启用

需要毫秒以下的严格实时响应、需要 DMA 或高频中断时，用户态方案会力不从心，这时应考虑内核驱动，见 Linux 字符设备驱动开发。

2. GPIO：使用 libgpiod，而不是 sysfs

老资料中常见的 /sys/class/gpio/export 接口已经被标记为废弃，新内核中可能不再启用。推荐使用字符设备接口和 libgpiod 库：

gpiodetect                         # 列出 GPIO 控制器：gpiochip0 [ff720000.gpio] (32 lines)
gpioinfo gpiochip1                 # 查看每条线的名称、方向、是否被占用
gpioset gpiochip1 5=1              # 设置 GPIO1_A5 为高电平（libgpiod 1.x 语法）
gpioget gpiochip1 6                # 读取电平
gpiomon gpiochip1 6                # 监听边沿事件

libgpiod 1.x 与 2.x 的命令行参数和 C API 差异较大，使用前用 gpioset --version 确认版本，参照对应版本的文档。

引脚编号换算：Rockchip 平台上 GPIO1_A5 表示 gpiochip1 的第 5 号线（A=0~7、B=8~15、C=16~23、D=24~31），即 1 × 32 + 5 = 37 是旧 sysfs 接口中的全局编号。不同 SoC 的命名规则不同，以 gpioinfo 输出和原理图为准。

使用 libgpiod 的另一个好处是：程序退出时 GPIO 会被自动释放，同一条 GPIO 也不会被两个程序同时申请。

3. I2C：/dev/i2c-N

#include <linux/i2c-dev.h>
#include <sys/ioctl.h>
#include <fcntl.h>

int i2c_read_reg(const char *bus, uint8_t addr, uint8_t reg, uint8_t *buf, size_t len)
{
    int fd = open(bus, O_RDWR);                 /* 例如 "/dev/i2c-1" */
    if (fd < 0) return -1;

    struct i2c_msg msgs[2] = {
        { .addr = addr, .flags = 0,        .len = 1,   .buf = &reg },  /* 写寄存器地址 */
        { .addr = addr, .flags = I2C_M_RD, .len = len, .buf = buf  },  /* 重复起始后读取 */
    };
    struct i2c_rdwr_ioctl_data xfer = { .msgs = msgs, .nmsgs = 2 };
    int ret = ioctl(fd, I2C_RDWR, &xfer);
    close(fd);
    return ret < 0 ? -1 : 0;
}

调试工具 i2c-tools 非常有用：i2cdetect -y 1 扫描总线上的设备地址，i2cget / i2cset / i2cdump 直接读写寄存器。注意：i2cdetect 扫描时会向每个地址发送探测，个别器件可能因此进入异常状态；地址显示为 UU 表示该地址已被内核驱动占用。

4. SPI：spidev

spidev 需要在设备树中把 SPI 从设备声明为 spidev（各平台兼容字符串略有不同），之后出现 /dev/spidev0.0 这样的节点。完整的 RK3568 实例见 RK3568 SPI / spidev 调试。

#include <linux/spi/spidev.h>

int spi_transfer(int fd, const uint8_t *tx, uint8_t *rx, size_t len)
{
    struct spi_ioc_transfer tr = {
        .tx_buf        = (unsigned long)tx,
        .rx_buf        = (unsigned long)rx,
        .len           = len,
        .speed_hz      = 1000000,
        .bits_per_word = 8,
    };
    return ioctl(fd, SPI_IOC_MESSAGE(1), &tr);
}

/* 初始化：模式和速率 */
uint8_t mode = SPI_MODE_0;
ioctl(fd, SPI_IOC_WR_MODE, &mode);

一次 SPI_IOC_MESSAGE 调用中，片选在整个传输期间保持有效；需要多段传输共用一次片选时，把多个 spi_ioc_transfer 放进一个数组一起提交。

5. UART：termios 配置

串口是嵌入式 Linux 与 MCU、模组通信最常用的接口。很多问题出在 termios 配置上：默认的“规范模式”会按行缓冲、处理特殊字符，对二进制协议完全不适用。

#include <termios.h>

int serial_open(const char *dev, speed_t baud)
{
    int fd = open(dev, O_RDWR | O_NOCTTY);
    if (fd < 0) return -1;

    struct termios tio;
    tcgetattr(fd, &tio);
    cfmakeraw(&tio);                       /* 原始模式：关闭行缓冲、回显、特殊字符处理 */
    cfsetispeed(&tio, baud);
    cfsetospeed(&tio, baud);
    tio.c_cflag |= (CLOCAL | CREAD);       /* 忽略调制解调器控制线，启用接收 */
    tio.c_cflag &= ~CRTSCTS;               /* 关闭硬件流控（按需开启） */
    tio.c_cc[VMIN]  = 0;                   /* read 不要求最少字节数 */
    tio.c_cc[VTIME] = 1;                   /* 超时 100ms：没有数据时 read 返回 0 */
    tcsetattr(fd, TCSANOW, &tio);
    tcflush(fd, TCIOFLUSH);
    return fd;
}
  • 一次 read 不等于一帧：串口数据可能被拆成多次 read 返回，也可能一次 read 读到多帧。应用层必须自己组帧（帧头、长度、校验），思路与 MCU 上的 环形缓冲区按帧提取 相同。
  • USB 转串口的设备名会变：/dev/ttyUSB0 和 ttyUSB1 的顺序取决于枚举顺序，产品中应使用 udev 规则或 /dev/serial/by-id/ 下的固定名称。
  • 权限：普通用户访问串口需要加入 dialout 组。

6. 事件驱动：poll / epoll

同时处理多个串口、GPIO 事件、网络连接时，不要为每个设备开一个死循环线程，而是用 poll / epoll 统一等待：

struct pollfd fds[2] = {
    { .fd = uart_fd,   .events = POLLIN },
    { .fd = button_fd, .events = POLLIN },     /* libgpiod 的边沿事件也可以通过 fd 等待 */
};
for (;;) {
    int n = poll(fds, 2, 1000);                /* 1 秒超时，用于周期任务 */
    if (n == 0) { periodic_work(); continue; }
    if (fds[0].revents & POLLIN) handle_uart(uart_fd);
    if (fds[1].revents & POLLIN) handle_button(button_fd);
}

7. 工作场景：Linux 主控与 MCU 协处理器通信

常见架构：Linux SoC 负责网络、界面、存储，MCU 负责实时控制和采集，两者通过 UART（或 SPI）通信。

  1. 硬件：确认电平匹配（1.8V / 3.3V），保留一根 GPIO 让 Linux 能复位 MCU，另一根作为 MCU 的“数据就绪”中断。
  2. 协议：帧头 + 长度 + 命令 + 数据 + CRC，带序号和应答，见 结构体与数据组织。
  3. Linux 侧程序：原始模式打开串口，epoll 同时等待串口数据和 GPIO 事件，收到数据后组帧、校验、分发。
  4. 服务化：以 systemd 服务运行，异常退出自动重启，日志进入 journald，见 Shell 脚本与 systemd 服务。
  5. MCU 升级：Linux 通过同一串口给 MCU 下发固件，MCU 侧 Bootloader 负责接收，见 MCU Bootloader 与固件升级。

8. 用户态外设访问检查清单

  • 外设是否适合在用户态访问，实时性和性能要求是否满足。
  • GPIO 是否使用 libgpiod 字符设备接口，命令语法是否与 libgpiod 版本对应。
  • I2C 是否用 i2cdetect 确认地址，读寄存器是否使用带重复起始的 I2C_RDWR。
  • spidev 节点是否出现，SPI 模式、速率、片选行为是否与器件一致。
  • 串口是否设置为原始模式，VMIN / VTIME 是否符合需求，应用层是否自行组帧。
  • USB 转串口是否使用固定的设备名，程序运行用户是否有设备权限。
  • 多个设备是否用 poll / epoll 统一处理，程序是否以服务方式运行并能自动恢复。
