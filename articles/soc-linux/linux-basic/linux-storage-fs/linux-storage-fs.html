嵌入式 Linux 存储与文件系统

对比 NOR、NAND、eMMC 等存储介质与 ext4、squashfs、UBIFS 等文件系统，说明分区规划、只读根文件系统与掉电安全写文件的方法。

1. 嵌入式存储介质怎么选

嵌入式 Linux 设备的存储方案决定了文件系统选择、升级方式和掉电可靠性，项目早期就要定下来：

介质特点坏块 / 磨损管理常用文件系统典型场景
SPI NOR容量小（16~64MB），可靠、读快写慢无坏块，擦写约 10 万次squashfs + JFFS2 / UBIFS小型网关、只读系统
裸 NAND（SLC/MLC）容量中等，便宜，有坏块需要软件（MTD + UBI）管理UBIFS、squashfs over UBI工控、老平台
SPI NAND引脚少，容量 128MB~1GB同裸 NAND，片内 ECCUBIFS中低端网关、IPC
eMMC内置控制器，块设备接口控制器内部完成ext4、squashfs、f2fsRK3568 / i.MX 等主流板卡
SD 卡可拔插、便于调试控制器内部完成，质量参差ext4、FAT（启动分区）开发调试、数据记录

关键区别是：NOR / NAND 是 MTD 设备（/dev/mtdN），需要用懂擦除块的文件系统；eMMC / SD 是块设备（/dev/mmcblkN），可以直接使用 ext4 等通用文件系统。把 ext4 直接放在裸 NAND 上是错误用法。

2. 分区规划

以 eMMC 为例，一个支持 A/B 升级的典型分区表：

分区大小内容挂载方式
bootloader4~8MBSPL / U-Boot（部分 SoC 放在固定偏移）不挂载
env64KB~1MBU-Boot 环境变量（建议双份冗余）不挂载
boot_a / boot_b32~64MBKernel、DTB（FIT 镜像）不挂载或只读
rootfs_a / rootfs_b512MB~2GB只读根文件系统只读
data剩余空间配置、日志、用户数据读写

规划原则：

  • 系统与数据分离：rootfs 只读、data 读写，升级只替换系统分区，不碰用户数据。
  • 日志有上限：日志写入 data 分区并配置轮转，防止写满分区导致应用写配置失败。
  • 预留余量：rootfs 分区至少预留 30% 以上空间，后续版本增加功能不需要重新分区（重新分区意味着现场设备无法 OTA）。

查看分区与挂载状态的常用命令：

lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT,LABEL   # 块设备与分区
cat /proc/mtd                                # MTD 分区（NOR / NAND）
cat /proc/partitions
findmnt                                      # 挂载树，包含挂载选项
df -h; df -i                                 # 空间与 inode 使用率

3. 常用文件系统对比

文件系统类型掉电安全特点
squashfs只读、压缩只读，天然安全体积小（xz/zstd 压缩），适合 rootfs
ext4块设备读写日志保护元数据通用、工具齐全，eMMC 首选读写文件系统
f2fs块设备读写检查点机制针对闪存优化，对写放大更友好
UBIFSMTD 读写日志结构，掉电安全运行在 UBI 之上，NAND 首选
JFFS2MTD 读写掉电安全老方案，大容量下挂载慢，新项目优先 UBIFS
tmpfs内存掉电丢失/tmp、/run、运行时缓存
vfat块设备不安全启动分区、与 Windows 交换数据
ext4 的日志默认只保护元数据（data=ordered），不保证文件内容完整。应用写配置文件时仍然要用“写临时文件 + fsync + rename”的方式，见下文。

4. NAND 上的 MTD 与 UBI

裸 NAND 有坏块、需要 ECC 和磨损均衡，Linux 的分层是：

UBIFS（文件系统）
  └─ UBI 卷（ubi0:rootfs、ubi0:data ...）  磨损均衡、坏块管理、逻辑擦除块映射
      └─ MTD 分区（/dev/mtd3）             原始擦除 / 读写接口
          └─ NAND 控制器驱动 + ECC

制作和挂载 UBI 卷的典型步骤：

# 主机端：用 ubinize 把 UBIFS 镜像打包成 UBI 镜像（参数必须与 NAND 页大小、擦除块大小匹配）
mkfs.ubifs -r rootfs/ -m 2048 -e 126976 -c 2048 -o rootfs.ubifs
ubinize -o rootfs.ubi -m 2048 -p 128KiB ubinize.cfg

# 设备端：附加 MTD 分区、挂载数据卷
ubiattach /dev/ubi_ctrl -m 4
ubinfo -a                         # 查看卷与坏块、最大擦写次数
mount -t ubifs ubi0:data /data

-m（最小写入单元，即页大小）、-e（逻辑擦除块大小）、-p（物理擦除块大小）必须与芯片一致，参数错误时会出现挂载失败或 “bad VID header” 一类错误。更换 NAND 型号时要重点核对这些参数。

5. 只读 RootFS 与 overlayfs

只读 rootfs 的好处：掉电不会损坏系统、所有设备的系统分区内容一致、问题容易复现。但一些程序需要写 /etc、/var，常用的处理方式：

  • /tmp、/run、/var/log（或 /var/volatile）挂载为 tmpfs。
  • 需要持久化的配置放在 data 分区，/etc 中对应文件改为软链接。
  • 或者使用 overlayfs：只读的 rootfs 作为下层，data 分区上的目录作为可写上层，合并后对应用透明。
# 把 /etc 做成 overlay：下层只读，上层与工作目录在 data 分区（必须在同一文件系统）
mkdir -p /data/overlay/etc/upper /data/overlay/etc/work
mount -t overlay overlay \
  -o lowerdir=/etc,upperdir=/data/overlay/etc/upper,workdir=/data/overlay/etc/work /etc
overlayfs 的上层保存的是“与出厂不同的文件”，系统升级后旧的上层文件会覆盖新版本 rootfs 中的同名文件，可能导致新版本配置不生效。升级流程中要明确：哪些上层文件需要保留、哪些需要清除。

6. 掉电安全：应用层怎么写文件

文件系统只能保证自身结构不损坏，应用数据是否完整由应用负责。写配置、写计数等关键数据的标准做法：

/* 原子替换：要么是旧文件，要么是新文件，不会出现写了一半的文件 */
int save_config_atomic(const char *path, const void *buf, size_t len)
{
    char tmp[256];
    snprintf(tmp, sizeof(tmp), "%s.tmp", path);

    int fd = open(tmp, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return -1;
    if (write(fd, buf, len) != (ssize_t)len || fsync(fd) != 0) {   /* 数据落盘 */
        close(fd);
        unlink(tmp);
        return -1;
    }
    close(fd);
    if (rename(tmp, path) != 0) return -1;                          /* 原子替换 */

    /* 同步目录项，保证 rename 本身也已落盘 */
    char dir[256];
    snprintf(dir, sizeof(dir), "%s", path);
    char *slash = strrchr(dir, '/');
    if (slash) *slash = '\0';
    int dfd = open(slash ? dir : ".", O_RDONLY | O_DIRECTORY);
    if (dfd >= 0) { fsync(dfd); close(dfd); }
    return 0;
}

其他要点：

  • 关键数据再加一层校验（CRC + 版本号），读取时校验失败则回退到备份或默认值。
  • 不要频繁 sync 整个系统；对单个文件 fsync 即可。
  • 高频写入的数据（如计数、状态）先在内存中合并，定时或在关机流程中写入，降低闪存磨损。

7. 工作场景：设备反复掉电后无法启动

现象：现场设备在频繁断电后出现无法启动、配置丢失或 EXT4-fs error 日志。排查与改进路径：

  1. 看串口日志：确认是 rootfs 挂载失败、文件系统检查失败，还是应用读到损坏的配置后异常退出。
  2. 检查挂载方式：rootfs 是否以读写方式挂载？如果是，改为只读（squashfs 或 ext4 ro），可写内容迁移到 data 分区。
  3. data 分区自修复：启动脚本中对 data 分区执行 fsck 或挂载失败时重新格式化并恢复默认配置，保证设备至少能启动。
  4. 应用写文件改为原子替换，并为关键配置增加校验和双份备份。
  5. 评估介质健康：eMMC 可以通过 mmc extcsd read /dev/mmcblk0 查看寿命估计字段（EXT_CSD_DEVICE_LIFE_TIME_EST），NAND 通过 ubinfo 查看最大擦写计数。
  6. 硬件侧：评估是否需要掉电检测 + 储能电容，在掉电前给系统留出几十毫秒写完关键数据。

8. 存储与文件系统检查清单

  • 存储介质类型（MTD 或块设备）是否明确，文件系统选择是否匹配介质。
  • 分区表是否区分系统分区与数据分区，rootfs 是否预留了足够的升级余量。
  • rootfs 是否只读挂载，需要写入的目录是否由 tmpfs、data 分区或 overlayfs 提供。
  • NAND / UBI 参数（页大小、擦除块大小）是否与芯片一致，更换物料时是否复核。
  • 关键文件是否使用“临时文件 + fsync + rename”的原子写入，并带有校验。
  • 日志是否有轮转与上限，data 分区写满时系统能否正常运行。
  • data 分区损坏时是否有自修复或恢复出厂配置的路径。
  • 是否在掉电测试中反复验证过（数百次以上随机断电）。
