Linux 进程、线程与内存管理

Linux 应用程序运行后就是进程。每个进程都有自己的虚拟地址空间、文件描述符、信号处理方式和线程集合。嵌入式 Linux 上的很多崩溃、卡死、资源泄漏和性能问题，都可以从进程、线程、内存和文件描述符这几个角度定位。

1. 进程与线程

进程是资源分配单位，线程是执行单位。同一个进程内的多个线程共享地址空间、全局变量、堆和文件描述符，但每个线程有自己的栈和调度上下文。

2. 查看进程状态

ps aux
ps -ef
top
htop
pidof app
cat /proc/$(pidof app)/status

常见关注点包括 CPU 占用、内存占用、进程状态、线程数量、打开文件数和启动参数。嵌入式板子上如果没有 htop，通常至少会有 BusyBox 的 top 和 ps。

3. 虚拟内存与 maps

Linux 进程访问的是虚拟地址。/proc/<pid>/maps 可以看到当前进程的地址空间布局，包括代码段、堆、栈、动态库和 mmap 区域。 

cat /proc/1234/maps
cat /proc/1234/smaps
pmap 1234

如果程序发生段错误，maps 可以帮助判断出错地址落在哪个区域：是空指针、堆、栈、动态库，还是未映射区域。

4. 文件描述符

Linux 中打开文件、串口、socket、管道、设备节点，都会占用文件描述符。长期运行程序如果忘记关闭文件或 socket，就可能出现资源泄漏。 

ls -l /proc/1234/fd
ls /proc/1234/fd | wc -l
ulimit -n

如果程序运行一段时间后打开文件失败、socket 创建失败，应检查文件描述符数量是否持续增长。

5. 信号与进程退出

信号是 Linux 进程间异步通知机制。常见信号包括 SIGINT、SIGTERM、SIGKILL、SIGSEGV、SIGABRT。 

kill -TERM 1234
kill -9 1234
trap 'echo exit' INT TERM

SIGTERM 可以被程序捕获并做清理，SIGKILL 不能被捕获。服务程序应尽量处理 SIGTERM，释放资源后退出。

6. strace 跟踪系统调用

strace 可以跟踪进程的系统调用，非常适合定位文件打不开、权限不足、设备节点不存在、网络连接失败等问题。 

strace ./app
strace -p 1234
strace -o trace.log ./app

例如程序提示“打开设备失败”，用 strace 可以看到它实际打开的是哪个路径，以及内核返回了什么错误码。

7. core dump 与 gdb

程序崩溃后保留 core dump，可以用 gdb 查看崩溃调用栈、局部变量、寄存器和内存。 

ulimit -c unlimited
./app

gdb ./app core
(gdb) bt
(gdb) frame 0
(gdb) info locals
(gdb) x/32gx $sp

嵌入式 Linux 上如果 rootfs 空间较小，需要配置 core 文件路径，避免 core 文件把系统分区写满。

8. 多线程编程要点

嵌入式 Linux 应用常见的结构是“一个进程、多个线程”：通信线程、采集线程、业务线程、日志线程。pthread 的基本用法：

#include <pthread.h>

static pthread_mutex_t g_lock = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  g_cond = PTHREAD_COND_INITIALIZER;
static int g_ready;

static void *worker(void *arg)
{
    pthread_mutex_lock(&g_lock);
    while (!g_ready)                         /* 必须用 while：防止虚假唤醒 */
        pthread_cond_wait(&g_cond, &g_lock); /* 等待时自动释放锁，被唤醒后重新加锁 */
    pthread_mutex_unlock(&g_lock);
    /* ... 处理数据 ... */
    return NULL;
}

int main(void)
{
    pthread_t tid;
    pthread_create(&tid, NULL, worker, NULL);
    pthread_setname_np(tid, "worker");       /* 便于 top -H / gdb 中识别线程 */

    pthread_mutex_lock(&g_lock);
    g_ready = 1;
    pthread_cond_signal(&g_cond);
    pthread_mutex_unlock(&g_lock);

    pthread_join(tid, NULL);
    return 0;
}

工程要点：

  • 给线程命名：top -H -p <pid> 和 gdb 的 info threads 中可以直接看到线程名，定位 CPU 占用高的线程非常方便。
  • 锁的粒度：锁只保护共享数据，不要在持锁期间做阻塞 IO（读串口、网络发送、写文件）。
  • 加锁顺序：需要同时持有多把锁时，所有线程按相同顺序加锁，避免死锁。
  • 线程退出：要么 pthread_join 回收，要么 pthread_detach，否则线程资源不会释放。
  • 编译时加 -pthread，调试数据竞争时可以用 -fsanitize=thread（需要工具链支持）。

9. 进程间通信怎么选

方式特点适用
管道 / FIFO简单，单向字节流父子进程、脚本与程序之间
Unix 域套接字双向、可传文件描述符、支持多客户端本机服务与客户端（最常用）
共享内存 + 信号量速度最快，需要自行同步视频帧、大块采样数据
消息队列（POSIX mq）带消息边界、可设优先级小消息、多生产者
D-Bus标准化、有工具支持与系统服务（NetworkManager、BlueZ）交互
TCP / MQTT 本地回环与远程通信接口统一进程以后可能分布到多台设备

嵌入式设备中最推荐 Unix 域套接字：它是本机通信的通用方案，客户端断开时服务端能感知（读到 0 或 EPIPE），比共享内存更容易做到健壮。

10. 内存使用分析：RSS、PSS 与泄漏

top 中的内存数字经常被误读：

指标含义
VSZ / VIRT虚拟地址空间大小，包含未实际使用的映射，参考意义有限
RSS / RES实际驻留在物理内存中的页，共享库的页会被每个进程重复计算
PSS共享页按共享进程数平摊后的值，加总接近真实占用
USS进程独占的页，进程退出后能释放的内存
 
cat /proc/<pid>/status | grep -E 'VmRSS|VmHWM|Threads'   # VmHWM：RSS 峰值
cat /proc/<pid>/smaps_rollup                             # Pss、Private_Dirty 汇总（4.14+ 内核）
free -h                                                   # 关注 available，而不是 free
cat /proc/meminfo | grep -E 'MemAvailable|Slab|CmaFree'

判断内存泄漏：长时间（几小时到几天）定时记录 VmRSS 或 Pss，持续单调上涨且不回落就是可疑泄漏。定位方法：

  • 开发阶段在 x86 主机上用 Valgrind 或 AddressSanitizer（-fsanitize=address）跑单元测试和模拟场景。
  • 在目标板上可以用 heaptrack、glibc 的 mtrace，或在自己的内存分配封装中统计分配次数和大小。
free 显示 free 很少通常不是问题：Linux 会把空闲内存用作页缓存，需要时再回收。判断内存是否紧张应看 MemAvailable。

11. OOM 与内存不足时的行为

物理内存耗尽时，内核的 OOM killer 会根据 oom_score 选择一个进程杀掉。嵌入式设备上要主动控制：

dmesg | grep -i -E 'oom|killed process'        # 查看是否发生过 OOM
cat /proc/<pid>/oom_score                       # 当前得分
echo -1000 > /proc/<pid>/oom_score_adj          # 关键进程：基本不会被选中

systemd 服务中可以用 OOMScoreAdjust= 设置，并用 MemoryMax= 限制某个非关键服务的内存上限，让它在超限时被单独处理，而不是拖垮整个系统。

12. 实时性：调度策略与 CPU 绑定

普通线程使用 SCHED_OTHER（CFS）调度，时延不确定。对时延敏感的线程（控制环、高速采集）可以：

struct sched_param sp = { .sched_priority = 50 };      /* SCHED_FIFO 优先级 1~99 */
pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp); /* 需要 root 或 CAP_SYS_NICE */

cpu_set_t set;
CPU_ZERO(&set);
CPU_SET(3, &set);                                       /* 绑定到 CPU3 */
pthread_setaffinity_np(pthread_self(), sizeof(set), &set);

mlockall(MCL_CURRENT | MCL_FUTURE);                     /* 锁定内存，避免缺页导致的延迟 */

注意 SCHED_FIFO 线程如果死循环不让出 CPU，会饿死同核上的其他任务。标准内核的调度延迟通常在几十微秒到毫秒级；需要更确定的时延时，考虑 PREEMPT_RT 补丁（6.12 起已合入主线）或把硬实时部分交给 MCU / 协处理器。用 cyclictest 可以测量实际调度延迟。

13. 工作场景：应用运行几天后变慢、最终被杀

  1. dmesg 中发现 Out of memory: Killed process xxx，确认是 OOM。
  2. 部署脚本每 10 分钟记录主程序的 VmRSS 和线程数，发现 RSS 每小时增长约 2MB，线程数稳定。
  3. 在主机上用 AddressSanitizer 回放通信报文，发现协议解析失败的分支中漏了 free。
  4. 修复后长时间运行，RSS 稳定在固定范围；同时给主程序设置 OOMScoreAdjust=-500，给日志上传服务设置 MemoryMax=32M。
  5. 加入运行时监控：内存超过阈值时上报告警，而不是等到被杀才发现。

14. 工程检查清单

  • 进程是否还活着，PID 是否变化。
  • CPU 占用是否异常。
  • 线程数和文件描述符数量是否持续增长。
  • /proc/<pid>/maps 是否能定位异常地址区域。
  • 崩溃后是否保留 core dump。
  • 文件、设备、socket 失败是否用 strace 验证。
  • 退出信号是否能触发资源清理。
  • 线程是否命名，持锁期间是否避免了阻塞 IO，多把锁是否有统一的加锁顺序。
  • 本机进程间通信是否优先使用 Unix 域套接字，对端断开时能否正确处理。
  • 是否长时间记录 RSS / PSS 判断内存泄漏，并在主机上用 ASan / Valgrind 验证。
  • 关键进程是否设置了 oom_score_adj，非关键服务是否限制了内存上限。
  • 实时线程是否合理设置调度策略、CPU 绑定和内存锁定，并用 cyclictest 实测延迟。
