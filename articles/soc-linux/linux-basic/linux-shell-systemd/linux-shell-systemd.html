Linux Shell 脚本与 systemd 服务

Linux 工程中，Shell 脚本经常用于自动构建、部署、启动、日志收集和环境检查。systemd 则常用于把应用程序做成系统服务，实现开机自启、异常重启、日志统一管理和依赖控制。

1. Shell 脚本基础结构

#!/bin/sh

APP_DIR=/opt/app
APP_BIN=$APP_DIR/app

if [ ! -x "$APP_BIN" ]; then
    echo "app not executable: $APP_BIN"
    exit 1
fi

exec "$APP_BIN"

嵌入式系统里常见的是 BusyBox sh，不一定支持完整 Bash 语法。脚本如果要在裁剪系统里运行，建议优先写 POSIX sh 风格。

2. 变量与引号

Shell 中变量替换和空格处理非常容易出错。路径变量建议始终加双引号，避免路径中出现空格或空值导致命令行为异常。 

LOG_DIR="/var/log/my app"
mkdir -p "$LOG_DIR"

echo "log dir: $LOG_DIR"

3. 条件判断与循环

if [ -f /etc/os-release ]; then
    cat /etc/os-release
fi

for dev in /dev/ttyS*; do
    echo "found serial: $dev"
done

while true; do
    date
    sleep 1
done

脚本里不要写没有退出条件的死循环，除非它本来就是守护脚本；即便是守护脚本，也要考虑日志大小、异常退出和信号处理。

4. 重定向与日志

./app > app.log 2>&1
./app >> app.log 2>&1

tail -f app.log

stdout 是标准输出，stderr 是标准错误。2>&1 表示把错误输出也重定向到标准输出。嵌入式设备要注意日志文件大小，避免写满 Flash。

5. set -e 与错误处理

set -e 可以让脚本在命令失败时退出，但它并不是万能的。复杂脚本建议对关键命令显式检查返回值。 

if ! cp app /usr/bin/app; then
    echo "copy app failed"
    exit 1
fi

6. systemd 服务文件

在带 systemd 的 Linux 系统中，可以把应用做成服务。这样可以实现开机启动、异常重启、统一日志和依赖管理。 

[Unit]
Description=My Embedded App
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/app
ExecStart=/opt/app/app
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target

保存为 /etc/systemd/system/myapp.service 后，可以启用服务：

systemctl daemon-reload
systemctl enable myapp
systemctl start myapp
systemctl status myapp

7. journalctl 查看日志

journalctl -u myapp -f
journalctl -u myapp --since "1 hour ago"
journalctl -xe

如果程序通过 systemd 启动，标准输出和标准错误通常会进入 journal。现场排查时，journalctl -u 服务名 -f 非常常用。

8. crontab 与定时任务

crontab -e

# 每天凌晨 3 点执行日志清理
0 3 * * * /opt/app/clean_log.sh

对于周期性维护任务，crontab 很简单；对于长期运行的服务，systemd service 更合适。

9. 嵌入式启动脚本建议

  • 启动前检查配置文件和可执行权限。
  • 日志路径要存在，并限制日志大小。
  • 脚本中使用绝对路径，减少环境变量依赖。
  • 启动失败要打印明确错误原因。
  • 可执行文件升级时，保留版本号和回滚路径。

10. systemd 服务的工程化写法

一个用于量产设备的业务服务，通常需要处理依赖、重启策略、看门狗和资源限制：

# /etc/systemd/system/gateway.service
[Unit]
Description=Gateway main application
After=network-online.target data.mount
Wants=network-online.target
Requires=data.mount                     # data 分区挂载失败时不启动
StartLimitIntervalSec=60
StartLimitBurst=5                       # 60 秒内最多重启 5 次，超过则进入 failed

[Service]
Type=notify                             # 程序初始化完成后调用 sd_notify("READY=1")
ExecStartPre=/usr/bin/gateway --check-config
ExecStart=/usr/bin/gateway -c /data/gateway.conf
Restart=on-failure
RestartSec=2
WatchdogSec=10                          # 程序需要每 10 秒内发送 WATCHDOG=1
User=gateway
Group=gateway
SupplementaryGroups=dialout gpio        # 访问串口、GPIO 设备节点
Environment=LOG_LEVEL=info
LimitCORE=infinity
MemoryMax=128M
OOMScoreAdjust=-500

[Install]
WantedBy=multi-user.target

字段要点：

  • After= 只决定顺序，Wants= / Requires= 才决定依赖，两者通常一起使用。
  • network-online.target 只表示网络管理服务认为网络已就绪，业务程序本身仍然要处理网络断开和重连。
  • Type=notify 配合 WatchdogSec=：程序卡死不再喂狗时，systemd 会杀掉并按 Restart= 重启它，这是应用层的软件看门狗。
  • 不要用 root 运行业务程序，通过用户组授予设备节点权限（配合 udev 规则）。

程序端的通知实现（链接 libsystemd，或者直接向 $NOTIFY_SOCKET 发送数据报）：

#include <systemd/sd-daemon.h>

sd_notify(0, "READY=1");                     /* 初始化完成 */
for (;;) {
    process_once();
    sd_notify(0, "WATCHDOG=1");              /* 主循环每轮喂狗，间隔小于 WatchdogSec 的一半 */
}

11. 硬件看门狗与 systemd

systemd 本身可以负责喂硬件看门狗（/dev/watchdog），形成两级保护：

# /etc/systemd/system.conf
[Manager]
RuntimeWatchdogSec=30        # systemd 每 15 秒左右喂一次硬件看门狗
RebootWatchdogSec=10min      # 重启过程卡住时的保护
  • 业务进程卡死 → 服务级 WatchdogSec 触发 → systemd 重启服务。
  • systemd 或内核卡死 → 硬件看门狗超时 → 整机复位。

注意硬件看门狗设备同一时间只能被一个程序打开，如果已经有独立的喂狗程序，就不要再启用 RuntimeWatchdogSec。

12. udev 规则：稳定的设备名与权限

USB 转串口、4G 模块等设备的 /dev/ttyUSBx 编号会随枚举顺序变化。用 udev 规则生成稳定的软链接：

# 查询设备属性
udevadm info -a -n /dev/ttyUSB0 | grep -E 'idVendor|idProduct|serial|devpath'

# /etc/udev/rules.d/90-gateway.rules
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", SYMLINK+="ttyRS485", GROUP="dialout", MODE="0660"
SUBSYSTEM=="tty", KERNELS=="1-1.2:1.2", SYMLINK+="ttyModemAT"     # 按物理 USB 端口 / 接口号匹配
SUBSYSTEM=="gpio", ACTION=="add", RUN+="/bin/chgrp -R gpio /sys%p", RUN+="/bin/chmod -R g+rw /sys%p"

# 重新加载规则并触发
udevadm control --reload-rules && udevadm trigger

同型号的多个 USB 串口没有唯一序列号时，按物理端口（KERNELS / devpath）匹配最可靠。应用程序统一打开 /dev/ttyRS485 这类稳定名称。

13. 日志管理：journald 与持久化

# /etc/systemd/journald.conf
[Journal]
Storage=persistent          # 日志写到 /var/log/journal（需在可写分区上）
SystemMaxUse=64M            # 磁盘占用上限
RuntimeMaxUse=16M           # 只保存在内存时的上限
MaxRetentionSec=14day
RateLimitIntervalSec=30s
RateLimitBurst=1000         # 防止某个程序疯狂打印拖垮系统
journalctl -u gateway -b -1 -n 200     # 上一次启动中该服务的最后 200 行（分析重启原因）
journalctl -p warning -b               # 本次启动的警告及以上
journalctl --list-boots                # 历次启动记录
journalctl --disk-usage

在闪存寿命敏感的设备上，可以只把日志保存在内存（Storage=volatile），出现异常时再由程序把最近的日志打包保存或上传。

14. 定时任务：systemd timer

相比 crontab，systemd timer 可以查看上次执行结果和日志，并能处理设备关机期间错过的任务：

# /etc/systemd/system/log-upload.timer
[Unit]
Description=Upload logs every hour

[Timer]
OnBootSec=5min
OnUnitActiveSec=1h
RandomizedDelaySec=10min    # 加随机延迟，避免大量设备同时访问服务器
Persistent=true

[Install]
WantedBy=timers.target

配套的 log-upload.service 使用 Type=oneshot。systemctl list-timers 可以查看所有定时器的下次执行时间。

15. 工作场景：服务开机偶尔起不来

现象：设备开机后约 5% 的概率主程序没有运行。排查过程：

  1. systemctl status gateway 显示 failed，journalctl -u gateway -b 显示打开 /dev/ttyUSB2 失败。
  2. systemd-analyze critical-chain gateway.service 显示服务启动时 4G 模块还没有完成 USB 枚举。
  3. 改进：
  4. udev 规则为 4G 模块的 AT 口生成 /dev/ttyModemAT，并添加 TAG+="systemd"，让 systemd 生成对应的 device 单元。
  5. 服务中增加 BindsTo=dev-ttyModemAT.device 与 After=dev-ttyModemAT.device，设备出现后再启动、设备消失时停止。
  6. 程序本身在打开失败时重试，而不是直接退出。
  7. Restart=on-failure 作为兜底。
  8. 用 systemd-analyze blame 查看各服务启动耗时，顺便把不需要的服务禁用，缩短开机时间。

16. 工程检查清单

  • 脚本首行解释器是否存在。
  • 脚本是否有执行权限。
  • 路径变量是否加双引号。
  • 是否兼容 BusyBox sh。
  • systemd 服务是否设置 WorkingDirectory。
  • 服务异常退出后是否需要自动重启。
  • 日志是否可能写满 Flash。
  • 服务是否同时使用 After= 与 Wants= / Requires= 描述顺序和依赖，是否设置了重启频率限制。
  • 关键服务是否使用 Type=notify + WatchdogSec=，硬件看门狗由谁负责喂狗是否明确。
  • 业务程序是否以非 root 用户运行，设备节点权限是否通过 udev 规则和用户组授予。
  • USB 串口等动态设备是否使用 udev 生成的稳定名称。
  • journald 是否设置了存储位置、容量上限和速率限制。
  • 定时任务是否使用 systemd timer，并对大量设备加入随机延迟。
