Linux Kernel 组成与构建流程

Linux Kernel 是系统的核心，负责进程调度、内存管理、文件系统、网络协议栈、设备驱动、中断处理和系统调用。嵌入式 Linux 开发中，Kernel 构建通常和设备树、驱动模块、根文件系统、U-Boot 启动参数一起配合使用。

内核构建不只是执行 make。真正要理解的是：配置项决定编进内核还是编成模块，设备树决定硬件描述，驱动 probe 依赖 compatible，最终 U-Boot 负责加载 Image 和 dtb。

1. Kernel 在启动链路中的位置

U-Boot 加载内核镜像和设备树后，把控制权交给 Kernel。Kernel 完成解压、架构初始化、驱动初始化、挂载根文件系统，最后启动第一个用户态进程。

2. Kernel 源码目录

linux/
├── arch/              # 架构相关代码和 defconfig.dts
├── block/             # 块设备层
├── crypto/            # 加密子系统
├── drivers/           # 设备驱动
├── fs/                # 文件系统
├── include/           # 头文件
├── init/              # 启动初始化
├── ipc/               # 进程间通信
├── kernel/            # 调度.进程.时间等核心代码
├── lib/               # 通用库
├── mm/                # 内存管理
├── net/               # 网络协议栈
└── scripts/           # 构建脚本

嵌入式开发最常接触的是 arch/arm、arch/arm64、drivers、arch/*/boot/dts、include 和 scripts。

3. 配置系统：Kconfig.defconfig..config

Kernel 使用 Kconfig 管理配置。defconfig 是默认配置，.config 是当前实际构建配置。驱动可以选择编进内核，也可以编成模块。

make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- defconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- menuconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- savedefconfig
  • y：编进内核镜像。
  • m：编译成内核模块 .ko。
  • n：不编译。

4. 设备树 DTS/DTB

设备树源码是 .dts 或 .dtsi，编译后生成 .dtb。Kernel 通过设备树了解板级硬件资源，例如串口、I2C、SPI、GPIO、中断、时钟和 pinctrl。

make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- dtbs

驱动是否 probe 成功，通常依赖设备树节点的 compatible 是否和驱动匹配。

5. 交叉编译 Kernel

不同平台的构建命令会有差异，下面是常见 ARM64 形式：

export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-

make defconfig
make -j$(nproc) Image modules dtbs

ARM32 平台可能生成 zImage，ARM64 平台通常生成 Image。某些平台还需要通过 U-Boot 工具生成 uImage。

6. 常见构建产物

  • arch/arm64/boot/Image：ARM64 内核镜像。
  • arch/arm/boot/zImage：ARM32 常见压缩内核镜像。
  • arch/*/boot/dts/*.dtb：设备树二进制文件。
  • *.ko：内核模块。
  • System.map：符号地址表，调试内核问题有用。
  • vmlinux：未压缩、带符号的内核 ELF 文件。

7. 安装内核模块

如果驱动编成模块，需要把模块安装进根文件系统的 /lib/modules/$(uname -r) 目录。

make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
     INSTALL_MOD_PATH=$PWD/rootfs modules_install

目标板上加载模块常用 modprobe 或 insmod。如果模块版本和当前内核不匹配，可能出现 vermagic 错误。

8. 管理配置：savedefconfig 与 config 片段

直接把完整的 .config 提交到仓库，会混入大量自动生成的默认项，升级内核时难以对比。推荐做法：

# 在 menuconfig 中修改后，生成精简的 defconfig（只保留与默认值不同的项）
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- menuconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- savedefconfig
cp defconfig arch/arm64/configs/xyj_rk3568_defconfig

# 对比两次配置的差异
scripts/diffconfig .config.old .config

# 用配置片段叠加（例如调试版本额外打开的选项）
scripts/kconfig/merge_config.sh -m arch/arm64/configs/xyj_rk3568_defconfig debug.config
make ARCH=arm64 olddefconfig

debug.config 这类片段只包含几行 CONFIG_xxx=y，发布版与调试版共用同一个基础配置，差异一目了然。Buildroot / Yocto 中也有对应的配置片段机制。

9. 内核编译与修改的工程习惯

  • 基于厂商 BSP 内核：SoC 厂商的内核包含主线尚未合入的驱动，开发板通常从厂商仓库的某个稳定分支开始。
  • 修改以补丁形式管理：在厂商分支上建立自己的分支，每个修改一个提交；或者在 Buildroot / Yocto 中用补丁文件管理，便于升级基线时重放。
  • 版本可追溯：设置 CONFIG_LOCALVERSION，并让构建脚本把 Git 提交号写入版本字符串，设备上 uname -a 即可知道对应的源码版本。
  • 只编译需要的部分：修改驱动后只编译模块（make M=drivers/xxx modules）或只编译设备树（make dtbs），缩短迭代时间。
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc) Image dtbs modules
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- rockchip/rk3568-xyj-board.dtb   # 只编译单个 DTB
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- M=drivers/misc modules          # 只编译某个目录的模块

10. 设备树修改实践

板级差异尽量只修改板级 dts，而不改 SoC 公共的 dtsi：

/* rk3568-xyj-board.dts：在板级文件中引用并覆盖 SoC dtsi 定义的节点 */
#include "rk3568.dtsi"

&uart3 {
    pinctrl-names = "default";
    pinctrl-0 = <&uart3m1_xfer>;
    status = "okay";
};

&i2c1 {
    status = "okay";
    clock-frequency = <400000>;

    temp_sensor: sensor@48 {
        compatible = "ti,tmp102";
        reg = <0x48>;
    };
};

&spi1 {
    status = "disabled";          /* 本板不使用 */
};

几个容易出错的地方：

  • 引脚复用冲突：两个外设使用了同一组引脚，后 probe 的那个会失败，dmesg 中会有 pinctrl 相关错误。
  • compatible 字符串必须与驱动 of_match_table 中的条目完全一致。
  • 修改后检查实际生效的设备树：dtc -I fs -O dts /proc/device-tree > live.dts，确认节点和属性与预期一致。

设备树 overlay（.dtbo）可以在不重新编译主设备树的情况下启用扩展板外设，适合同一主板搭配不同扩展板的产品，U-Boot 中通过 fdt apply 加载。

11. 启动参数（bootargs）

内核命令行决定了控制台、根文件系统和很多调试行为：

console=ttyS2,1500000 root=/dev/mmcblk0p5 rootfstype=ext4 ro rootwait
loglevel=4 panic=5 init=/sbin/init
参数作用
console=内核与 init 的控制台，串口号与波特率必须与硬件一致
earlycon在串口驱动加载前就输出日志，用于排查“Starting kernel...”之后没有输出的问题
root= / rootfstype= / rootwait根文件系统位置与类型，rootwait 等待 eMMC / SD 初始化完成
ro / rw根文件系统挂载方式
panic=5panic 后 5 秒自动重启，量产设备推荐设置
initcall_debug打印每个驱动初始化的耗时，用于优化启动时间
quiet / loglevel=减少控制台输出，加快启动

运行中的参数可以通过 cat /proc/cmdline 确认，排查启动问题时第一步就要看它。

12. 内核崩溃信息怎么读

驱动 bug 导致的 Oops / panic 会打印调用栈，关键信息：

Unable to handle kernel NULL pointer dereference at virtual address 0000000000000010
pc : xyj_sensor_read+0x2c/0x90 [xyj_sensor]
lr : xyj_sensor_show+0x24/0x50 [xyj_sensor]
Call trace:
 xyj_sensor_read+0x2c/0x90 [xyj_sensor]
 xyj_sensor_show+0x24/0x50 [xyj_sensor]
 dev_attr_show+0x20/0x60
  • NULL pointer dereference at ...0010：访问空指针偏移 0x10 处，通常是结构体指针为空时访问其成员。
  • pc : 函数名+偏移/函数长度 [模块名]：出错指令位置。
  • 用 faddr2line 把偏移转换为源码行（需要带调试信息的 vmlinux 或 .ko）：
./scripts/faddr2line drivers/misc/xyj_sensor.ko xyj_sensor_read+0x2c/0x90

开启 CONFIG_DEBUG_INFO、CONFIG_KALLSYMS_ALL 能让调用栈信息更完整；现场设备可以开启 pstore / ramoops，把 panic 日志保存在保留内存中，重启后从 /sys/fs/pstore/ 读取。

13. 工作场景：为新板卡适配一个 I2C 温度传感器

  1. 确认驱动：在内核源码中搜索型号（grep -r "tmp102" drivers/），确认已有驱动和对应的 compatible 字符串，在 menuconfig 中打开（CONFIG_SENSORS_TMP102）。
  2. 修改设备树：在板级 dts 的对应 I2C 节点下添加子节点，地址与硬件一致，确认 I2C 控制器为 okay。
  3. 单独编译 DTB 和模块，替换后重启。
  4. 验证：i2cdetect -y 1 中对应地址显示为 UU（已被驱动占用），dmesg 无报错，/sys/class/hwmon/hwmonN/temp1_input 能读到温度。
  5. 固化：用 savedefconfig 更新配置，提交 dts 修改与配置变更。

14. Kernel 调试检查清单

  • 内核 Image.dtb、模块是否来自同一次构建。
  • .config 中驱动是 y 还是 m。
  • 设备树 compatible 是否和驱动匹配。
  • U-Boot 加载的 dtb 是否确实是你修改后的版本。
  • 模块安装路径是否和 uname -r 一致。
  • dmesg 中是否有 probe 失败、时钟、pinctrl、电源或中断错误。
  • 内核启动参数 console、root、rootwait 是否正确。
  • 内核配置是否以 savedefconfig 生成的精简 defconfig 管理，调试选项是否使用配置片段叠加。
  • 内核修改是否以独立提交或补丁形式管理，版本字符串能否追溯到源码提交。
  • 板级差异是否只修改板级 dts，引脚复用是否检查过冲突。
  • bootargs 中的控制台、根文件系统和 panic= 等参数是否与产品一致，可通过 /proc/cmdline 确认。
  • 是否掌握 Oops 调用栈与 faddr2line 的使用，现场设备是否开启 pstore 保存崩溃日志。
