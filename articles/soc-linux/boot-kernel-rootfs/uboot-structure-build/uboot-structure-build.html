U-Boot 组成与构建流程

U-Boot 是嵌入式 Linux 系统中常见的 Bootloader。它的核心任务是完成最早期硬件初始化.加载内核镜像.加载设备树.准备启动参数，并最终跳转到 Linux Kernel 入口。

学 U-Boot 不要只记命令。要先理解启动链路：ROM Code → SPL/TPL → U-Boot proper → Kernel → RootFS。调板子时，任何一个环节出错，最终表现都可能是"系统起不来"。

1.为什么需要 SPL 和 U-Boot 两个阶段

嵌入式 SoC 上电后，首先运行的是芯片内部 ROM Code。这段代码由芯片厂商固化在 ROM 中，无法修改。ROM Code 的能力很有限：它只能完成最基本的硬件初始化，并从某个固定存储位置加载下一阶段程序到 SRAM 中运行。

问题在于：SRAM 通常很小，只有几十 KB 到几百 KB。而完整的 U-Boot 编译后往往超过 500 KB，根本放不下。因此出现了 SPL：它作为 ROM Code 和完整 U-Boot 之间的桥梁，体积小到能放进 SRAM，只负责初始化 DDR，然后加载完整的 U-Boot 到 DDR 中运行。

表格总结两阶段分工：

对比项SPLU-Boot proper

2.SPL 详解

2.1 SPL 是什么

SPL 是 Secondary Program Loader 的缩写，中文意思是"第二阶段程序加载器"。它是 ROM Code 加载的第一个可执行程序。由于 ROM Code 只能把数据加载到 SRAM，而 SRAM 空间非常有限，所以 SPL 必须极度精简。

2.2 SPL 包含哪些内容

SPL 代码来源于 U-Boot 源码的 spl/ 目录。编译时通过特殊配置，只编译其中的部分模块。一个典型 SPL 包含：

  • 时钟初始化：配置 ARM Core 时钟.PLL.分频器，让 CPU 运行在正确频率。
  • DDR 初始化：这是最关键的一步。不同芯片的 DDR 控制器配置差异巨大，需要厂商提供的 DDR 初始化参数（通常在芯片手册或 SDK 中）。
  • 存储控制器初始化：例如 eMMC.SPI Flash.NAND 控制器，让后续能读取存储介质。
  • 串口初始化（可选）：部分 SPL 会在串口输出早期日志，方便调试。
  • 搬移 U-Boot 到 DDR：这是 SPL 的最后一步任务。从存储介质读取完整 U-Boot 镜像到 DDR 某地址，然后跳转到 U-Boot 入口。

2.3 SPL 的限制

由于运行在 SRAM 中，SPL 受到严格限制：

  • 无堆.无栈或栈极小：无法支持复杂的 C 语言运行时环境。
  • 无标准输入输出：大部分 SPL 没有完整 libc 支持。
  • 代码必须静态链接：无法使用动态链接。
  • 部分驱动不可用：只有被显式编译进去的驱动才可用。

2.4 TPL 是什么

有些平台存在第三阶段 TPL，即 Third Program Loader（第三阶段程序加载器）。这通常是因为芯片内部 SRAM 空间仍然不够放下完整的 DDR 初始化代码，需要再切一刀。TPL 负责更完整的 DDR 训练（Training）和初始化，之后再加载 SPL 或 U-Boot。

3.瑞芯微 Rockchip TPL 详解

3.1 Rockchip 平台的启动链路

以 Rockchip 芯片（如 RK3588.RK3566.RK3399 等）为例，其启动链路与其他平台略有不同。Rockchip 使用 idbloader 作为 SPL 的替代方案，但实际上 idbloader 内部包含了 TPL 和 U-Boot 两部分：

  1. ROM Code：芯片固化，从启动介质（eMMC.SPI Flash.SD 卡等）加载 idbloader。
  2. TPL（信任固件）：运行在 SRAM，负责 DDR 初始化和部分安全初始化。
  3. U-Boot（ATF 之前）：继续运行在 SRAM做一些早期初始化。
  4. ATF（ARM Trusted Firmware）：如果启用EL3安全世界。
  5. U-Boot proper：运行在 DDR，完整 Bootloader 功能。
  6. Linux Kernel：内核启动。
Rockchip 的 SPL 概念与其他平台略有混淆。在标准术语中，SPL 指运行在 SRAM 的第二阶段加载器。但在 Rockchip 文档中，idbloader 包含了 TPL + U-Boot，展开后才得到完整的启动镜像。因此看到 Rockchip 文档提到"从 idbloader 启动"时，要理解这已经是 TPL + U-Boot 的组合产物。

3.2 TPL 在 Rockchip 中的具体职责

Rockchip 的 TPL（有时也叫 Miniloader 或 BL31 之前的阶段）主要负责：

  • DDR 初始化：这是最核心的任务。Rockchip 芯片的 DDR 控制器配置非常复杂，需要进行 DDR Training（包括 Write Leveling.Read Gate Training.MPR Calibration 等多个步骤），确保数据信号完整性。这部分代码通常由芯片原厂提供，以二进制 blob 或参数表形式存在。
  • PMIC 初始化：配置电源管理芯片，为 CPU.DDR 等上电。
  • 时钟树配置：设置 ARM Core.PLL.总线时钟等。
  • 安全初始化（可选）：如果启用 ARM TrustZone，TPL 会初始化安全世界环境。
  • 加载下一阶段：TPL 最后从存储介质读取 U-Boot 或 ATF，并跳转到对应入口。

3.3 Rockchip DDR 初始化的特殊性

Rockchip 平台的 DDR 初始化与其他平台有显著差异：

对比项一般平台（如 NXP TI）Rockchip 平台
DDR 参数来源厂商提供完整 DDR 初始化代码，可直接编译进 SPL原厂提供 DDR Bin 文件（二进制参数表），由 TPL 加载到 DDR 控制器
DDR Training 方式SPL 代码中实现硬件校准流程PC 端工具（如 Rockchip SDK 中的 rockchip_ddr driver）生成参数文件，TPL 仅加载
参数存储位置通常编译进镜像独立 rk3588_ddr_vx.x.x.bin 文件，与 idbloader 打包
调试复杂度相对简单，有完整源码较复杂，二进制参数需要配合示波器或 Rockchip 工具调试

3.4 idbloader 打包流程

Rockchip 的启动镜像打包使用 Rockchip 提供的 tools（rkboot 和 loaderimage），典型流程如下： 

# 1. 编译得到各阶段镜像
# TPL (DDR 初始化) + U-Boot 编译产物
tpl/u-boot-tpl.bin
u-boot-spl.bin
u-boot.bin

# 2. 下载 Rockchip 官方 DDR Bin（由芯片厂商提供）
# 不同芯片型号对应不同 DDR 参数文件
rk3588_ddr_v1.00_20210806.bin

# 3. 使用 rockchip 工具打包 idbloader
# 该工具将 TPL + DDR Bin + U-Boot 打包为 idbloader.img
rkbin/tools/trust_merger -- bl31 -- firmware tpl/u-boot-tpl.bin \
  -- output rk3588_ddr_v1.00_20210806.bin idbloader.img

最终烧录到 eMMC/SPI Flash 的 idbloader.img 包含了完整的启动初始化代码。ROM Code 只需加载这个文件到 SRAM 并跳转即可。

3.5 常见 Rockchip 启动问题与排查

  • DDR 初始化失败：串口无输出，最常见原因是 DDR 参数与实际硬件不匹配（颗粒型号.频率.拓扑等）。需要确认使用的 DDR Bin 文件是否对应当前硬件。
  • idbloader 偏移错误：Rockchip 对 idbloader 的存储偏移有严格要求（通常是 0x4000 或 0x2000），烧录时需确认。
  • TPL 运行但 U-Boot 未加载：串口有输出但停在 TPL 阶段，说明 DDR 已正常但后续镜像加载失败，检查存储介质连接和镜像偏移。

4.U-Boot proper 详解

4.1 U-Boot proper 是什么

U-Boot proper 是完整版的 U-Boot，"proper" 在英文中是"正式的.真正的"意思。它是 SPL/TPL 加载到 DDR 后运行的程序，具备完整的 Bootloader 功能。

4.2 U-Boot proper 包含哪些内容

相比 SPL，U-Boot proper 运行在 DDR 中，有充足的内存空间，因此包含大量功能模块：

  • 完整硬件初始化：除了 SPL 已初始化的硬件，U-Boot 还会初始化更多外设，如 USB.Ethernet.WiFi.显示等。
  • 命令系统：U-Boot 提供了数十条命令，如 bootz.booti.fatload.ext4load.tftp.setenv.saveenv.mmc.sf 等。
  • 网络协议栈：支持 TFTP.NFS.DHCP.DNS 等网络协议，可通过网络加载内核。
  • 文件系统命令：支持 FAT.EXT4.BTRFS.NTFS 等文件系统，可读写分区。
  • 设备树操作：支持 FDT 命令，可查看.修改.传递设备树。
  • 启动介质驱动：eMMC.SPI Flash.NAND.SD.USB 等完整驱动。
  • 环境变量系统：持久化存储启动参数.bootcmd.bootargs 等。
  • 启动镜像格式支持：支持 FIT 镜像.Image.zImage 等。

4.3 U-Boot proper 启动流程

U-Boot proper 启动后大致经历以下阶段：

  1. 汇编初始化阶段（arch/arm/cpu/）：设置中断向量表.初始化栈.清除 BSS 段。
  2. board_init_f：早期板级初始化，配置部分硬件。
  3. relocate：将自身代码重定位到 DDR 高地址（避免覆盖低地址的存储缓冲区域）。
  4. board_init_r：完整板级初始化，包括外设.驱动.命令系统.网络等。
  5. 启动命令执行：根据 bootcmd 执行自动启动，或进入命令行等待输入。

5.常见启动介质与镜像布局

不同启动介质的镜像布局和烧录方式不同：

启动介质典型镜像布局说明
eMMC / SD卡SPL → U-Boot → env → kernel → dtb → rootfs按分区表连续存储，各镜像有固定偏移
SPI FlashSPL → U-Boot → env (单独区域)通常使用 spi bus 读取，env 在固定偏移
NAND FlashSPL → U-Boot → oob 数据区NAND 有 OOB 区域存放 ECC 和坏块信息
TFTP 网络仅 U-Boot proper 存在内核和设备树从网络加载，不烧录到介质

烧录时需要确认芯片数据手册中规定的各镜像偏移地址和大小限制，确保 SPL 恰好放在 SRAM 可寻址范围内。

6.构建产物详解

  • u-boot.bin：裸二进制 U-Boot 镜像，没有任何头部。直接烧录到存储介质的 U-Boot 分区。
  • u-boot.elf：带符号信息的 ELF 文件。用于调试，可配合 GDB 使用。
  • u-boot.img：带 64 字节镜像头的 bin，用于部分需要校验启动介质完整性的平台。
  • u-boot.itb：FIT（Flattened Image Tree）镜像格式，可打包内核.设备树.配置签名等信息。
  • SPL / u-boot-spl.bin：SPL 阶段镜像，通常放在存储介质开头，需要符合芯片规定的偏移和大小。
  • tpl/u-boot-tpl.bin：TPL 阶段镜像（如果平台有 TPL）。

7.环境变量与 bootcmd

U-Boot 环境变量决定了从哪里加载内核.设备树和根文件系统。常见变量包括 bootcmd.bootargs.kernel_addr_r.fdt_addr_r。 

printenv
setenv bootargs console=ttyS0,115200 root=/dev/mmcblk0p2 rw rootwait
saveenv
boot

调试启动失败时，重点查看 bootargs 是否正确.内核和 dtb 是否加载到正确地址.rootfs 路径是否匹配实际分区。

8.调试检查清单

  • 串口波特率和串口号是否正确。
  • SPL 是否正确初始化 DDR，内存容量是否识别正确。
  • 启动介质偏移和镜像格式是否符合 SoC 要求。
  • U-Boot proper 是否正确加载到 DDR。
  • defconfig 是否对应当前板卡。
  • 设备树是否和板级硬件一致。
  • bootargs 中 rootfs 分区是否正确。
  • 内核镜像.dtb.rootfs 是否版本匹配。
