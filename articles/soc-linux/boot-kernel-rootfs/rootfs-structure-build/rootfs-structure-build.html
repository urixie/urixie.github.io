根文件系统组成与构建流程

根文件系统 RootFS 是 Linux 启动后挂载的第一个文件系统，里面包含用户态程序、动态库、配置文件、设备节点、启动脚本和应用程序。Kernel 启动成功后，如果无法挂载 rootfs 或找不到 init，系统仍然无法进入用户态。

U-Boot 负责加载 Kernel，Kernel 负责驱动硬件和挂载 RootFS，RootFS 负责提供用户态环境。三者版本、路径、启动参数必须匹配，否则系统会卡在启动阶段。

1. RootFS 在启动链路中的作用

Kernel 根据启动参数中的 root= 找到根文件系统，挂载后执行第一个用户态程序，常见是 /sbin/init、/init 或 systemd。

2. RootFS 基本目录结构

rootfs/
├── bin/        # 基础用户命令
├── sbin/       # 系统管理命令
├── etc/        # 配置文件和启动脚本
├── lib/        # 动态库
├── usr/        # 用户程序和库
├── dev/        # 设备节点
├── proc/       # procfs 挂载点
├── sys/        # sysfs 挂载点
├── tmp/        # 临时目录
├── var/        # 日志.运行时数据
└── home/       # 用户目录

最小 rootfs 可以非常小，只需要 BusyBox、必要动态库、init 脚本和几个挂载点。完整发行版 rootfs 则会包含包管理器、systemd、网络工具、调试工具等。

3. BusyBox 根文件系统

BusyBox 把大量常用 Linux 命令集成到一个可执行文件中，非常适合资源有限的嵌入式系统。

make menuconfig
make -j$(nproc)
make CONFIG_PREFIX=$PWD/rootfs install

安装后，BusyBox 会在 bin、sbin 等目录下创建大量指向 busybox 的软链接，例如 ls、cat、sh。

4. 动态库与链接器

如果用户程序是动态链接的，rootfs 中必须包含对应架构的动态库和动态链接器。否则即使文件存在，也可能运行时报 “not found”。

file app
readelf -l app | grep interpreter
readelf -d app | grep NEEDED

典型问题是：应用是 ARM64 架构，但 rootfs 里缺少 /lib/ld-linux-aarch64.so.1 或依赖库版本不匹配。

5. init 与启动脚本

Kernel 挂载 rootfs 后会尝试启动 init。BusyBox 系统常用 /etc/inittab 和 /etc/init.d/rcS，systemd 系统则启动 /sbin/init 指向 systemd。

::sysinit:/etc/init.d/rcS
::respawn:-/bin/sh
::ctrlaltdel:/sbin/reboot

最小系统中，rcS 通常负责挂载 proc、sysfs、devtmpfs，配置网络，启动应用。

6. 挂载 proc.sysfs.devtmpfs

mount -t proc none /proc
mount -t sysfs none /sys
mount -t devtmpfs none /dev
mount -t tmpfs none /tmp

如果这些伪文件系统没有挂载，很多命令和服务会异常，例如看不到进程信息、设备节点不完整、系统服务启动失败。

7. 使用 Buildroot 构建 RootFS

Buildroot 可以自动构建交叉工具链、Bootloader、Kernel、RootFS 和用户态软件包，适合快速生成嵌入式 Linux 系统。

make menuconfig
make -j$(nproc)

Buildroot 常见产物位于 output/images，包括 rootfs.ext4.rootfs.tar.Image.dtb 等，具体取决于配置。

8. 使用 Ubuntu Base 构建 RootFS

如果板子资源足够，也可以使用 Ubuntu Base 这类发行版根文件系统。它的优点是软件生态完整，缺点是体积更大、启动更慢、依赖更多。

tar -xpf ubuntu-base-xx.xx-base-arm64.tar.gz -C rootfs
cp /usr/bin/qemu-aarch64-static rootfs/usr/bin/
chroot rootfs /bin/bash

进入 chroot 后可以安装软件包、配置用户、网络、systemd 服务等。构建完成后再打包成 ext4.tar 或其它格式。

9. RootFS 打包格式

  • rootfs.tar：适合部署到已有分区。
  • rootfs.ext4：适合直接烧录到 ext4 分区。
  • cpio.gz：常用于 initramfs。
  • squashfs：只读压缩文件系统，适合固件镜像。
  • ubifs：适合 NAND Flash。

10. RootFS 启动问题排查

现象优先排查方向

No init found/sbin/init./init.BusyBox 安装、执行权限
app: not found架构不匹配、动态链接器缺失、依赖库缺失
设备节点缺失devtmpfs.mdev/udev、驱动是否 probe
系统只读挂载参数、分区损坏、只读文件系统设计

11. Buildroot 的工程化组织：BR2_EXTERNAL

直接修改 Buildroot 源码树，升级 Buildroot 版本时会很痛苦。推荐把所有产品相关内容放在独立的外部目录中：

xyj-br2-external/
├── external.desc            # name: XYJ
├── external.mk              # include $(sort $(wildcard $(BR2_EXTERNAL_XYJ_PATH)/package/*/*.mk))
├── Config.in                # source "$BR2_EXTERNAL_XYJ_PATH/package/gateway/Config.in"
├── configs/
│   └── xyj_rk3568_defconfig
├── board/xyj/
│   ├── rootfs-overlay/      # 直接覆盖到 rootfs 的文件（/etc 配置、systemd 服务等）
│   ├── post-build.sh        # 生成镜像前对 target 目录做最后调整
│   ├── post-image.sh        # 生成分区镜像、升级包
│   └── genimage.cfg
└── package/gateway/         # 自己的应用软件包
    ├── Config.in
    └── gateway.mk
make BR2_EXTERNAL=../xyj-br2-external xyj_rk3568_defconfig
make menuconfig                      # 修改后
make savedefconfig                   # 写回 configs/xyj_rk3568_defconfig
make gateway-rebuild                 # 只重新编译某个包
make -j$(nproc)

一个本地应用包的描述文件示例：

# package/gateway/gateway.mk
GATEWAY_VERSION = 1.0
GATEWAY_SITE = $(BR2_EXTERNAL_XYJ_PATH)/../gateway
GATEWAY_SITE_METHOD = local
GATEWAY_DEPENDENCIES = libgpiod
GATEWAY_CONF_OPTS = -DCMAKE_BUILD_TYPE=Release

$(eval $(cmake-package))

SITE_METHOD = local 让 Buildroot 直接使用本地源码目录，配合 make gateway-rebuild 就能快速迭代应用程序。

12. 裁剪体积与启动时间

手段效果
使用 squashfs（xz / zstd 压缩）rootfs 体积通常缩小一半以上
选择合适的 C 库glibc 兼容性最好；musl 体积更小，部分软件需要适配
去掉调试符号（BR2_STRIP_strip）发布镜像体积显著减小，调试符号另外保存用于分析 core
只启用需要的 BusyBox applet 和软件包减少体积和攻击面
禁用不需要的服务、按需启动缩短启动时间
systemd-analyze blame / bootchart找出启动慢的服务

去掉调试符号时，保留一份带符号的镜像或 staging 目录，现场 core dump 才能被解析。

13. 用户、权限与基本安全

量产设备的 rootfs 至少要做到：

  • root 账户：禁用密码登录，或者每台设备使用不同的密码；不要所有设备共用一个默认密码。
  • SSH：只允许密钥登录（PasswordAuthentication no），调试版本与发布版本使用不同配置。
  • 串口控制台：发布版本可以关闭登录 shell，或者要求认证。
  • 业务进程以独立用户运行，只授予必要的设备访问权限。
  • 关闭不需要的网络服务，用 ss -tulnp 检查监听端口。
  • 文件权限：Buildroot 中使用 BR2_ROOTFS_DEVICE_TABLE / users table（BR2_ROOTFS_USERS_TABLES）声明用户和文件权限，而不是在 post-build 脚本中到处 chmod。

14. 调试版与发布版

同一套源码通常要生成两种镜像：

项目调试版发布版
工具gdbserver、strace、tcpdump、i2c-tools不包含或最小化
登录串口 / SSH 可直接登录受限或关闭
日志级别debuginfo / warning
文件系统可读写，方便替换程序只读
符号保留去除（另存一份）

用配置片段（merge_config.sh 或 Buildroot 的多个 defconfig 片段）区分两种构建，保证除调试差异外完全一致，避免“调试版正常、发布版有问题”。

15. 工作场景：从开发板镜像到产品镜像

  1. 基线：从 SoC 厂商 SDK 中提取能启动的 Buildroot 配置，确认串口登录正常。
  2. 外部目录：建立 BR2_EXTERNAL，把板级配置、overlay、自研应用包移入，产品仓库与 Buildroot 版本解耦。
  3. 分区与镜像：用 genimage 描述分区表，post-image 脚本生成完整烧录镜像和 OTA 升级包，分区规划见 嵌入式存储与文件系统。
  4. 只读化：rootfs 改为只读，可写目录迁移到 data 分区或 tmpfs。
  5. 安全：配置用户、SSH 和服务，检查监听端口。
  6. 可复现：在 CI 中用固定版本的 Docker 镜像构建，产物记录 Buildroot 版本、外部目录提交号和配置哈希。

16. 工程检查清单

  • rootfs 架构是否和 Kernel/应用一致。
  • 动态库和动态链接器是否完整。
  • /sbin/init 或 /init 是否存在且可执行。
  • /proc、/sys、/dev 挂载点是否存在。
  • U-Boot 的 bootargs 中 root= 是否匹配实际分区。
  • rootfs 打包格式是否符合启动介质和内核配置。
  • 日志目录是否可写，是否会写满 Flash。
  • 产品相关内容是否放在 BR2_EXTERNAL 外部目录中，而不是直接修改 Buildroot 源码树。
  • 自研应用是否作为 Buildroot 软件包管理，能否单独重新编译。
  • 发布镜像是否去除了调试符号，并另存一份带符号的版本用于分析 core dump。
  • 是否禁用了默认密码与密码登录，监听端口与运行用户是否经过检查。
  • 调试版与发布版是否由同一套配置加片段生成，构建过程能否在 CI 中复现。
