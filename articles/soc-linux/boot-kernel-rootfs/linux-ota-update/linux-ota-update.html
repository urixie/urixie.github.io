嵌入式 Linux OTA 升级设计

以 A/B 双分区为核心，说明升级流程、启动计数与自动回滚、SWUpdate/RAUC 框架、健康检查与数据迁移。

1. OTA 要解决的问题

嵌入式 Linux 设备的远程升级，核心要求只有一条：升级过程中任何时刻断电，设备都必须还能启动，并且能再次升级。在此基础上还要考虑：

  • 完整性与真实性：升级包没有损坏，并且确实来自厂商（签名校验）。
  • 回滚：新版本启动失败或业务异常时，自动回到旧版本。
  • 数据保留：用户配置、日志、业务数据在升级后仍然可用，必要时做数据迁移。
  • 可观测：每台设备的当前版本、升级结果、失败原因能够上报。

与 MCU 的 Bootloader 升级相比，Linux 的启动链更长（Bootloader → Kernel → RootFS → 应用），但思路相同，可以对照 MCU Bootloader 与 OTA。

2. 常见升级方案对比

方案做法优点缺点
文件级更新解压覆盖可执行文件、库包小、实现简单断电易损坏，版本状态难以管理
包管理器（opkg / apt）按软件包升级粒度细设备间状态容易发散，不适合量产设备
单分区 + 恢复系统正常系统 + 一个最小 recovery 系统，升级时进入 recovery 写入存储占用少升级期间业务中断，recovery 本身也要维护
A/B 双分区两套系统分区，升级写入非活动分区，切换后启动断电安全、可回滚、停机时间短系统分区占用翻倍
增量 / 差分只传输差异（如 casync、bsdiff、RAUC adaptive）节省流量生成与校验更复杂，依赖基线版本

量产设备推荐 A/B 双分区 + 签名校验 + 自动回滚，在存储允许的情况下这是最稳妥的方案。分区规划见 嵌入式存储与文件系统。

3. A/B 升级的完整流程

1. 下载升级包到 data 分区（或边下载边写入非活动分区）
2. 校验签名与哈希
3. 写入非活动槽位（例如当前运行 A，则写 boot_b + rootfs_b）
4. 写入后回读校验
5. 设置 bootloader 变量：下次从 B 启动，剩余尝试次数 = 3
6. 重启
7. U-Boot 启动 B，尝试次数减 1
8. 系统启动后，应用健康检查通过 → 标记 B 为“好”（清除尝试计数）
9. 若 B 连续启动失败、尝试次数耗尽 → U-Boot 自动切回 A

关键是第 5~9 步的启动计数机制。U-Boot 内置的 bootcount 功能可以配合环境变量实现：

# U-Boot 环境变量（示意）
boot_slot=b
bootlimit=3
altbootcmd=run switch_slot; run bootcmd     # 启动次数超过 bootlimit 时执行
upgrade_available=1                         # 只在升级后的试运行期间启用计数

# Linux 端：健康检查通过后确认新系统（fw_setenv 来自 libubootenv / u-boot-tools）
fw_setenv upgrade_available 0
fw_setenv bootcount 0

fw_setenv 依赖 /etc/fw_env.config 描述环境变量所在的设备、偏移和大小，必须与 U-Boot 编译配置一致，否则读写的是错误位置。环境变量建议启用冗余（两份副本），避免写环境变量时断电导致两个槽位都无法启动。

4. 升级框架：SWUpdate 与 RAUC

自己实现 A/B 升级容易遗漏细节，工程上常用成熟框架：

框架升级包格式特点
SWUpdate.swu（cpio，内含 sw-description）灵活，支持脚本 hook、Lua 处理器、Web 界面和 hawkBit 服务器
RAUC.raucb（squashfs + 签名）槽位模型清晰，强制签名，支持 adaptive 增量更新
MenderArtifact带服务器与设备管理，开源版功能有限制

RAUC 的系统配置示例，清楚描述了槽位与 bootloader 的关系：

# /etc/rauc/system.conf
[system]
compatible=xyj-gateway-rk3568
bootloader=uboot

[keyring]
path=/etc/rauc/ca.cert.pem

[slot.rootfs.0]
device=/dev/mmcblk0p5
type=ext4
bootname=A

[slot.rootfs.1]
device=/dev/mmcblk0p6
type=ext4
bootname=B

compatible 字段用于防止把其他产品的升级包装到这台设备上；升级包签名证书对应的私钥要严格保管，不要放进代码仓库或 CI 日志。

5. 升级后的健康检查

“能启动”不等于“能工作”。确认新版本之前，健康检查至少应包括：

  • 关键服务（主业务进程、网络管理、看门狗喂狗进程）在规定时间内启动并持续运行。
  • 网络可以连接到服务器（如果业务依赖网络）。
  • 关键外设能够正常打开和读写（例如串口通信对端能正常响应）。

可以用 systemd 实现：一个 health-check.service 在依赖服务启动后运行检查脚本，通过后执行 fw_setenv 确认；硬件看门狗确保系统卡死时会重启，从而进入启动计数逻辑。systemd 服务的写法见 Shell 与 systemd。

6. 数据兼容与迁移

升级失败最常见的原因之一不是系统本身，而是新版本读不懂旧数据：

  • 配置文件带版本号，新程序启动时检测到旧版本格式就执行迁移，迁移前先备份。
  • 迁移要考虑回滚：B 版本把配置迁移成新格式后，如果回滚到 A，A 要么能读新格式，要么能使用迁移前的备份。
  • 数据库（SQLite 等）的 schema 变更同样需要版本管理和迁移脚本。
  • 不要在升级包中覆盖 data 分区的用户数据。

7. 工作场景：给网关设备设计一套 OTA

需求：RK3568 网关，eMMC 8GB，4G / 以太网联网，现场设备约 5000 台。

  1. 分区：boot_a/boot_b（64MB）、rootfs_a/rootfs_b（1.5GB，ext4 只读挂载）、data（剩余）。
  2. 框架：RAUC + U-Boot bootcount，升级包使用公司 CA 签名，compatible 区分硬件型号。
  3. 下载：设备定期查询版本服务器，支持断点续传；4G 网络下限速并避开业务高峰。
  4. 灰度：先升级内部测试设备，再按 1% → 10% → 全量分批，每批观察升级成功率和回滚率。
  5. 确认：启动后健康检查服务验证业务进程、网络和串口外设，通过后确认新槽位。
  6. 上报：设备上报当前槽位、版本号、上次升级结果和回滚原因，后台统计异常。
  7. 兜底：保留 USB / TF 卡本地升级入口和 Maskrom 烧录方式，用于现场维修。

8. OTA 检查清单

  • 升级过程中任意时刻断电，设备是否都能启动并再次升级（需要实测，而不是推理）。
  • 升级包是否签名，设备端是否校验签名、哈希和硬件兼容性（compatible）。
  • 是否有启动计数与自动回滚，环境变量是否启用冗余副本。
  • fw_env.config 是否与 U-Boot 环境变量的位置和大小一致。
  • 健康检查是否覆盖关键业务，而不只是“系统启动成功”。
  • 新版本是否兼容旧数据，回滚后旧版本能否读取数据。
  • 是否支持断点续传、限速与分批灰度发布。
  • 签名私钥是否妥善保管，没有出现在仓库、镜像或日志中。
  • 是否保留了本地升级与底层烧录的兜底手段。
