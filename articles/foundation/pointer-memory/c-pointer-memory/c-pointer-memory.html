C语言指针与内存模型整理

本文整理 C 语言中最容易出错、但也是嵌入式开发最常用的指针与内存知识。重点关注地址、解引用、数组与指针、字符串、缓冲区、栈、堆、指针函数、函数指针、野指针、越界访问以及协议解析中的典型写法。

指针不是单纯的语法点，而是 C 语言访问内存、组织数据、传递缓冲区和操作硬件的基础能力。写指针代码时，要始终知道“它指向哪里、长度是多少、谁负责释放、是否还能访问”。

1. 为什么指针是 C 语言的核心

嵌入式系统资源有限，很多数据不能随意复制。驱动接收缓冲区、Flash 读写数据、DMA 数据区、协议帧、显示缓冲区都常通过指针传递。指针可以避免大块数据复制，但也会把内存安全责任交给开发者。

  • 传递数据缓冲区：uint8_t *buf、const uint8_t *data。
  • 输出函数结果：通过指针把读取结果写回调用者。
  • 访问寄存器地址：把固定地址转换成寄存器指针。
  • 组织动态数据：链表、队列、环形缓冲区等结构都依赖指针。
  • 组织回调入口：通过函数指针实现驱动回调、命令分发和状态机处理。

2. 地址、指针变量与解引用

普通变量保存数据，指针变量保存地址。取地址使用 &，访问指针指向的数据使用 *。指针变量本身也占内存，它保存的是另一个对象的地址。 

uint16_t adc = 1234;
uint16_t *p = &adc;

*p = 2048;       // 修改 adc 的值
uint16_t v = *p; // 读取 adc 的值

指针使用前必须保证它指向有效对象。空指针、野指针、已经释放的内存、已经离开作用域的局部变量地址，都是常见风险来源。

3. 数组与指针

数组是一段连续存储空间，指针是保存地址的变量。在大多数表达式中，数组名会退化为指向首元素的指针，但数组和指针不是同一个概念。 

uint8_t frame[8] = {0xAA, 0x55, 0x01, 0x02};
uint8_t *p = frame;

uint8_t head0 = frame[0];   // 数组下标访问
uint8_t head1 = *(p + 1);   // 指针偏移访问

sizeof(frame); // 结果是整个数组大小：8
sizeof(p);     // 结果是指针变量大小：与平台位宽有关

函数参数中的数组写法会退化为指针，所以函数内部无法通过 sizeof(buf) 得到原始数组长度。工程接口应同时传入指针和长度。 

int frame_parse(const uint8_t *buf, uint16_t len)
{
    if (buf == NULL || len < 4U) {
        return -1;
    }

    if (buf[0] != 0xAA || buf[1] != 0x55) {
        return -2;
    }

    return 0;
}

4. 字符串、字符数组与二进制缓冲区

字符串本质上是以 \0 结尾的字符数组。如果处理的是串口、SPI、Flash 中的二进制数据，不要假设它一定有字符串结束符。 

char name[] = "ESP32";          // 字符串，末尾自动带 \0
uint8_t bin[] = {0x45, 0x53};   // 二进制数据，不一定有 \0

协议帧和文件内容优先使用 uint8_t * 表示原始字节流。只有确定数据是文本并且有结束符时，才使用字符串函数。

5. 指针加减与数据类型长度

指针加一不是地址加一字节，而是移动一个指向类型的长度。uint16_t * 加一会移动 2 字节，uint32_t * 加一会移动 4 字节。 

uint32_t words[4] = {1, 2, 3, 4};
uint32_t *p = words;

p = p + 1; // 地址移动 sizeof(uint32_t) 字节

解析字节流时建议使用 uint8_t *，因为协议帧通常以字节为基本单位。如果直接把字节流强转成结构体指针，需要特别注意对齐、大小端和填充字节。

6. 栈、堆、全局区与静态区

嵌入式系统中，内存区域通常比较有限。局部变量一般在栈上，全局变量和静态变量位于静态存储区，动态申请的内存在堆上。小 MCU 项目中应谨慎使用动态内存。

  • 栈：函数调用、局部变量、返回地址等，速度快但空间有限。
  • 全局区 / 静态区：生命周期贯穿整个程序，适合长期存在的缓冲区和状态。
  • 堆：由 malloc / free 管理，灵活但容易碎片化。

对于串口接收、ADC 采样、DMA 缓冲区等长期使用的数据，通常优先使用静态或全局缓冲区，而不是在函数内部创建大数组。

7. 指针函数与函数指针

指针函数和函数指针名字相近，但含义完全不同。指针函数是“返回指针的函数”；函数指针是“指向函数入口地址的指针”。

7.1 指针函数

指针函数的返回值是一个指针，常用于返回静态缓冲区、查表结果或对象地址。注意不要返回局部变量的地址。 

static const char *state_names[] = {
    "IDLE",
    "RUN",
    "ERROR",
};

const char *get_state_name(uint8_t state)
{
    if (state >= 3U) {
        return "UNKNOWN";
    }
    return state_names[state];
}
不要返回函数内部局部数组的地址。函数返回后，局部数组所在栈空间已经失效，继续访问会产生未定义行为。 
// 错误示例
char *get_name_bad(void)
{
    char name[16] = "device";
    return name; // 错误：返回局部变量地址
}

7.2 函数指针

函数指针保存函数入口地址，常用于回调函数、命令分发表、驱动抽象层和状态机处理。它可以减少大量分支判断，让新增命令只需要增加表项。 

typedef int (*cmd_handler_t)(const uint8_t *data, uint16_t len);

typedef struct {
    uint8_t cmd;
    cmd_handler_t handler;
} cmd_item_t;

static int handle_read(const uint8_t *data, uint16_t len)
{
    (void)data;
    (void)len;
    return 0;
}

static int handle_write(const uint8_t *data, uint16_t len)
{
    (void)data;
    (void)len;
    return 0;
}

static const cmd_item_t g_cmd_table[] = {
    {0x01, handle_read},
    {0x02, handle_write},
};

调用函数指针前必须确认它不为空，并且要统一函数签名。回调是在中断中执行、任务中执行还是主循环中执行，也必须提前约定清楚。 

int dispatch_cmd(uint8_t cmd, const uint8_t *data, uint16_t len)
{
    for (uint16_t i = 0; i < ARRAY_SIZE(g_cmd_table); i++) {
        if (g_cmd_table[i].cmd == cmd && g_cmd_table[i].handler != NULL) {
            return g_cmd_table[i].handler(data, len);
        }
    }

    return -1;
}

8. 二级指针与指针数组

二级指针常用于修改调用者持有的指针，或者处理字符串表、命令表。指针数组则常用于保存多个字符串或多个回调入口。 

static const char *state_name[] = {
    "IDLE",
    "RUN",
    "ERROR",
};

const char *get_state_name_simple(uint8_t state)
{
    if (state >= 3U) {
        return "UNKNOWN";
    }
    return state_name[state];
}

如果只是读取字符串表，建议使用 const char *，避免误修改只读字符串。

9. 嵌入式场景下的指针用法

常见场景包括串口协议解析、Flash 数据读写、DMA 接收缓冲区、上位机参数下发、显示缓存刷新等。此类函数的接口建议统一表达为“数据指针 + 数据长度”。 

typedef struct {
    uint8_t cmd;
    uint8_t payload[64];
    uint16_t payload_len;
} app_frame_t;

int parse_frame(const uint8_t *data, uint16_t len, app_frame_t *out_frame)
{
    if (data == NULL || out_frame == NULL) {
        return -1;
    }

    if (len < 4U) {
        return -2;
    }

    out_frame->cmd = data[2];
    return 0;
}

10. 野指针、空指针与越界访问

指针问题最难排查的地方在于：错误不一定马上暴露。一次越界写入可能破坏旁边变量，最终在完全无关的代码位置表现为死机、重启或随机数据异常。 

int buffer_write(uint8_t *buf, uint16_t buf_size, uint16_t index, uint8_t value)
{
    if (buf == NULL) {
        return -1;
    }

    if (index >= buf_size) {
        return -2;
    }

    buf[index] = value;
    return 0;
}

11. 完整案例：设计一个不会越界的缓冲区接口

一个可靠的缓冲区接口至少要同时表达地址、有效长度、容量和所有权。下面的接口只借用调用者提供的内存，不负责释放；成功后返回写入字节数，失败时不修改输出长度。这样的约定适合 UART 接收、Flash 读写和协议编码等场景。 

#include <stddef.h>
#include <stdint.h>

int append_byte(uint8_t *buffer,
                size_t capacity,
                size_t *in_out_len,
                uint8_t value)
{
    if (buffer == NULL || in_out_len == NULL) {
        return -1;
    }
    if (*in_out_len >= capacity) {
        return -2;
    }

    buffer[*in_out_len] = value;
    ++(*in_out_len);
    return 0;
}

调用者仍然要保证 buffer 的生命周期覆盖整个调用过程，不能把字符串常量传给可写接口，也不能在另一个线程同时改变长度变量。若接口要转移堆内存所有权，应在函数名或注释中明确“调用者释放”还是“被调用者接管”，不要靠猜测。

12. const 与指针：接口里的承诺

const 放在 * 的左边还是右边，含义完全不同。读法技巧：从变量名开始向左读，const 修饰它左边紧挨着的东西（左边没有则修饰右边）。

声明指向的数据能否修改指针本身能否修改典型用途
const uint8_t *p否能只读输入参数：send(const uint8_t *buf, size_t len)
uint8_t *const p能否固定指向某个缓冲区或寄存器的指针
const uint8_t *const p否否指向 Flash 中常量表的固定指针
volatile uint32_t *const reg能（每次真实访问）否固定地址的寄存器

在函数接口里，const 是写给调用者的承诺：“我只读你的数据，不会修改它。”调用者因此可以放心传入 Flash 中的常量表、其他模块的只读数据。反过来，如果一个参数没有 const，调用者就要假设数据会被修改。

/* 好的接口：输入只读、输出可写、长度明确 */
int crc16_calc(const uint8_t *data, size_t len, uint16_t *out_crc);

/* 存放在 Flash 中的字符串表：表本身和每个字符串都不可修改 */
static const char *const err_names[] = { "OK", "PARAM", "TIMEOUT", "CRC" };

13. 内存重叠：memcpy、memmove 与 restrict

memcpy 要求源和目标不重叠，重叠时行为未定义；需要在同一缓冲区内移动数据（例如把未处理完的半帧移到缓冲区开头）时，必须用 memmove。

/* 解析了 used 字节后，把剩余数据挪到缓冲区开头：区域重叠，必须用 memmove */
memmove(rx_buf, rx_buf + used, rx_len - used);
rx_len -= used;

C99 的 restrict 关键字表示“在这个指针的生命周期内，它指向的内存只通过它访问”。编译器据此可以做更激进的优化，标准库的 memcpy 原型就带有 restrict。在 DSP 类的数组运算函数里使用 restrict，常常能让编译器生成更高效的循环；但如果调用时实际发生了重叠，结果就是未定义的。

void vec_add(int16_t *restrict dst, const int16_t *restrict a, const int16_t *restrict b, size_t n);

14. 回调函数与上下文指针

驱动和中间件常常需要在某个事件发生时“回调”上层代码。只传一个函数指针是不够的：同一个回调函数可能服务多个实例（两个串口、三个传感器），回调里需要知道“是谁的事件”。惯用做法是同时传一个 void * 上下文指针：

typedef void (*uart_rx_cb_t)(void *user, const uint8_t *data, size_t len);

typedef struct {
    uart_rx_cb_t cb;
    void        *user;          /* 注册时保存，回调时原样传回 */
} uart_handle_t;

void uart_set_rx_callback(uart_handle_t *h, uart_rx_cb_t cb, void *user)
{
    h->cb = cb;
    h->user = user;
}

/* 上层：一个解析函数服务两个串口，通过 user 区分各自的解析器 */
static void on_rx(void *user, const uint8_t *data, size_t len)
{
    parser_t *p = user;
    parser_input(p, data, len);
}

uart_set_rx_callback(&uart1, on_rx, &parser_a);
uart_set_rx_callback(&uart2, on_rx, &parser_b);

使用回调时要明确三件事：回调在什么上下文中执行（中断还是任务）；回调里能否调用阻塞函数；data 指针在回调返回后是否仍然有效（通常无效，需要的话必须拷贝）。

15. 工作场景：DMA 缓冲区的指针陷阱

DMA 绕过 CPU 直接读写内存，很多指针相关的问题在 DMA 场景下会以更隐蔽的方式出现：

  • 不要把 DMA 缓冲区放在栈上：函数返回后栈空间被复用，而 DMA 仍在往那块地址写数据，结果是随机踩坏其他局部变量。DMA 缓冲区应使用全局或静态变量。
  • 对齐：部分 DMA 控制器要求缓冲区地址按传输宽度对齐；带 Cache 的芯片还要求按 Cache 行（Cortex-M7 为 32 字节）对齐，长度也最好是 Cache 行的整数倍。
  • Cache 一致性：Cortex-M7 等带数据 Cache 的内核上，CPU 写入的数据可能还在 Cache 中，DMA 读到的是内存里的旧数据；DMA 写入内存后，CPU 读到的可能是 Cache 中的旧数据。发送前需要清理（Clean），接收后需要失效（Invalidate），或者通过 MPU 把 DMA 缓冲区配置为不可缓存。
  • DMA 能访问的内存区域有限：部分芯片上某些 RAM 不在 DMA 的总线矩阵覆盖范围内（例如 STM32H7 的 DTCM 不能被普通 DMA 访问），缓冲区放错位置时 DMA 会报错或静默失败。
/* 32 字节对齐、长度为 32 的整数倍，放在 DMA 可访问的 RAM 段 */
__attribute__((aligned(32), section(".dma_buffer")))
static uint8_t spi_tx_buf[256];

int spi_send_dma(const uint8_t *data, size_t len)
{
    if (len > sizeof(spi_tx_buf)) {
        return -EINVAL;
    }
    memcpy(spi_tx_buf, data, len);
    SCB_CleanDCache_by_Addr((uint32_t *)spi_tx_buf, (int32_t)sizeof(spi_tx_buf));  /* 把 Cache 写回内存 */
    dma_start(spi_tx_buf, len);
    return 0;
}

.dma_buffer 段需要在链接脚本中放到合适的 RAM 区域。没有 Cache 的 Cortex-M0/M3/M4 不需要 Cache 维护，但“不放在栈上”“地址对齐”两条依然适用。

16. 指针问题排查清单

  • 指针使用前是否判空。
  • 是否同时传入了缓冲区长度。
  • 数组访问下标是否小于数组长度。
  • 函数参数中的数组是否误用 sizeof 求长度。
  • 是否返回了局部变量地址。
  • 函数指针调用前是否判空，函数签名是否一致。
  • 是否把二进制数据误当成字符串处理。
  • 结构体强转时是否考虑了对齐和大小端。
  • 大数组是否放在了栈上导致栈溢出。
  • 只读的指针参数是否加了 const，常量表是否用 const 放入 Flash。
  • 同一缓冲区内移动数据时是否用了 memmove 而不是 memcpy。
  • 回调接口是否带 void * 上下文指针，回调的执行上下文和数据有效期是否写清楚。
  • DMA 缓冲区是否避免放在栈上，是否满足对齐要求，带 Cache 的芯片是否做了 Cache 维护。
