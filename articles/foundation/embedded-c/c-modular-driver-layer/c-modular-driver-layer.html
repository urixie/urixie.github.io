嵌入式 C 模块化与驱动分层设计

整理嵌入式工程的模块化与分层方法：分层结构与依赖规则、头文件接口与不透明指针、函数指针操作表抽象设备、依赖注入与 PC 端测试、板级差异管理、错误码约定、初始化顺序和目录结构，并以一套业务适配两款传感器为例。

1. 为什么需要分层

很多嵌入式项目一开始只有一个 main.c：初始化外设、读传感器、算数据、刷屏幕全写在一起。功能少时没问题，一旦出现下面这些需求，代码就开始失控：

  • 传感器换型号，或者同一套产品要支持两种传感器。
  • 主控芯片换系列，从 STM32F1 换到 GD32、从 STM32 换到 ESP32。
  • 需要在 PC 上跑单元测试，或者在没有硬件时先开发业务逻辑。
  • 多人协作，每个人负责不同模块，改动经常互相冲突。

分层的目的不是“看起来专业”，而是把会变化的部分隔离起来：硬件变化只影响底层，业务变化只影响上层，中间用稳定的接口连接。

2. 常见的分层结构

层次职责示例依赖
应用层 App产品业务逻辑、状态机、策略温控策略、报警逻辑、界面流程只依赖服务层接口
服务层 Service与具体硬件无关的通用能力参数存储、日志、协议栈、命令解析依赖设备驱动接口
设备驱动层 Device某个外部器件的驱动SHT30 温湿度、W25Q 闪存、OLED依赖总线接口
板级 / 芯片抽象层 BSP/HAL芯片外设和板子引脚I2C、SPI、GPIO、UART 的读写依赖芯片厂商库或寄存器

两条依赖规则：

  1. 只能向下依赖：驱动层不能调用应用层函数。需要“通知上层”时，用回调函数或事件，而不是直接 #include "app.h"。
  2. 不跨层访问：应用层不直接操作 I2C 寄存器，也不直接调用 HAL 库函数。
分层的粒度要和项目规模匹配。几百行的小工具不必强行分四层；但“驱动不依赖业务”“接口与实现分离”这两条，在任何规模的项目里都值得坚持。

3. 头文件就是接口

模块对外暴露什么，完全由头文件决定。好的头文件只包含调用者必须知道的东西：类型、函数声明、少量常量。

3.1 不透明指针隐藏内部结构

/* sensor.h —— 调用者只知道有一个 sensor_t，看不到里面的字段 */
typedef struct sensor sensor_t;

sensor_t *sensor_create(const sensor_config_t *cfg);
int       sensor_read(sensor_t *s, int16_t *temp_x10, uint16_t *hum_x10);
void      sensor_destroy(sensor_t *s);

/* sensor.c —— 只有实现文件知道完整定义 */
struct sensor {
    i2c_bus_t *bus;
    uint8_t    addr;
    uint32_t   last_read_ms;
    int16_t    cached_temp;
};

这样调用者无法直接修改内部字段，实现改了结构体也不需要重新编译所有调用者。嵌入式里常常不希望动态分配，可以改为“调用者提供存储”：

/* 头文件给出足够大的不透明存储，实现中用 _Static_assert 保证真实结构体放得下 */
typedef struct { uint32_t opaque[8]; } sensor_storage_t;
sensor_t *sensor_init(sensor_storage_t *mem, const sensor_config_t *cfg);

3.2 头文件的几条规矩

  • 每个头文件都能单独被包含并编译通过：自己需要的 <stdint.h> 等由自己包含。
  • 只放声明，不放变量定义；需要共享的全局变量用 extern 声明、在一个 .c 中定义，并尽量用访问函数代替。
  • 内部函数在 .c 中用 static，不要出现在头文件里。
  • 需要被 C++ 调用的头文件加 extern "C" 包裹。

4. 用函数指针表抽象设备

当同一类设备有多种实现（多款温度传感器、多种存储介质），可以借鉴 Linux 驱动的做法：定义一个操作表（ops），每种设备提供自己的实现，上层只通过操作表调用。

/* temp_sensor.h —— 统一接口 */
typedef struct temp_sensor temp_sensor_t;

typedef struct {
    int (*init)(temp_sensor_t *dev);
    int (*read)(temp_sensor_t *dev, int16_t *temp_x10);
    int (*sleep)(temp_sensor_t *dev);
} temp_sensor_ops_t;

struct temp_sensor {
    const temp_sensor_ops_t *ops;   /* 指向某种传感器的实现 */
    void                    *ctx;   /* 该实例的私有数据：总线、地址、校准值 */
    const char              *name;
};

static inline int temp_sensor_read(temp_sensor_t *dev, int16_t *t)
{
    return dev->ops->read(dev, t);
}
/* sht30.c —— 一种具体实现 */
typedef struct {
    i2c_bus_t *bus;
    uint8_t    addr;
} sht30_ctx_t;

static int sht30_read(temp_sensor_t *dev, int16_t *temp_x10)
{
    sht30_ctx_t *c = dev->ctx;
    uint8_t cmd[2] = { 0x24, 0x00 };          /* 单次测量，高重复性，不使用时钟拉伸 */
    uint8_t rx[6];
    if (i2c_write(c->bus, c->addr, cmd, sizeof(cmd)) != 0) return -EIO;
    delay_ms(16);
    if (i2c_read(c->bus, c->addr, rx, sizeof(rx)) != 0) return -EIO;
    if (crc8_sht(rx, 2) != rx[2]) return -EBADMSG;
    uint16_t raw = (uint16_t)((rx[0] << 8) | rx[1]);
    *temp_x10 = (int16_t)(-450 + (int32_t)1750 * raw / 65535);   /* T = -45 + 175 × raw / 65535 */
    return 0;
}

const temp_sensor_ops_t sht30_ops = {
    .init  = sht30_init,
    .read  = sht30_read,
    .sleep = sht30_sleep,
};

上层业务只依赖 temp_sensor_t，换传感器只需要换一个 ops 和 ctx。操作表本身定义为 const，会被放进 Flash，不占 RAM，也不会被意外改写。

5. 依赖注入与可测试性

驱动直接调用 HAL_I2C_Master_Transmit() 时，它就和 HAL 库绑死了，没有硬件就无法测试。把总线也抽象成接口，在创建驱动时“注入”进去，就能在 PC 上用假的总线测试驱动和业务逻辑。

/* i2c_bus.h */
typedef struct i2c_bus {
    int (*write)(struct i2c_bus *bus, uint8_t addr, const uint8_t *buf, size_t len);
    int (*read)(struct i2c_bus *bus, uint8_t addr, uint8_t *buf, size_t len);
    void *hw;
} i2c_bus_t;

/* 测试代码中的假总线：返回预设数据，并记录驱动发出的命令 */
static uint8_t fake_rx[6] = { 0x66, 0x66, 0x93, 0x80, 0x00, 0xA2 };
static int fake_read(i2c_bus_t *bus, uint8_t addr, uint8_t *buf, size_t len)
{
    (void)bus; (void)addr;
    memcpy(buf, fake_rx, len);
    return 0;
}

在 PC 上配合 Unity、CMocka 这类轻量测试框架，可以覆盖 CRC 错误、总线超时、数据边界等难以在真实硬件上构造的情况。业务逻辑越复杂，这种测试的收益越大。

6. 配置与板级差异

同一份代码适配多块板子时，常见的混乱来源是到处散落的 #ifdef BOARD_V2。更可维护的做法：

  • 板级差异集中在一个地方：board.h / board.c 描述引脚、外设实例、器件型号，其他模块只读取板级配置。
  • 用配置表代替条件编译：引脚映射、通道参数做成 const 结构体数组，换板只换表。
  • 编译期选择只出现在边界：例如构建系统根据目标板选择编译 board_v1.c 还是 board_v2.c，而不是在业务代码里写 #ifdef。
/* board_v2.c */
const led_config_t board_leds[] = {
    { .port = GPIOB, .pin = 0,  .active_low = false },   /* 电源灯 */
    { .port = GPIOB, .pin = 7,  .active_low = true  },   /* 告警灯 */
};
const size_t board_led_count = sizeof(board_leds) / sizeof(board_leds[0]);

7. 跨层的错误码与日志约定

  • 统一错误码：整个项目使用一套错误码（例如负的 errno 风格：-EIO、-ETIMEDOUT、-EINVAL），底层返回具体原因，上层决定重试、降级还是报警。
  • 底层不吞错误：驱动不要在内部打印一行日志就返回成功，调用者会以为一切正常。
  • 日志带模块标签：每个模块定义自己的 TAG，日志级别可以按模块调整。
  • 边界处转换：对外协议的错误码和内部错误码分开，在协议层做一次映射，避免内部重构影响上位机。

8. 初始化顺序与模块生命周期

模块之间有依赖：传感器驱动依赖 I2C 总线，参数服务依赖 Flash 驱动，应用依赖参数服务。初始化顺序错了，轻则读到默认值，重则访问未初始化的外设。

建议每个模块都遵循相同的生命周期接口：init（准备资源，不启动）、start（开始工作）、stop、deinit，并在一个地方按依赖顺序集中调用：

void system_init(void)
{
    board_init();          /* 时钟、引脚、调试串口 */
    log_init();            /* 越早越好，后续模块出错时能看到日志 */
    i2c_bus_init(&i2c1);
    flash_init();
    param_init();          /* 依赖 flash */
    sensor_init_all();     /* 依赖 i2c 和 param 中的校准值 */
    app_init();
}

RT-Thread 的 INIT_BOARD_EXPORT、INIT_DEVICE_EXPORT 等宏，利用链接器段把初始化函数按等级自动收集并依次调用，是这一思路的自动化版本，原理和 GNU C 的 section 属性 有关。

9. 目录结构示例

project/
├── app/            # 业务逻辑：状态机、策略、界面流程
├── service/        # 参数、日志、命令解析、协议
├── drivers/        # 器件驱动：sht30.c、w25qxx.c、oled.c
├── bsp/
│   ├── board_v1/   # 引脚、时钟、外设实例
│   └── board_v2/
├── platform/       # 芯片抽象：i2c_bus、uart_port 的芯片相关实现
├── third_party/    # 厂商库、RTOS、开源组件，尽量不修改
└── test/           # PC 上运行的单元测试和假驱动

第三方代码单独放置并尽量不改。确实需要修改时，记录修改点和原因，否则升级厂商库时会非常痛苦。

10. 工作场景：同一套业务适配两款温湿度传感器

需求：老板子用 SHT30（I2C），新板子换成 AHT20（同样 I2C，但命令和数据格式不同），业务逻辑完全一样。

  1. 定义 temp_sensor_ops_t 接口，业务层只调用 temp_sensor_read()。
  2. 分别实现 sht30_ops 和 aht20_ops，各自处理命令、等待时间和数据换算。
  3. 在 board_v1.c / board_v2.c 中创建对应的传感器实例，并通过 board_get_temp_sensor() 提供给业务层。
  4. 在 PC 上为两种驱动各写一组测试：正常数据、CRC 错误、总线失败，确认换算结果都是放大 10 倍的整数温度。
/* app_climate.c —— 业务层，与具体传感器无关 */
void climate_task(void)
{
    temp_sensor_t *sensor = board_get_temp_sensor();
    int16_t t_x10;
    int err = temp_sensor_read(sensor, &t_x10);
    if (err != 0) {
        LOGW(TAG, "%s read failed: %d", sensor->name, err);
        climate_on_sensor_error(err);
        return;
    }
    climate_update(t_x10);
}

后来又要支持第三款传感器时，改动只有“新增一个驱动文件 + 修改板级文件”，业务代码和测试用例都不需要动。这就是分层带来的实际回报。

11. 模块化设计检查清单

  • 模块之间是否只向下依赖，底层是否通过回调或事件通知上层。
  • 头文件是否只暴露必要接口，能否单独编译通过，内部函数是否加了 static。
  • 同类多实现的设备是否抽象出 ops 接口，操作表是否声明为 const。
  • 驱动是否通过注入的总线接口访问硬件，是否能在 PC 上测试。
  • 板级差异是否集中在 BSP 中，业务代码里是否还散落着 #ifdef BOARD_xxx。
  • 错误码是否统一，底层是否吞掉了错误。
  • 初始化顺序是否集中定义，是否符合模块依赖关系。
  • 第三方代码是否与自研代码分离，修改是否有记录。
