嵌入式 C 编译、链接与启动流程

梳理嵌入式固件从源码到烧录的全过程：编译四个阶段、目标文件中的段、链接脚本与 VMA/LMA、Cortex-M 启动流程、向量表与弱符号、map 文件与常用工具、固件瘦身、RAM 函数与 noinit 段，以及 Bootloader 与 App 的地址划分和跳转。

1. 从源文件到固件

点一下 IDE 的“编译”按钮，几秒后得到一个 .hex 或 .bin。中间经历了什么，平时可以不关心，但下面这些问题都需要理解这条链路才能解决：

  • RAM 明明还有空间，链接却报 region RAM overflowed。
  • 全局变量上电后不是 0，或者初始值不对。
  • 函数在 Flash 擦写时执行就死机，需要放到 RAM 中运行。
  • Bootloader 跳转到 App 后立刻 HardFault。
  • 固件突然大了 10KB，不知道是哪里引入的。

GCC 工具链（arm-none-eabi-gcc）下，一个工程的构建过程可以概括为：

.c / .h  ──预处理──▶  .i  ──编译──▶  .s  ──汇编──▶  .o  ──┐
startup.s ─────────────────────────────汇编──▶  .o  ──┼──链接（按链接脚本）──▶ .elf ──objcopy──▶ .hex / .bin
libc / libgcc / 厂商库  ───────────────────────── .a  ──┘

2. 编译的四个阶段

阶段命令产物能发现的问题
预处理gcc -E main.c -o main.i展开宏、头文件后的源码宏展开错误、头文件包含了错误版本
编译gcc -S main.c汇编代码 .s优化后的实际指令，验证 volatile、内联是否生效
汇编gcc -c main.c目标文件 .o每个文件单独编译，符号尚未确定地址
链接gcc *.o -T link.ld -o app.elf可执行文件未定义符号、重复定义、内存区域溢出

工作中最常用的两个技巧：

  • 宏写得复杂、怀疑展开结果不对时，用 -E 看预处理输出，或在 IDE 里对单个文件生成 .i。
  • 怀疑编译器“优化掉了”某段代码时，用 -S 或 objdump -d 看生成的指令，而不是猜。

3. 目标文件里的段

编译器把不同性质的内容放进不同的段（section），链接器再按链接脚本把它们放到 Flash 或 RAM 的不同位置。

段内容存放位置运行时
.text函数代码Flash直接从 Flash 执行
.rodataconst 全局变量、字符串常量、查找表Flash只读
.data有非零初值的全局 / 静态变量初值存 Flash，运行时在 RAM启动代码从 Flash 拷贝到 RAM
.bss无初值或初值为 0 的全局 / 静态变量只在 RAM 中占位启动代码清零
栈 / 堆局部变量、mallocRAM由链接脚本预留
 
uint32_t boot_count;                 /* .bss：上电清零 */
uint32_t baud = 115200;              /* .data：Flash 中存一份初值，启动时拷贝到 RAM */
const uint16_t crc_table[256] = { 0x0000, 0x1021, 0x2042 /* ... */ };  /* .rodata：只在 Flash 中 */
static uint8_t rx_buf[1024];         /* .bss：占 1KB RAM */

void func(void)
{
    uint8_t tmp[256];                /* 栈：运行到这里时才占用 */
    static uint8_t cache[64];        /* .bss：虽然写在函数里，但是全局生命周期 */
}
一个常见的 RAM 浪费：大表格忘了加 const，例如字库、CRC 表、正弦表。没有 const 的表进入 .data，既占 Flash（存初值）又占同样大小的 RAM。加上 const 后只占 Flash。

4. 链接脚本：MEMORY 与 SECTIONS

链接脚本（.ld）告诉链接器：芯片有哪些存储区域、各个段放在哪里、导出哪些符号给启动代码使用。下面是 Cortex-M 工程中常见结构的精简版：

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

_estack = ORIGIN(RAM) + LENGTH(RAM);     /* 栈顶：RAM 末尾，栈向下增长 */
_Min_Stack_Size = 0x800;                 /* 2KB，仅用于链接时检查空间是否足够 */

SECTIONS
{
  .isr_vector : { KEEP(*(.isr_vector)) } > FLASH       /* 向量表必须在起始位置 */

  .text : {
    *(.text*)
    *(.rodata*)
    . = ALIGN(4);
    _etext = .;
  } > FLASH

  _sidata = LOADADDR(.data);             /* .data 初值在 Flash 中的地址 */
  .data : {
    _sdata = .;
    *(.data*)
    . = ALIGN(4);
    _edata = .;
  } > RAM AT> FLASH                      /* 运行地址在 RAM，加载地址在 Flash */

  .bss (NOLOAD) : {
    _sbss = .;
    *(.bss*)
    *(COMMON)
    . = ALIGN(4);
    _ebss = .;
  } > RAM

  ._user_stack (NOLOAD) : {
    . = . + _Min_Stack_Size;             /* 空间不够时链接报错，而不是运行时才溢出 */
  } > RAM
}

两个关键概念：

  • VMA（运行地址）与 LMA（加载地址）：.data 的 VMA 在 RAM，LMA 在 Flash。程序烧录在 Flash 里，上电后由启动代码把 LMA 处的初值拷贝到 VMA。> RAM AT> FLASH 正是在表达这件事。
  • KEEP：开启 --gc-sections 后，链接器会删除没有被引用的段。向量表、通过段自动收集的初始化函数表没有被代码直接引用，必须用 KEEP 保留。

5. 启动流程：从复位到 main

Cortex-M 上电后，硬件做两件事：从地址 0（通常映射到 Flash 起始）读取初始栈指针 MSP，从地址 4 读取复位向量并跳转。之后就是启动代码的工作：

extern uint32_t _sidata, _sdata, _edata, _sbss, _ebss;
extern int main(void);
extern void SystemInit(void);
extern void __libc_init_array(void);

void Reset_Handler(void)
{
    /* 1. 把 .data 的初值从 Flash 拷贝到 RAM */
    uint32_t *src = &_sidata;
    for (uint32_t *dst = &_sdata; dst < &_edata; ) {
        *dst++ = *src++;
    }
    /* 2. 把 .bss 清零 */
    for (uint32_t *dst = &_sbss; dst < &_ebss; ) {
        *dst++ = 0U;
    }
    /* 3. 时钟、FPU、向量表偏移等芯片级初始化（厂商提供） */
    SystemInit();
    /* 4. C 库初始化：调用构造函数、静态初始化代码 */
    __libc_init_array();
    /* 5. 进入 main，正常不会返回 */
    main();
    for (;;) { }
}

厂商提供的 startup_xxx.s 做的就是这些事，只是用汇编写成。理解这段流程后，很多现象就有了解释：

  • “全局变量初值不对”：链接脚本中 .data 没有正确设置 LMA，或者启动代码被修改过。
  • “变量上电不是 0”：变量被放进了自定义段，而启动代码只清零 .bss。
  • “SystemInit 之前的代码不能用全局变量”：此时 .data / .bss 可能还没准备好（部分启动文件在拷贝之前调用 SystemInit）。

6. 中断向量表与弱符号

向量表是一个函数指针数组，第 0 项是初始栈顶，之后依次是复位、NMI、HardFault 和各个外设中断。启动文件中所有中断处理函数都被定义为弱符号，默认指向一个死循环：

void Default_Handler(void) { for (;;) { } }

void USART1_IRQHandler(void) __attribute__((weak, alias("Default_Handler")));
void TIM2_IRQHandler(void)   __attribute__((weak, alias("Default_Handler")));

用户在自己的代码里定义同名函数（强符号），链接时就会覆盖弱符号。这带来一个经典问题：中断函数名拼错了，编译链接都不会报错，中断触发后进入 Default_Handler 死循环，看起来像“程序跑飞了”。遇到“开中断就卡死”，先检查函数名是否和启动文件中完全一致。C++ 文件中的中断函数还要加 extern "C"，否则名字被修饰后同样无法覆盖。

7. 读懂 map 文件和常用工具

链接时加 -Wl,-Map=app.map 生成 map 文件。它记录了每个段、每个函数和变量的地址与大小，是分析固件体积和内存分布的第一手资料。

# 各段总大小：text = 代码 + 只读数据，data 同时占 Flash 和 RAM，bss 只占 RAM
arm-none-eabi-size app.elf
#    text    data     bss     dec     hex filename
#   48212     420   18996   67628   1082c app.elf

# 按大小排序列出符号，找出最占空间的函数和变量
arm-none-eabi-nm --size-sort --print-size --radix=d app.elf | tail -20

# 反汇编，查看某个函数实际生成的指令
arm-none-eabi-objdump -d -S app.elf > app.lst

# 把崩溃时的 PC 地址翻译成源文件和行号
arm-none-eabi-addr2line -e app.elf -f -C 0x08003A5C

Flash 占用 = text + data，RAM 占用 = data + bss（另加栈和堆的预留）。addr2line 要配合带调试信息（-g）的 elf 使用，发布版本也建议保留同一次构建的 elf 文件，现场崩溃时才能把地址翻译回代码。

8. 减小固件体积

手段做法效果
删除未使用的函数和数据编译加 -ffunction-sections -fdata-sections，链接加 -Wl,--gc-sections通常能减少 10%~30%
优化等级-Os 以体积为目标；调试用 -Og-Os 相比 -O0 显著减小
精简 C 库使用 newlib-nano：--specs=nano.specsprintf 等函数小很多
避免浮点 printf不链接 -u _printf_float，或自己格式化定点数可省数 KB
链接时优化-flto跨文件内联与删除，效果明显，但调试信息变差
检查大常量用 nm --size-sort 找出大表，确认是否必要、是否加了 const针对性强

体积突然变大时，对比两次构建的 nm --size-sort 输出，通常能立刻定位到新增的大块内容，例如意外引入了浮点格式化、sprintf 或一张未压缩的图片。

9. 把代码或数据放到指定位置

9.1 在 RAM 中运行的函数

很多 MCU 在擦写内部 Flash 时，同一块 Flash 上的代码无法读取执行。Flash 编程函数需要放在 RAM 中运行：

__attribute__((section(".ramfunc"), noinline))
void flash_program_word(uint32_t addr, uint32_t data)
{
    /* 擦写过程中不能调用 Flash 中的其他函数，也要避免中断从 Flash 中取指 */
}

链接脚本中需要把 .ramfunc 放进 .data 一起拷贝到 RAM（*(.ramfunc*) 写在 .data 段内）。部分厂商工程已经预定义了类似的段名，如 .RamFunc、.ram_code。

9.2 复位后保留的数据：.noinit

.bss 在每次复位时被清零。如果希望记录“上一次是为什么复位的”“崩溃时的 PC 地址是多少”，就需要一块启动代码不会清零的 RAM：

typedef struct {
    uint32_t magic;
    uint32_t reset_count;
    uint32_t last_fault_pc;
    uint32_t last_fault_lr;
} crash_info_t;

__attribute__((section(".noinit"))) static crash_info_t crash_info;

void crash_info_check(void)
{
    if (crash_info.magic != 0xC0DEFA11U) {          /* 冷启动：内容是随机值，初始化 */
        memset(&crash_info, 0, sizeof(crash_info));
        crash_info.magic = 0xC0DEFA11U;
    }
    crash_info.reset_count++;
}

链接脚本中增加 .noinit (NOLOAD) : { *(.noinit*) } > RAM，并放在 .bss 之外。HardFault 处理函数把现场写进这块区域后触发复位，重启后上报，就能拿到远程设备的崩溃信息。

9.3 固定地址的版本信息

__attribute__((section(".fw_info"), used))
const struct {
    uint32_t magic;
    uint32_t version;
    char     build[24];
} fw_info = { 0x46574E46U, 0x00010203U, BUILD_GIT_HASH };

把版本结构放在固定偏移（如向量表之后），Bootloader 或升级工具无需解析 elf 就能读取版本号。used 属性防止它因为没被引用而被优化掉。

10. 工作场景：Bootloader 与 App 的地址划分

一个常见的划分：Flash 前 32KB 给 Bootloader，之后给 App。

0x08000000 ┌──────────────┐
           │  Bootloader  │  32KB
0x08008000 ├──────────────┤
           │     App      │  链接脚本 ORIGIN = 0x08008000
           │              │
           └──────────────┘

App 侧需要修改两处：链接脚本中 FLASH 的 ORIGIN 和 LENGTH；启动后把向量表偏移寄存器 SCB->VTOR 设为 0x08008000（很多工程在 SystemInit 中通过宏 VECT_TAB_OFFSET 配置）。

Bootloader 跳转到 App 的标准步骤：

typedef void (*app_entry_t)(void);

void jump_to_app(uint32_t app_addr)
{
    uint32_t sp    = *(volatile uint32_t *)app_addr;          /* App 向量表第 0 项：栈顶 */
    uint32_t entry = *(volatile uint32_t *)(app_addr + 4U);   /* 第 1 项：复位入口 */

    if ((sp & 0x2FF00000U) != 0x20000000U) {                  /* 简单校验栈顶落在 RAM 区间 */
        return;
    }
    __disable_irq();
    SysTick->CTRL = 0;                                         /* 关闭 SysTick */
    for (uint32_t i = 0; i < 8U; i++) {                        /* 关闭并清除所有 NVIC 中断 */
        NVIC->ICER[i] = 0xFFFFFFFFU;
        NVIC->ICPR[i] = 0xFFFFFFFFU;
    }
    /* 反初始化 Bootloader 用过的外设和时钟（视情况恢复到复位状态） */
    SCB->VTOR = app_addr;
    __set_MSP(sp);
    __enable_irq();
    ((app_entry_t)entry)();
}

跳转后立刻 HardFault 或中断异常，最常见的原因是：App 链接地址没改、VTOR 没设置、Bootloader 开着的中断在 App 里没有处理函数、App 依赖的时钟配置与 Bootloader 留下的状态冲突。实际项目中通常还要校验 App 的 CRC，校验失败则停留在 Bootloader 等待升级。

11. 编译链接检查清单

  • 大常量表、字库是否加了 const，避免同时占用 Flash 和 RAM。
  • 是否开启 -ffunction-sections -fdata-sections 与 --gc-sections，向量表等是否用 KEEP 保留。
  • 链接脚本是否为栈和堆预留了空间，RAM 不足能否在链接阶段报错。
  • 中断函数名是否与启动文件完全一致，C++ 中是否加了 extern "C"。
  • 是否生成 map 文件，每次发布是否保留对应的 elf 以便 addr2line 定位。
  • 需要在 RAM 中运行的函数、需要复位保留的数据，是否放进了正确的段，链接脚本是否同步修改。
  • Bootloader + App 方案中，App 的链接地址、VTOR、跳转前的外设和中断清理是否都已处理。
  • 固件体积变化是否有记录，异常增长时能否通过 nm --size-sort 对比定位。
