C语言调试与工程排错整理

本文整理 C 语言和嵌入式工程中常见的调试思路，包括编译告警、日志、断点、HardFault、map 文件、内存占用、数组越界、栈溢出、未初始化变量和错误码设计。

工程调试的关键不是“碰运气改代码”，而是先缩小问题范围，再用日志、断点、数据校验和最小复现逐步定位根因。

1. C 语言问题为什么难排查

C 语言直接操作内存，没有自动边界检查。一次错误写入可能不会立即崩溃，而是在后续任意位置表现为数据异常、死机、重启或通信错误。

  • 数组越界可能破坏旁边变量。
  • 野指针可能写坏栈、堆或全局数据。
  • 未初始化变量可能导致随机状态。
  • 结构体对齐问题可能导致上下位机解析不一致。
  • 中断并发问题可能偶发出现，难以稳定复现。

2. 编译告警优先级

编译告警不是噪声，而是潜在 bug 的提前暴露。工程中应尽量开启较高告警等级，并把核心模块做到无告警。 

// 常见危险告警类型
// 1. 未使用或未初始化变量
// 2. 有符号 / 无符号比较
// 3. 隐式函数声明
// 4. 类型不匹配
// 5. 可能的数组越界
// 6. 返回值未使用

如果某个告警确实可以忽略，也应该通过注释说明原因，而不是长期让告警堆积。告警太多会让真正的问题被淹没。

3. printf 日志与断点调试

日志适合观察长期运行过程和偶发问题，断点适合分析确定路径下的变量变化。二者不是替代关系，而是互补关系。 

#define APP_LOGE(tag, fmt, ...)  printf("[E][%s] " fmt "\n", tag, ##__VA_ARGS__)
#define APP_LOGI(tag, fmt, ...)  printf("[I][%s] " fmt "\n", tag, ##__VA_ARGS__)

APP_LOGI("uart", "rx len=%u", rx_len);
APP_LOGE("crc", "crc error: calc=%04X recv=%04X", calc_crc, recv_crc);

日志内容要包含模块名、关键参数、错误码和状态变化。不要只打印“error”，否则后续无法判断错误发生在哪一步。

4. HardFault / 崩溃问题排查

Cortex-M 项目中，HardFault 常见原因包括空指针、非法地址访问、栈溢出、函数指针错误、数组越界和中断优先级配置错误。

  • 先确认是否每次固定位置崩溃，还是随机崩溃。
  • 查看 PC、LR、SP 等寄存器，定位崩溃前执行位置。
  • 检查最近修改的指针、数组、结构体和中断代码。
  • 减小复现范围，保留最小触发路径。

随机 HardFault 优先怀疑内存破坏、栈溢出和中断并发问题；固定位置 HardFault 优先检查空指针、非法地址和函数指针。

5. map 文件和内存占用分析

map 文件可以看到代码段、只读数据、全局变量、静态变量和链接地址。分析 RAM 不够、Flash 变大、某个数组异常占用时，map 文件非常有用。 

// 排查方向
// .text    代码大小
// .rodata  只读常量.字符串.const 表
// .data    有初值的全局/静态变量
// .bss     无初值的全局/静态变量
// stack    栈空间
// heap     堆空间

如果一个大数组放在全局区，会体现在 bss 或 data 中；如果放在函数局部变量中，则会消耗栈空间，栈太小时容易运行后崩溃。

6. 数组越界和栈溢出

数组越界是 C 语言中最常见的问题之一。所有写数组的位置都应该检查索引和长度，尤其是串口接收、文件解析、协议解析和字符串处理。 

int safe_copy(uint8_t *dst, uint16_t dst_size, const uint8_t *src, uint16_t src_len)
{
    if (dst == NULL || src == NULL) {
        return -1;
    }

    if (src_len > dst_size) {
        return -2;
    }

    for (uint16_t i = 0; i < src_len; i++) {
        dst[i] = src[i];
    }

    return 0;
}

大数组不要轻易放在函数局部变量中。嵌入式项目里，几 KB 的局部数组就可能导致栈溢出。

7. 未初始化变量与随机问题

未初始化变量会让程序表现出随机性。局部变量如果没有显式初始化，其值是不确定的。结构体在使用前也应该清零或完整赋值。 

typedef struct {
    uint8_t cmd;
    uint16_t len;
    uint8_t payload[64];
} frame_t;

frame_t frame = {0};

如果某个问题上电后偶尔出现、重启后消失、加一条日志后现象变化，要优先检查未初始化变量、越界访问和时序问题。

8. 接口返回值和错误码设计

工程代码中，函数失败必须能说明原因。简单返回 0/1 在复杂项目里不够用，建议定义统一错误码，方便日志和上层处理。 

typedef enum {
    APP_OK = 0,
    APP_ERR_PARAM,
    APP_ERR_TIMEOUT,
    APP_ERR_CRC,
    APP_ERR_NO_MEMORY,
    APP_ERR_IO,
} app_err_t;

底层驱动返回具体错误，上层业务再决定是否重试、报警、复位设备或提示用户。不要在底层函数里偷偷吞掉错误。

9. 完整案例：串口偶发解析错误如何取证

假设设备偶尔把一帧 32 字节数据报告为“长度错误”。直接在报错行加一个断点，往往会改变时序，使问题消失。更稳妥的做法是记录输入摘要、当前状态、缓冲区容量和返回码，再用固定输入离线重放解析函数。 

typedef struct {
    uint16_t expected;
    uint16_t received;
    uint16_t capacity;
    int error;
} parse_snapshot_t;

int copy_payload(uint8_t *dst,
                 uint16_t capacity,
                 const uint8_t *src,
                 uint16_t length,
                 parse_snapshot_t *snapshot)
{
    if (snapshot != NULL) {
        snapshot->expected = length;
        snapshot->received = 0U;
        snapshot->capacity = capacity;
        snapshot->error = 0;
    }
    if (dst == NULL || src == NULL || snapshot == NULL) {
        return -1;
    }
    if (length > capacity) {
        snapshot->error = -2;
        return -2;
    }

    for (uint16_t i = 0U; i < length; ++i) {
        dst[i] = src[i];
        snapshot->received = (uint16_t)(i + 1U);
    }
    return 0;
}

现场记录应包含固件版本、硬件版本、输入长度、缓冲区容量和最近一次状态，而不必把整帧敏感数据全部打印出来。随后用同一组参数跑单元测试，验证长度等于容量、长度超过容量、空指针和重复调用等边界，才能判断修复是否真正覆盖根因。

10. 推荐的编译告警选项

GCC 默认几乎不给告警。下面是一组适合嵌入式项目的起点，新项目建议从第一天就开启，老项目可以先在新增模块上开启：

选项能发现的问题
-Wall -Wextra未使用变量、未初始化、缺少返回值等基础问题
-Wshadow局部变量遮蔽同名全局变量或外层变量
-Wconversion -Wsign-conversion隐式截断、有符号与无符号转换（初期告警较多，可逐步清理）
-Wdouble-promotionfloat 被意外提升为 double（单精度 FPU 芯片上很关键）
-Wformat=2printf 格式串与参数类型不匹配
-Wundef#if 中使用了未定义的宏（常见于拼错配置宏名）
-Wcast-align指针强转导致对齐要求提高，在 Cortex-M0 上可能 HardFault
-Wstrict-prototypes -Wmissing-prototypes函数缺少原型、void f() 未声明参数
-Werror=implicit-function-declaration调用未声明的函数（参数和返回值按 int 处理，极其危险）
-Wstack-usage=512单个函数栈使用超过阈值

厂商库和第三方代码的告警可以用 -isystem 包含其头文件，或对这些目录单独降低告警等级，避免淹没自研代码的告警。CI 中对自研模块开启 -Werror，能防止告警重新积累。

11. 静态分析与断言

编译器之外，静态分析工具能在不运行程序的情况下发现越界、空指针、资源泄漏和未定义行为：

# cppcheck：轻量、开源，适合直接接入 CI
cppcheck --enable=warning,style,performance,portability --std=c99 \
         --inline-suppr -I inc/ src/

# clang-tidy：规则丰富，bugprone-* 和 cert-* 类检查对嵌入式很有价值
clang-tidy src/*.c -checks='bugprone-*,cert-*,clang-analyzer-*' -- -Iinc -std=c99

汽车、医疗等行业还会使用 MISRA C 规则集配合商业工具（PC-lint Plus、Polyspace 等）。即使项目没有合规要求，MISRA 中“禁止隐式类型转换”“switch 必须有 default”“函数单一出口”等规则也值得参考。

断言用来捕获“理论上不应该发生”的情况。嵌入式中通常自定义断言处理函数，记录文件名和行号后进入安全状态：

void app_assert_failed(const char *file, int line);

#ifdef NDEBUG
#define APP_ASSERT(expr)  ((void)0)
#else
#define APP_ASSERT(expr)  ((expr) ? (void)0 : app_assert_failed(__FILE__, __LINE__))
#endif

/* 编译期断言：结构体大小、数组长度与枚举数量的一致性 */
_Static_assert(sizeof(param_block_t) == 64, "param block layout changed");
_Static_assert(ARRAY_SIZE(cmd_handlers) == CMD_COUNT, "cmd table out of sync");

断言不能替代输入校验：来自串口、网络、文件的数据随时可能非法，必须用正常的错误处理返回错误码；断言只用于检查程序内部的约定。

12. HardFault 现场解析（Cortex-M）

发生 HardFault 时，硬件已经把关键寄存器压入栈中。只要在处理函数里把这些值取出来，就能知道崩溃发生在哪条指令。

typedef struct {
    uint32_t r0, r1, r2, r3, r12, lr, pc, xpsr;    /* 硬件自动压栈的顺序 */
} stack_frame_t;

void hardfault_handler_c(stack_frame_t *frame)
{
    volatile uint32_t cfsr  = SCB->CFSR;           /* 可配置故障状态，0xE000ED28 */
    volatile uint32_t hfsr  = SCB->HFSR;           /* HardFault 状态，0xE000ED2C */
    volatile uint32_t mmfar = SCB->MMFAR;          /* 存储器管理故障地址 */
    volatile uint32_t bfar  = SCB->BFAR;           /* 总线故障地址 */

    crash_record(frame->pc, frame->lr, cfsr, (cfsr & (1U << 15)) ? bfar : mmfar);
    for (;;) { }                                   /* 调试时停在这里；量产版本记录后复位 */
}

/* 判断异常发生时使用的是 MSP 还是 PSP（RTOS 任务中为 PSP），把栈帧地址传给 C 函数 */
__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile(
        "tst lr, #4      \n"
        "ite eq          \n"
        "mrseq r0, msp   \n"
        "mrsne r0, psp   \n"
        "b hardfault_handler_c \n");
}

上面的汇编适用于 Cortex-M3/M4/M7。Cortex-M0/M0+ 不支持 ite 条件执行，需要改用分支指令实现。

拿到寄存器后按下面的思路分析：

线索含义
frame->pc出错指令的地址，用 addr2line 翻译成源码行
frame->lr调用者的返回地址，帮助判断是从哪里调用进来的
CFSR 的 PRECISERR + BFARVALID精确总线错误，BFAR 就是被访问的非法地址（常见于空指针 + 偏移）
CFSR 的 IMPRECISERR非精确总线错误，PC 已经越过出错指令；调试时可通过 SCB->ACTLR 的 DISDEFWBUF 位关闭写缓冲，把它变成精确错误
CFSR 的 UNDEFINSTR / INVSTATE执行了非法指令，通常是函数指针错误或跳转到了非 Thumb 地址（地址最低位为 0）
CFSR 的 UNALIGNED / DIVBYZERO非对齐访问、除零（需在 SCB->CCR 中开启对应陷阱）
CFSR 的 STKERR / MSTKERR异常压栈失败，几乎可以确定是栈溢出
HFSR 的 FORCED可配置故障（MemManage / BusFault / UsageFault）未单独使能，被升级为 HardFault

13. 看门狗、复位原因与崩溃记录

现场设备出问题时通常没有调试器，能依靠的只有设备自己留下的证据。三件事建议每个项目都做：

  • 记录复位原因：上电后读取芯片的复位标志寄存器（如 STM32 的 RCC->CSR），区分上电复位、外部引脚复位、看门狗复位、软件复位、低电压复位，读取后清除标志，并写入日志或上报。“设备偶尔重启”时，这是第一条线索。
  • 崩溃信息跨复位保存：HardFault、断言失败时，把 PC、LR、故障寄存器、任务名写入启动代码不会清零的 RAM 区域（.noinit 段），然后复位；重启后检查并上报。实现方式见 编译、链接与启动流程。
  • 看门狗要喂得“有意义”：不要在定时器中断里无条件喂狗，那样主循环卡死了看门狗也不会复位。推荐每个关键任务定期报告“我还活着”，由一个监控任务确认所有任务都按时报告后才喂狗。
#define TASK_BIT_COMM    (1U << 0)
#define TASK_BIT_SENSOR  (1U << 1)
#define TASK_BIT_CTRL    (1U << 2)
#define TASK_BITS_ALL    (TASK_BIT_COMM | TASK_BIT_SENSOR | TASK_BIT_CTRL)

static volatile uint32_t alive_bits;

void task_checkin(uint32_t bit)        /* 各任务在主循环中调用 */
{
    uint32_t key = irq_save();
    alive_bits |= bit;
    irq_restore(key);
}

void watchdog_task(void)               /* 周期小于看门狗超时时间 */
{
    uint32_t key = irq_save();
    uint32_t bits = alive_bits;
    alive_bits = 0U;
    irq_restore(key);

    if (bits == TASK_BITS_ALL) {
        iwdg_feed();
    } else {
        LOGE(TAG, "task stalled, alive=0x%02lX", (unsigned long)bits);   /* 不喂狗，等待复位 */
    }
}

14. 日志系统的工程化

printf 直接输出到串口在项目初期够用，但设备一多、问题一复杂就会遇到瓶颈：日志太多刷屏、关键日志被淹没、打印阻塞影响时序、现场没有串口可看。成熟一些的日志系统通常具备：

  • 分级：ERROR / WARN / INFO / DEBUG，发布版本在编译期去掉 DEBUG 级别，减小体积和开销。
  • 模块标签与时间戳：每条日志带毫秒时间戳和模块名，便于对照多个模块的时序。
  • 异步输出：日志先写入环形缓冲区，由低优先级任务或 DMA 发送，避免在中断或高优先级任务中被串口速度拖慢。
  • 限流：同一条错误在循环里每毫秒触发一次时，只记录首次和累计次数，防止刷屏和缓冲区溢出。
  • 持久化关键日志：错误级别日志额外写入 Flash 中的小型环形日志区，设备返修时可以导出。
#define LOG_LEVEL_ERROR 1
#define LOG_LEVEL_WARN  2
#define LOG_LEVEL_INFO  3
#define LOG_LEVEL_DEBUG 4

#ifndef LOG_LEVEL
#define LOG_LEVEL LOG_LEVEL_INFO
#endif

#define LOG_IMPL(lvl, ch, tag, fmt, ...) \
    do { if ((lvl) <= LOG_LEVEL) log_write(ch, tag, fmt, ##__VA_ARGS__); } while (0)

#define LOGE(tag, fmt, ...) LOG_IMPL(LOG_LEVEL_ERROR, 'E', tag, fmt, ##__VA_ARGS__)
#define LOGD(tag, fmt, ...) LOG_IMPL(LOG_LEVEL_DEBUG, 'D', tag, fmt, ##__VA_ARGS__)

LOG_LEVEL 是编译期常量，低于等级的日志调用会被编译器整体删除。注意日志参数中不要包含有副作用的表达式（如 LOGD(TAG, "%d", count++)），否则发布版本和调试版本的行为会不同。

15. 版本信息与问题可追溯

“这台设备跑的到底是哪个版本？”是现场排查的第一个问题。建议把以下信息编译进固件，并能通过命令、日志或上位机读取：

  • 语义化版本号（如 1.4.2）和构建号。
  • 代码仓库的提交哈希，以及是否有未提交的修改（dirty 标记）。
  • 构建时间、编译器版本、目标板型号。
/* 构建系统传入：-DGIT_HASH=\"$(git rev-parse --short HEAD)\" */
#ifndef GIT_HASH
#define GIT_HASH "unknown"
#endif

const char fw_build_info[] = "fw 1.4.2 (" GIT_HASH ") " __DATE__ " " __TIME__;

同时要保存每个发布版本对应的 elf 和 map 文件。设备上报的崩溃 PC 地址，只有对照同一次构建的 elf 才能正确翻译成源码位置。

16. 工程排错清单

  • 先确认问题是否可稳定复现。
  • 记录输入条件、硬件版本、固件版本和操作步骤。
  • 先看编译告警，再看运行日志。
  • 检查最近修改过的指针、数组、结构体和中断代码。
  • 给所有缓冲区操作增加长度检查。
  • 确认大数组是否导致栈溢出。
  • 确认结构体是否初始化。
  • 把复杂问题拆成最小复现程序。
  • 自研代码是否开启了 -Wall -Wextra 等告警，CI 中是否对新增告警报错。
  • 是否接入 cppcheck、clang-tidy 等静态分析，断言是否只用于内部约定而非输入校验。
  • HardFault 处理函数是否能输出 PC、LR、CFSR、BFAR/MMFAR，是否保留了对应构建的 elf。
  • 上电是否记录复位原因，崩溃信息能否跨复位保存并上报。
  • 看门狗是否由监控任务在所有关键任务都报告存活后才喂。
  • 日志是否分级、带时间戳和模块标签，是否异步输出并限流。
  • 固件是否内置版本号、提交哈希和构建信息，并能在现场读取。
